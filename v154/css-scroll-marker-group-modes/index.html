Is a row of carousel dots a list of links, or a set of tabs?

Chrome 135 let CSS generate carousel markers with ::scroll-marker-group. Chrome 154 answers the question that shipped alongside them: what are those markers to a keyboard or a screen reader? Two new keywords on the same property choose an answer — links makes the group a navigation list of sequential tab stops, tabs makes it a WAI-ARIA tablist with roving focus, arrow keys, and inactive panels pruned from the accessibility tree.

concepts

  1. The grammar, measured

    The spec grammar is none | [ [ before | after ] || [ links | tabs ] ] — position and mode, either order, either one alone. Every form the grammar names is fed to CSS.supports live, plus invalid controls, plus a serialization inspector that catches mode-aware computed values.

  2. A carousel that declares its mode

    A real scroll-marker carousel — working today — whose scroll-marker-group declaration you switch between after, after links, after tabs and the rest. The computed value is read back live, so a mode keyword the browser rejects is visible as a cascade fallback, not a guess.

  3. Links mode vs tabs mode, by hand

    The two semantic targets the keywords map to, built as real HTML you can keyboard through: a <nav> of anchor links next to a WAI-ARIA tablist with roving tabindex. A live focus journal shows the difference the one keyword will make natively.

why it shipped

A marker group is interactive chrome the browser builds for you, and interactive chrome has to mean something to assistive technology. The first release of ::scroll-marker-group could not decide what: a photo carousel's dots behave like tabs (one stop, arrow keys, panels), while a table of contents' markers behave like links (each its own stop, activation jumps you to the content). Those are different ARIA patterns with different focus orders, and no heuristic can pick between them.

So the choice became part of the property. links — the default when the keyword is omitted — maps the group to navigation and each marker to link, every marker a sequential tab stop, activation moving the sequential-focus starting point to the target. tabs maps the group to tablist and the markers to tab, only the active marker a tab stop, arrow keys switching within the group, activation retaining focus on the marker, and content of inactive panels hidden from the accessibility tree without any interactivity: inert bookkeeping by the author.

the API shape

/* Grammar: none | [ [ before | after ] || [ links | tabs ] ] */

.slides {
  overflow-x: auto;
  scroll-snap-type: x mandatory;
  scroll-marker-group: after tabs;   /* a tablist below the scroller */
}
.toc {
  scroll-marker-group: before links; /* a nav list above — also the default mode */
}

.slides > section::scroll-marker { content: "•" / attr(data-label); }
.slides > section::scroll-marker:target-current { background: var(--accent-blue); }

enabling it now

The mode keywords ship for all users in Chrome 154 (desktop, Android, WebView). The Blink runtime flag is CSSScrollMarkerGroupModes (runtime_enabled_features.json5; there is no dedicated chrome://flags entry). On an earlier Chrome or Canary, launch with --enable-blink-features=CSSScrollMarkerGroupModes, or --enable-features=CSSScrollMarkerGroupModes, or enable chrome://flags/#enable-experimental-web-platform-features.

Measured on the Chromium 141 these pages were built with, without any flag: the two-keyword forms already parse — after tabs, after links, before tabs are all accepted, and a plain after already computes to after links, mode included. What does not parse yet is the rest of the spec grammar: a bare links or tabs with the position omitted, and the reversed order tabs before, are rejected. The pages measure whichever browser is visiting rather than assuming either state, and the parts that cannot be probed from script — the roles, the roving focus, the accessibility-tree pruning — are labelled as manual observation, with a hand-built reference implementation to make them concrete anywhere.

One more measured fact worth knowing before 154 arrives: inspected through the DevTools accessibility tree on that same Chromium 141, a marker group is exposed as a tablist with tab children no matter which mode the computed value reports — the grammar landed ahead of the semantics. Since links is the default mode, shipping 154 changes existing carousels too: a marker group that never declares a mode moves from today's tablist to a navigation list of links unless its author writes tabs.

portfolio notes

Basic carousel and marker-styling use cases — pagination dots, numbered markers, progress trackers, tabbed sections built on the base property — shipped with the Chrome 135 scroll-marker feature and are not re-demonstrated here; these pages cover only what the mode keywords add. A configuration-tooling angle is folded into the grammar page's free-form value tester and serialization inspector rather than a separate page, because the property's entire configurable surface is five keywords. The edge/failure angle is folded into the carousel page's observable cascade fallback and the grammar page's invalid controls, for the same reason.
