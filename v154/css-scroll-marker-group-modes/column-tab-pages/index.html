Tab pages from ::column fragments

The markup below is one flat list of changelog entries. The multicol engine fragments it into pages, each generated ::column emits its own ::scroll-marker, and tabs mode turns the marker row into a tablist — the spec even says where the tabpanel role goes when a marker's originating "element" is a ::column: to the column's originating element. Pagination, markers, and tab semantics, none of them in the markup.

Measuring pages…

why this composition matters

Every hand-built "paginated tabs" widget maintains three parallel structures: the pages, the tab buttons, and the script that keeps them in sync when content changes. Here there is only content. Drag the height slider and watch the browser re-fragment: entries reflow into a different number of columns, markers appear or disappear to match, and :target-current keeps tracking — nothing observed, nothing rebuilt, no ids. With tabs mode (Chrome 154), the same zero-markup structure also carries the WAI-ARIA tabs contract, including tabpanel assigned through each ::column's originating element and inactive pages pruned from the accessibility tree.

One honest limitation this page inherits from its build browser: CSS counters do not yet increment on ::column here, so the markers are square glyphs rather than numbered "Page N" chips. That is a marker-content limitation, not a modes limitation.

/* One flat list in, tabbed pages out */
.pages {
  columns: 1;
  column-fill: auto;
  height: 16rem;                     /* the fragmenter */
  overflow-x: auto;
  scroll-snap-type: x mandatory;
  scroll-marker-group: after;        /* fallback for Chrome 135–153 */
  scroll-marker-group: after tabs;   /* Chrome 154+: tablist semantics */
}
.pages::column { scroll-snap-align: start; }
.pages::column::scroll-marker { content: ""; /* one marker per generated page */ }
.pages::column::scroll-marker:target-current { background: black; }
