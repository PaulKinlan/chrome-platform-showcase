BYOB or not: the observable difference

A default readable stream refuses getReader({ mode: "byob" }) with a TypeError; a readable byte stream hands one over. transport.datagrams.readable exists from the moment the constructor returns — no connection required — so the whole feature is observable right here: construct two transports, ask both for a BYOB reader, compare.

Chrome targets this for Chrome 157 behind WebTransportDatagramsReadableType (--enable-blink-features=WebTransportDatagramsReadableType, or chrome://flags/#enable-experimental-web-platform-features). Three real-world outcomes exist, and this page names whichever one it actually observes: new Chrome (default refuses BYOB, "bytes" grants it), old Chrome (both grant it — the legacy byte stream this feature replaces), and engines that ignore the option (both refuse it).

Why anyone opts in

BYOB readers exist for allocation control: the application supplies the buffer each read fills, so a high-rate datagram consumer can recycle one 64 KiB buffer instead of having the stream allocate per datagram. The spec recommends 64 KiB buffers because the QUIC maximum datagram frame size is bounded by that — a smaller buffer risks erroring the stream on a large datagram. The price of that control is datagram semantics, which the next concept demonstrates.

const t = new WebTransport(url, { datagramsReadableType: "bytes" });
const reader = t.datagrams.readable.getReader({ mode: "byob" });
let buffer = new ArrayBuffer(65536);           // spec-recommended size
while (true) {
  const { value, done } = await reader.read(new Uint8Array(buffer));
  if (done) break;
  process(value);                              // one datagram, usually
  buffer = value.buffer;                       // recycle — zero allocation
}
