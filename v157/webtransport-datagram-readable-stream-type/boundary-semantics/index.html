What byte streams do to messages

The spec's own note is blunt: "Empty datagrams are lost, and min loses message delineation." Those are the two concrete casualties of treating messages as a byte sequence — and both are demonstrable with the real Streams API, no network needed.

No HTTP/3 endpoint is reachable from this showcase, so the two lanes below are a clearly-labelled local model: real ReadableStream objects — one default, one type: "bytes", the same two kinds datagrams.readable can be — fed the same three "datagrams" by the page instead of by a network. Every behaviour shown (the refusal, the loss, the merge) is the streams engine's own, not scripted output.

Three datagrams, two stream types

The input: a 5-byte position update, a 0-byte keep-alive, and a 7-byte chat fragment.

  • "HELLO" (5 bytes)
  • "" (0 bytes — a legal datagram!)
  • "GOODBYE" (7 bytes)

code path

// Lane A: default stream — one chunk per datagram, empties included.
controller.enqueue(new Uint8Array(0));     // fine: a chunk is a chunk
const { value } = await reader.read();     // value.byteLength === 0 ✓

// Lane B: byte stream — the engine itself refuses the empty message…
byteController.enqueue(new Uint8Array(0)); // TypeError at enqueue time!

// …and a min read spans boundaries:
const r = byteStream.getReader({ mode: "byob" });
await r.read(new Uint8Array(12), { min: 12 });
// resolves ONE view containing "HELLO" + "GOODBYE" — delineation gone
