Device listeners vs server listeners

Web Bluetooth already has events — they just all live one object up. gattserverdisconnected fires on the BluetoothDevice because, until Chrome 157, the device was the only EventTarget in the family. This page measures which pattern your browser supports and re-enacts both with plain EventTarget objects so the difference is drivable anywhere.

what actually changes for your code

Nothing is taken away: gattserverdisconnected stays on the device, and code written last year keeps working. What changes is where new connection-level events land. The connection's properties — like the negotiated write size — belong to the server object, so their change events fire on the server, and listening for them needs the server to be an EventTarget. The migration is therefore additive: keep the device listener for connection loss, add server listeners as connection-level events ship. The once: true toggle above matters for the same reason it does on any target — a reconnect creates fresh state, and a listener you only want for one connection's lifetime should say so.
