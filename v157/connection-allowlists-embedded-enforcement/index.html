Connection Allowlists - Embedded Enforcement

Connection Allowlists let a document restrict which external endpoints its code may contact. Embedded enforcement extends that control across the frame boundary: a parent sets a connectionallowlist attribute on an <iframe>, the browser carries the requirement to the framed server as the Sec-Required-Connection-Allowlist request header, and the framed document must opt in — with a Connection-Allowlist response header at least as strict, or an Allow-Connection-Allowlist-From delegation — or the frame does not load at all. The design deliberately mirrors CSP Embedded Enforcement.

concepts

  1. The requirement on the wire

    Frame a live echo endpoint with and without the connectionallowlist attribute and read back exactly what arrived: did the browser send Sec-Required-Connection-Allowlist, and with which allowlist value? Plus honest feature detection of the attribute surface itself — on a build without the origin trial, the echo proves the header was never sent.

  2. The opt-in handshake, three ways

    One enforcing iframe, three real server responses: a frame that answers Connection-Allowlist: (response-origin) (strict-enough opt-in), one that answers Allow-Connection-Allowlist-From: * (delegate to the embedder), and one with no headers at all — the frame an enforcing browser must refuse to load. Live load/blocked outcomes from real navigations, with each frame's same-origin fetch probe reported via postMessage.

  3. Local schemes inherit implicitly

    An about:srcdoc frame has no server to send headers, so the spec opts it in implicitly: it inherits the embedder's policy container, requirement and all. This page builds a srcdoc frame under a requirement and runs connection probes inside it — and contrasts the "at least as strict" rule for nested frames.

why it shipped

The base Connection Allowlists feature (Chrome 148 origin trial) answers "which endpoints may my document contact" — valuable for limiting exfiltration after an injection. But pages are rarely alone: ad slots, payment widgets, chat bubbles and analytics all arrive in iframes, and a parent that has carefully constrained its own connections had no way to demand the same discipline from what it embeds. Embedded enforcement is that missing half, borrowing the proven shape of CSP Embedded Enforcement: requirement attribute on the frame, Sec-Required-* request header on the navigation, explicit opt-in from the framed response, hard block otherwise. Because the accepted requirement joins the framed document's policy container, it propagates to the frame's own descendants and workers, and response-origin re-resolves against each inheritor's origin.

the API

<!-- the embedder requires an allowlist of the widget -->
<iframe connectionallowlist='(response-origin "https://api.widget.example")'
        src="https://widget.example/"></iframe>

<!-- the navigation carries the requirement -->
GET / HTTP/1.1
Host: widget.example
Sec-Required-Connection-Allowlist: (response-origin "https://api.widget.example")

<!-- the widget opts in (at least as strict), or is blocked -->
HTTP/1.1 200 OK
Connection-Allowlist: (response-origin)

<!-- …or delegates the decision to specific embedders -->
Allow-Connection-Allowlist-From: https://embedder.example

There is no JavaScript API: the contract is HTML markup plus HTTP headers, which is why every concept here talks to real server routes under this feature's folder.
