AccentColor & AccentColorText follows accent-color value

The AccentColor and AccentColorText system color keywords used to answer one global question: what is the operating system's accent color? Chrome 157 re-wires them to the element they are used on — AccentColor now resolves to the element's effective accent-color value, and AccentColorText to the contrasting foreground the browser would paint on top of it. Custom UI can finally use exactly the colors the browser paints native checkboxes, radios and progress bars with.

concepts

  1. Does your browser follow the value?

    The one-line behavioral probe this release is about: set accent-color: rgb(13 83 161) on a box, paint a child with color: AccentColor, and compare the two computed colors. Pick any accent with a real color input and watch the resolved values agree (Chrome 157+), stay pinned to the OS accent (older behavior), or report the keyword as unparsed — three honest verdicts, read straight off getComputedStyle().

  2. Custom widgets that match native ones

    The product reason the CSSWG made this change: one brand color drives native checkboxes, radios, ranges and progress bars via accent-color — and the same keywords paint your hand-built chips, badges and toggle so the two families never drift apart. Includes the inheritance story: accent-color inherits, so one declaration themes a whole subtree, and a nested override re-themes both native and custom controls below it.

  3. The AccentColorText contrast flip

    Where does the paired text color come from? Slide an accent from near-black to near-white and watch the browser flip AccentColorText between light and dark, with a live WCAG contrast ratio computed from the two resolved values — plus what accent-color: auto falls back to, and how this differs from the contrast-color() function.

why it shipped

Since Chrome 93, accent-color has tinted native form controls, and the browser has silently computed a readable foreground for the glyphs painted on top (the checkmark in a checked checkbox, for instance). But that color pair was locked inside the UA: a developer who wanted a custom-styled control, selected chip, or focus ring to match the native widgets next to it had to re-derive the pair by hand and hope it agreed with the browser's math. CSS Color 4 resolved (issue 5900) that AccentColor should take its value from the element's accent-color — unless Forced Colors Mode is active — and that AccentColorText should be the contrasting foreground the UA pairs with it. Chrome 157 ships that resolution, so the same two keywords now give custom UI the exact colors the widget machinery uses.

The practical consequences: the keywords are now per-element (two siblings with different accent-color values resolve them differently), they respond to inheritance the same way widget accents do, and accent-color: auto still routes through to the OS/system accent — which is what the keywords used to mean globally. In Forced Colors Mode the forced system palette wins, exactly as for other system colors.

the API

.card {
  accent-color: #0d53a1;          /* tints the native controls inside… */
}
.card .custom-chip[aria-pressed="true"] {
  background: AccentColor;        /* …and now paints custom UI with the SAME color */
  color: AccentColorText;         /* the UA-chosen readable foreground for it */
}

/* Per-element: each subtree's accent drives its own resolution */
.card.urgent { accent-color: #8b0000; }

/* auto (the initial value) still means the OS/system accent */
.card.system { accent-color: auto; }

AccentColor and AccentColorText are <system-color> keywords, usable anywhere a <color> is. What changed in 157 is their resolution: from a global OS lookup to the element's effective accent-color value and its UA-computed contrasting foreground.
