Add javascriptURLs option to SanitizerConfig and Sanitizer

The Sanitizer API has always stripped javascript: URLs from navigating attributes — but only as a hidden side effect of using a "safe" method like setHTML(). The HTML standard regularised that into an explicit, developer-selectable switch: the javascriptURLs boolean in SanitizerConfig, with a matching setJavascriptURLs() mutator on Sanitizer. Chrome 157 ships it, making the javascript:-URL policy a first-class, inspectable part of the configuration instead of folklore about which method you called.

concepts

  1. Canonicalization, read back with get()

    Construct sanitizers four ways — the "default" preset, an empty config, and explicit javascriptURLs: true / false — and read each canonicalized configuration back with get(). Shows the spec's two defaulting rules (permissive for bare dictionaries, strict for the safe preset), the setJavascriptURLs() changed/no-op return-value contract, and an honest probe that never mistakes an ignored unknown dictionary member for support.

  2. The javascript:-URL sanitization lab

    Paste or edit markup full of javascript: hrefs, formactions and iframe srcs, then run it through setHTML() or setHTMLUnsafe() with javascriptURLs on or off and diff what survives. The output is shown serialized — the lab never mounts a live javascript: link — with each stripped attribute called out.

  3. The navigating-attributes matrix

    The option only governs the spec's built-in navigating URL attributes list: a/area/base href, SVG a href / xlink:href, MathML href, button/input formaction, form action, iframe src, and SVG animations targeting href. This page runs every entry — plus a non-navigating counter-example — through both settings and renders the kept/stripped matrix your browser actually produced.

why it shipped

Before this change, whether a javascript: href survived sanitization depended on which method you called: setHTML() ("safe") removed them unconditionally, setHTMLUnsafe() kept them, and nothing in the configuration said so. That made configurations non-portable — the same SanitizerConfig meant different things in different call sites — and made it impossible to opt out in either direction: a safe-method caller could not keep javascript: URLs (say, for a CMS that post-processes them), and an unsafe-method caller could not strip them without also taking the full safe baseline. whatwg/html#12898 moved the policy into the config itself: javascriptURLs: true keeps them, false strips them from navigating attributes, and each canonicalized configuration now states its answer explicitly.

Defaults preserve the old behavior exactly: canonicalizing a bare dictionary for an unsafe method fills in true (keep), the built-in safe default configuration says false (strip), so code that never mentions the option behaves as before.

the API

// Explicit, portable policy in the config:
el.setHTML(untrusted, { sanitizer: { javascriptURLs: false } }); // strip (default for safe)
el.setHTMLUnsafe(untrusted, { sanitizer: { javascriptURLs: false } }); // strip, even unsafely

// Or mutate an existing Sanitizer:
const s = new Sanitizer();        // "default" preset → javascriptURLs: false
s.setJavascriptURLs(true);        // → true  (returns true: it changed)
s.setJavascriptURLs(true);        // → false (no-op: already true)

s.get().javascriptURLs;           // the canonicalized answer, inspectable

When javascriptURLs is not true, the sanitizer removes any attribute on the built-in navigating URL attributes list whose value is a javascript: URL. Non-navigating attributes are untouched by this option.
