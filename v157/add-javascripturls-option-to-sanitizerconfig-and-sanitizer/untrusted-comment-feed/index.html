why the unsafe path at all?

The safe path (setHTML) strips comments, data-* attributes and anything XSS-unsafe, always — including javascript: URLs, with no opt-out (removeUnsafe() forces the option off). But real pipelines sometimes need the permissive parse: a CMS that round-trips editorial comments, a widget that relies on data-* hooks, or markup that embeds inert <template> machinery. Before 157 that meant setHTMLUnsafe — and silently keeping javascript: hrefs. Now { sanitizer: { javascriptURLs: false } } gives the permissive parse without the script-URL hole. If your page also enforces Trusted Types (require-trusted-types-for 'script'), note setHTML() needs no policy while unsafe sinks may — see the guidance link below.
