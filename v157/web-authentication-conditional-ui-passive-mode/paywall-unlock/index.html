Paywall unlock

The explainer’s first motivating example: a reader lands on a paywalled article from a social link, has an account but no session, and is offered a sign-in suggestion the moment the page loads — no form, no modal, no click required to offer it. Readers without credentials see nothing different.

Developer trial — behind a flag, desktop only. To see the real passive prompt:

  1. Open chrome://flags/#web-authentication-ambient-signin, set it to Enabled, relaunch.
  2. Command-line equivalent: --enable-features=WebAuthenticationAmbientSignin (this also switches on the renderer’s WebAuthenticationAmbient runtime feature).
  3. --enable-blink-features=WebAuthenticationAmbient or --enable-experimental-web-platform-features enable only the renderer half: the request is accepted, but the browser downgrades it to ordinary conditional (autofill) mediation and no capability key is reported.
  4. You need a passkey or saved password for this site. If you don’t have one, the prompt correctly never appears and the promise never settles.

Chromium enables this on Windows, macOS, Linux and ChromeOS only (kOsDesktop flag, desktop-only origin trial list) — on Android the probes below honestly report “not available”.

Why browsers keep shipping new sign-in modes

You followed a link here from a social feed. You have an account with this publication, but no signed-in session on this device — so you get the free preview and a paywall.

Explicit sign-in links are easy to miss and annoying to complete; many readers bounce instead. Conditional UI passive mode lets the page offer a one-tap sign-in without a form and without a modal.

Sign in on the account page

This paragraph was revealed because navigator.credentials.get() resolved with a real credential from the passive prompt. In production the page would POST the assertion to the server, verify it, and receive this content; here the unlock is client-side and labelled as such.

—

behind the scenes

On load, with no click (passive mode does not need user activation, unlike Immediate UI mode), the page fires one passive request — but only if getClientCapabilities() reports it. No credentials means no UI and a promise that never settles, so readers without an account never see anything.

idle

the fallback stays

The “Sign in on the account page” link is never removed: passive mode is an enhancement for readers who already have a credential, not a replacement for your sign-in flow. When passive mode is unavailable, the page behaves exactly as it did before.

// on load — no user activation needed
const caps = await PublicKeyCredential.getClientCapabilities();
if (caps.conditionalPassiveGet) {
  const cred = await navigator.credentials.get({
    mediation: 'conditional', uiMode: 'passive',
    publicKey: await fetchOptions(), password: true, signal,
  });
  await unlockWith(await verifyOnServer(cred)); // resolves only if the reader picks an account
}
