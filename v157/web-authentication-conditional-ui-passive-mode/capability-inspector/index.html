Capability inspector

Three independent, real observations of whether passive mode is live — the capability map, the uiMode dictionary member, and a behavioural differential that only the passive code path can produce — combined into one verdict that can say no. Use it to check a flag, a Canary build, or a customer's browser before shipping uiMode: 'passive'.

Behind a flag — no shipping milestone yet. Enable chrome://flags/#web-authentication-ambient-signin and relaunch, or launch with --enable-features=WebAuthenticationAmbientSignin. Launching with only --enable-blink-features=WebAuthenticationAmbient turns on the renderer half without the browser half — this page detects exactly that split.

Probe B · does uiMode validate?

An unknown dictionary member is silently ignored, so "passing uiMode: 'passive' did not throw" proves nothing. Instead this sends a deliberately invalid value: a browser that knows the uiMode member must reject with TypeError. It shows the member exists — not that passive mode is on (Chromium shares the enum with 'immediate').

Not run yet.

Probe C · behavioural differential

The passive path refuses credential types it cannot show in its non-autofill surface. The same request — publicKey plus federated, mediation: 'conditional' — is sent twice, once with uiMode: 'passive' and once without. Different outcomes mean the passive branch really ran; identical outcomes mean the value was accepted and ignored. Each request is aborted after 0.7 s, so nothing is left pending.

Not run yet.

reading the verdict

  • Fully enabled: a passive capability key is true and the differential shows the passive branch.
  • Renderer only: the differential fires but no capability key is reported — typical of --enable-blink-features=WebAuthenticationAmbient without the browser feature.
  • Not enabled: no key and no behavioural difference. Ship your normal sign-in UI; adding uiMode: 'passive' to an existing conditional call is still harmless.
