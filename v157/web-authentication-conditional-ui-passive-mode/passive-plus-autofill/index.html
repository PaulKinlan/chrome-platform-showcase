Passive + autofill, one request

On a real sign-in page you can have it both ways. The explainer: “Credentials can be simultaneously made available in Passive Mode UI and autofill UI with a single JavaScript call.” This page arms exactly one request, lets you flip between the passive+autofill and autofill-only shapes, and shows the abort-and-re-arm dance an explicit passkey button needs.

Developer trial — behind a flag, desktop only. To see the real passive prompt:

  1. Open chrome://flags/#web-authentication-ambient-signin, set it to Enabled, relaunch.
  2. Command-line equivalent: --enable-features=WebAuthenticationAmbientSignin (this also switches on the renderer’s WebAuthenticationAmbient runtime feature).
  3. --enable-blink-features=WebAuthenticationAmbient or --enable-experimental-web-platform-features enable only the renderer half: the request is accepted, but the browser downgrades it to ordinary conditional (autofill) mediation and no capability key is reported.
  4. You need a passkey or saved password for this site. If you don’t have one, the prompt correctly never appears and the promise never settles.

Chromium enables this on Windows, macOS, Linux and ChromeOS only (kOsDesktop flag, desktop-only origin trial list) — on Android the probes below honestly report “not available”.

a sign-in page that wants both surfaces

One navigator.credentials.get() call, armed on load. With uiMode: 'passive' the browser shows its non-modal suggestion straight away; if you ignore it and later focus the username field, the same pending request surfaces in autofill. Picking a credential in either place resolves the one promise.

rules this page follows

  • One request, two surfaces. Don’t fire a second conditional request for the form: only one WebAuthn request can be pending per page, and the spec routes both prompts to the same |silentlyDiscoveredCredentials| list.
  • Abort before the modal. The “Sign in with a passkey” button aborts the pending conditional request, runs an ordinary modal get(), then re-arms the passive+autofill request.
  • Same fallback as before. Without passive support the request is exactly the existing conditional autofill request, so the form keeps working everywhere.
