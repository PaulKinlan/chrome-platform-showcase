Web Authentication Conditional UI Passive Mode

Conditional UI lets a page offer passkeys inside form autofill — which only works if the page has a sign-in form. Passive mode adds uiMode: 'passive' to a mediation: 'conditional' request: the browser shows a small, ignorable, non-modal sign-in suggestion on any page, but only when you actually have a passkey or saved password for the site. No credentials, no UI, and the promise simply never settles. No user activation needed — so a page can offer it on load.

Developer trial — behind a flag, desktop only. To see the real passive prompt:

  1. Open chrome://flags/#web-authentication-ambient-signin, set it to Enabled, relaunch.
  2. Command-line equivalent: --enable-features=WebAuthenticationAmbientSignin (this also switches on the renderer’s WebAuthenticationAmbient runtime feature).
  3. --enable-blink-features=WebAuthenticationAmbient or --enable-experimental-web-platform-features enable only the renderer half: the request is accepted, but the browser downgrades it to ordinary conditional (autofill) mediation and no capability key is reported.
  4. You need a passkey or saved password for this site. If you don’t have one, the prompt correctly never appears and the promise never settles.

Chromium enables this on Windows, macOS, Linux and ChromeOS only (kOsDesktop flag, desktop-only origin trial list) — on Android the probes below honestly report “not available”.

concepts

  1. Passive sign-in prompt

    The canonical call on a page with no sign-in form: probe conditionalPassiveGet, fire the request, watch it pend, abort it, or create a demo passkey and sign in through the bubble — with the returned credential’s clientData inspected live.

  2. Capability inspector

    Four independent probes — the capability record (spec key and Chrome’s earlier ambientGet), the uiMode member read, the enum vocabulary via pre-aborted signals, and a Chromium renderer-branch check — combined into a diagnosis: fully enabled, renderer-only, or not enabled.

  3. Paywall unlock

    The explainer’s motivating case: a paywalled article fires a passive request on load, without a click, and unlocks in place when a returning subscriber picks their account. Everyone else just sees the normal sign-in link.

  4. Passive + autofill, one request

    A sign-in form where one pending request feeds both the passive suggestion and the username autofill, with password credentials included and the abort-then-re-arm pattern around an explicit “Sign in with a passkey” modal button.

  5. Request shape matrix

    Nine real request shapes at the edges — unsupported credential combinations, password-only, the spec’s sibling 'active', 'immediate' under conditional, an unknown value, and the pre-146 prototype shape — plus migration notes for the ambientGet → conditionalPassiveGet rename.

why it exists

Users often don’t notice they’re signed out, or avoid the sign-in flow because they expect it to be painful. Sites that would be better signed-in (paywalled articles, personalised search results) can’t use Conditional UI without a form, and a modal WebAuthn prompt on page load is hostile to the many visitors with no passkey. Passive mode sits between: the browser only speaks up when sign-in is one tap away, and it never blocks the page.

the API

const caps = await PublicKeyCredential.getClientCapabilities();
if (caps.conditionalPassiveGet || caps.ambientGet /* earlier Chromium key */) {
  const cred = await navigator.credentials.get({
    mediation: 'conditional',
    uiMode: 'passive',          // CredentialRequestOptions member, sibling of mediation
    publicKey: { challenge, rpId: 'example.com', allowCredentials: [] },
    password: true,             // optional: saved passwords in the same UI
    signal: controller.signal,  // abort to withdraw the suggestion
  });
  // resolves only if the user picks a credential
}
