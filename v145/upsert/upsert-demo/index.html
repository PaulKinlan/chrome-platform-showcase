Upsert Demo

Hands-on with the TC39 "upsert" proposal shipping in Chrome 145 (V8): Map.prototype.getOrInsert() and Map.prototype.getOrInsertComputed() — one atomic get-or-insert call instead of the racy has()/get()/set() dance.

Chrome 145+ (V8 14.5) ships getOrInsert/getOrInsertComputed natively on Map and WeakMap. If this browser doesn't have them, the playground below installs a clearly labelled polyfill that models the spec semantics so you can still try the API shape — the support probes above the playground always report the real native state, checked before the polyfill is installed.

Enter a key/value and try getOrInsert. Call it twice with the same key: the first call inserts, the second returns the existing value untouched.

why "atomic" matters — interleaved writers

Two async tasks both want to initialise the same cache slot. With the old has()-then-set() pattern, a task that yields (awaits) between the check and the write loses its update. getOrInsert is a single synchronous operation, so there is no gap to interleave into.

edge case — callback re-entrancy

What if the getOrInsertComputed callback mutates the same key while it runs? The spec is explicit: the callback's return value is written after the callback finishes, overwriting anything the callback set for that key.

code

// Chrome 145+ (TC39 proposal-upsert, V8)
const cache = new Map();

// Insert if absent, otherwise return the existing value — one call:
const v1 = cache.getOrInsert('theme', 'dark');   // inserts → 'dark'
const v2 = cache.getOrInsert('theme', 'light');  // exists  → 'dark'

// Lazy variant: only compute the default when the key is missing.
const parsed = cache.getOrInsertComputed('config', (key) => expensiveParse(key));

// The old pattern this replaces (check-then-set — racy across awaits):
if (!cache.has('theme')) cache.set('theme', 'dark');
const v = cache.get('theme');

// Also on WeakMap:
weakCache.getOrInsert(element, { hits: 0 });
