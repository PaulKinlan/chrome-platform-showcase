Whole-input validator

Shared pattern libraries such as editor grammars, lint configs and route tables are often compiled with the m flag for every pattern. Under m, an allow-list like ^[a-z0-9_]{3,16}$ only checks that some line is valid. So "alice\n<script>" passes. \A…\z says "the whole input" no matter which flags the library adds. This page runs three real validators on the same values. It also shows a second trap: an <input pattern> that uses \A is silently ignored in a browser that cannot compile it.

Behind a V8 flag until it ships. ChromeStatus lists this feature in the Chrome 159 "Enabled by default" group (Finch V8Flag_js_regexp_buffer_boundaries). It is a V8 feature, with no Blink runtime flag, and --enable-experimental-web-platform-features does not turn it on. To run it today, launch Chrome with --js-flags=--js-regexp-buffer-boundaries (verified in Chrome 153). In builds where V8 marks it staged, chrome://flags/#enable-javascript-harmony turns it on as well. In Chrome 153 that flag does not.

2 · <input pattern> compiles with the v flag

The HTML spec compiles a pattern attribute as ^(?:pattern)$ with the v flag. So \A and \z are legal there once the engine supports them, even though they are redundant. In an engine without them the pattern is invalid. HTML then says the field has no pattern constraint at all, so any value is accepted. Attach the pattern and check a value that should fail.

If the engine cannot compile the pattern, Chrome logs a console message saying the pattern attribute is not a valid regular expression. On this page that message is the expected sign of the unsupported branch.

the code

const FLAGS = 'mu'; // the library compiles everything this way
const lineOnly  = new RegExp('^[a-z0-9_]{3,16}$', FLAGS);           // "alice\n<script>" passes
const wholeBuf  = new RegExp(String.raw`\A[a-z0-9_]{3,16}\z`, FLAGS); // only the whole value passes
const lenient   = new RegExp(String.raw`\A[a-z0-9_]{3,16}\Z`, FLAGS); // also allows ONE trailing terminator

// \Z suits a line read from a file ("alice\n"). It is WRONG for header values:
lenient.test('alice\r\n'); // true, so the CRLF reaches your header writer
