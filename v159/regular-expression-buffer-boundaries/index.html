Regular Expression Buffer Boundaries

Three new escapes for Unicode-mode regular expressions: \A matches the start of the input, \z the end, and \Z the end allowing one trailing line terminator — none of them affected by the m flag. They are defined as synonyms for (?-m:^), (?-m:$) and (?=(?:\r\n|\n|\r|\u2028|\u2029)?(?-m:$)), and they make patterns copied from PCRE, Ruby, .NET, Python and TextMate grammars work in JavaScript.

Not on by default before Chrome 159. It is a V8 flag, not a Blink runtime feature, so there is no chrome://flags entry: launch Chrome or Canary with --js-flags=--js-regexp-buffer-boundaries to try it today (Finch name V8Flag_js_regexp_buffer_boundaries). Every concept below probes the real syntax with new RegExp() and labels any fallback it uses.

concepts

  1. Syntax probe

    The exact grammar change, tested: \A, \z, \Z with u and v, plus the negative cases the spec pins down — not in a character class, not quantifiable, a literal letter without u. A probe that genuinely returns false on an unsupporting engine, and a compile-your-own box.

  2. Anchor playground

    Canonical usage: ^…$, \A…\z and \A…\Z run side by side on the same multi-line input, with the m flag toggle and trailing \n / \r\n presets. Matches are highlighted with the CSS Custom Highlight API and listed as text.

  3. Strict input validation

    Practical product use: a bulk-SKU import box where the legacy /^…$/m validator lets a junk line through. Strict \A…\Z (forgives one clipboard newline) and \A…\z (exact) validators are checked against a regex-free ground truth for six real-world pastes.

  4. Portable pattern converter

    Migration and edge cases: convert patterns from PCRE/Ruby/TextMate or Python (whose \Z is JS \z), emit both the native form and the modifier-based fallback, and verify the two agree on empty, \r\n, \u2028, double-newline and leading-newline inputs.

why it exists

With m, ^ and $ mean "line"; without it they mean "input". A single regex that needs both — "this header must be the very first line, then any lines" — previously needed lookbehind tricks or RegExp modifiers (?-m:^). The proposal gives the widely-documented two-character spellings from other engines, which matters because JavaScript now routinely consumes patterns written for other engines: TextMate grammars in editors, JSON/YAML configs, and code generated by LLMs.

use-case portfolio

  • Basic / canonical — anchor-playground.
  • Inspection tooling — syntax-probe (grammar matrix + compile-your-own).
  • Practical product use — strict-input-validation.
  • Edge / failure / migration — portable-pattern-converter (Python \Z, Annex B literal, class rejection, desugared fallback) and the negative rows of syntax-probe.
  • Advanced composition — portable-pattern-converter composes the escapes with RegExp modifiers (the fallback) and proves equivalence; anchor-playground composes match results with the CSS Custom Highlight API. A further composition with String.prototype.split/replaceAll was not built separately: buffer boundaries add no API surface beyond pattern syntax, so every consumer (test, exec, matchAll, replace) exercises the same compiled assertion.

the syntax

// Always build with the constructor (or ship only to supporting engines):
// a /\A/u literal is an early SyntaxError where unsupported.
const strict = new RegExp('\\Afoo\\z', 'mu');
strict.test('foo');        // true
strict.test('foo\nbar');   // false — m does not affect \A / \z

const mixed = new RegExp('\\Afoo|^bar$|baz\\z', 'mu');
mixed.test('\nbar');       // true  — ^ is still line-based
mixed.test('baz\n');       // false — \z is end of input

new RegExp('end\\Z', 'u').test('The end\r\n');   // true
new RegExp('\\A', '').test('A');                  // true — Annex B literal without u
