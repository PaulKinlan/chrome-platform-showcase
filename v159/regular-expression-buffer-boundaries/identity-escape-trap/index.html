Identity-escape trap

Without the u or v flag, \A is not an anchor. Web-compat Annex B makes it an identity escape for the letter A, and the same is true of \z and \Z. So /\Afoo\z/ quietly matches "Afooz", and the proposal cannot change that without breaking existing sites. This page runs each boundary case in this engine and compares the result with what the spec says an engine with the feature returns. The cases include the syntax errors that survive the change, and a script-killing early error.

Behind a V8 flag until it ships. ChromeStatus lists this feature in the Chrome 159 "Enabled by default" group (Finch V8Flag_js_regexp_buffer_boundaries). It is a V8 feature, with no Blink runtime flag, and --enable-experimental-web-platform-features does not turn it on. To run it today, launch Chrome with --js-flags=--js-regexp-buffer-boundaries (verified in Chrome 153). In builds where V8 marks it staged, chrome://flags/#enable-javascript-harmony turns it on as well. In Chrome 153 that flag does not.

why these cases

  • Non-Unicode patterns are frozen. The grammar adds \A, \z and \Z only under [+UnicodeMode]. Annex B's SourceCharacterIdentityEscape still applies to the others.
  • The README's /end\Z/ example has no u. Under the spec text that pattern means end followed by a literal Z, so "The end\n" does not match. The spec's Annex B note agrees.
  • Inside a character class, [\A] is still a SyntaxError in u-mode. ClassEscape does not gain the new escapes.
  • Assertions are not quantifiable in u-mode. \A* stays an error, but with a different message.
  • A regex literal is an early error. One /\A…/u literal in an engine without the feature fails the whole script at parse time, before any try/catch runs. Use new RegExp() behind a feature detection while support is partial.
