v159 · webtransport · connection stats

The exact surface, probed at both moments

The feature is one zero-argument method on WebTransport.prototype — not the older per-stream WebTransportSendStream.getStats(). The spec algorithm gives it two personalities around a doomed connection: called while the session is connecting, the promise waits for the state to change; once the session is failed, it rejects with InvalidStateError. This page probes the surface, then runs both moments against an endpoint where nothing is listening and shows each settled outcome verbatim.

Chrome targets WebTransport.getStats() for Chrome 159 behind the WebTransportStats runtime flag. On an earlier or unflagged build, launch with --enable-blink-features=WebTransportStats, or flip chrome://flags/#enable-experimental-web-platform-features and relaunch. The doomed session targets https://127.0.0.1:44443/never — nothing listens there, which is exactly what the failure branches need.

Two calls, one doomed session

Construct a real session to the dead endpoint, call getStats() immediately (moment A — still connecting), wait for ready to reject, then call again (moment B — now failed). The spec says A waits and then rejects when the state lands on failed; B rejects straight away. Both with InvalidStateError.

    code path

    const t = new WebTransport("https://127.0.0.1:44443/never");

const whileConnecting = t.getStats();   // spec: wait for [[State]] to change
try { await t.ready; } catch {}         // the connection genuinely fails

try { await whileConnecting; }
catch (e) { e.name; } // "InvalidStateError" — state changed to failed

try { await t.getStats(); }             // spec: failed -> reject immediately
catch (e) { e.name; } // "InvalidStateError"
