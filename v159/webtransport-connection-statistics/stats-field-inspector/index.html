Stats field inspector

Connect to a WebTransport server, call await transport.getStats(), and see every member the spec defines for WebTransportConnectionStats and WebTransportDatagramStats — marked returned, null, or not returned, straight from the dictionary you got. Chromium leaves out the byte and packet totals, and this page shows that gap as it is.

Behind a flag in Chrome 153–158. WebTransport.prototype.getStats is gated by Blink's WebTransportStats runtime feature (status: "experimental"; ChromeStatus targets Chrome 159 for desktop, Android and WebView). To try it now: open chrome://flags/#enable-experimental-web-platform-features, set it to Enabled and relaunch — or start Chrome with --enable-blink-features=WebTransportStats. There is no dedicated chrome://flags entry for the stats method itself. Reading statistics also needs a live HTTP/3 WebTransport session, which this site cannot host: use a public echo server or run your own (instructions on the feature page). Every number on this page comes from a real getStats() call — nothing is simulated.

what to look for

In Chromium you should see smoothedRtt, rttVariation and minRtt in milliseconds (left out until QUIC has a valid RTT sample — Chromium checks min_rtt > 0), estimatedSendRate in bits per second or null, and a datagrams object. The eight byte/packet totals and atSendCapacity are not in Chromium's IDL, so they come back as not returned. That is allowed: the spec says a user agent may hold back members, but it must choose once per session, not per call. The closed & failed connections page checks that across repeated calls.

the code

const wt = new WebTransport(url);
await wt.ready;
const stats = await wt.getStats();
for (const name of ["bytesSent", "smoothedRtt", "estimatedSendRate", "atSendCapacity"]) {
  console.log(name, Object.hasOwn(stats, name) ? stats[name] : "(not returned)");
}
console.log(stats.datagrams); // { droppedIncoming, expiredOutgoing, lostOutgoing, … }
