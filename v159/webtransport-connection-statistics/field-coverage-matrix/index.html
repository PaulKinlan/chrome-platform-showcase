Field coverage: the spec dictionary vs this browser

The spec dictionary promises fourteen connection members plus four datagram counters. Chromium deliberately ships a subset — the ChromeStatus entry says plainly that "Chromium does not currently expose connection byte or packet totals", and the Working Group has flagged bytesAcknowledged as a feature at risk. This matrix lists every member the spec defines and fills the "this browser" column from one real resolved getStats() object — never from assumptions.

Chrome targets WebTransport.getStats() for Chrome 159 behind the WebTransportStats runtime flag (--enable-blink-features=WebTransportStats, or chrome://flags/#enable-experimental-web-platform-features). Filling the matrix needs one resolved stats object, which needs an established session — a failed connection rejects by spec. Until a connection succeeds every row honestly reads "needs a resolved stats object".

reading the matrix

returned means the member was an own property of the resolved object with a concrete value. null is itself meaningful — estimatedSendRate is nullable in the IDL and comes back null when no estimate is available (pooled connections, or too little traffic). not returned means the member was absent from the object; for the byte/packet totals on Chromium that is the documented, deliberate position, not a bug in your network. On a pooled connection the spec itself strips everything not marked as a pooled stat, leaving only the RTT measurements.
