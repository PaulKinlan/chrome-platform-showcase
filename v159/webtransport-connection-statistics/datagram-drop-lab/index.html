Datagram drop lab

Datagrams are unreliable by design, and stats.datagrams tells you which kind of unreliability you hit. A datagram dropped because your page did not read fast enough is your bug. One that expired in the outgoing queue means you are sending more than the connection can carry. One the network lost is nobody's fault. Each experiment here changes one real queue setting on transport.datagrams, sends a real burst to an echo server, and reports the change in the matching counter between two getStats() calls.

Needs WebTransport.prototype.getStats (Chrome 159, or chrome://flags/#enable-experimental-web-platform-features / --enable-blink-features=WebTransportStats) and an HTTP/3 server that echoes datagrams, reachable over UDP (run one locally). Counters move only when the real event happens. A delta of 0 is reported as 0, and a counter this browser does not expose is reported as absent.

code path

const dg = transport.datagrams;
dg.incomingMaxBufferedDatagrams = 1;   // tiny receive queue
const before = (await transport.getStats()).datagrams;
for (let i = 0; i < 200; i++) writer.write(payload);   // echo server sends them back
await new Promise((r) => setTimeout(r, 800));        // ...and nobody reads
const after = (await transport.getStats()).datagrams;
after.droppedIncoming - before.droppedIncoming;      // overflowed the queue
