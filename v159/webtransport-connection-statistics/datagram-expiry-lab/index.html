Datagram expiry lab

Each counter in stats.datagrams is linked to a knob on transport.datagrams. expiredIncoming goes with incomingMaxAge, expiredOutgoing with outgoingMaxAge, and droppedIncoming with incomingMaxBufferedDatagrams. Inspect and set those attributes first: that part needs no server, because they are live even on a transport whose connection failed. Then, with a server, run each experiment and see whether its counter moved.

Behind a flag in Chrome 153–158. WebTransport.prototype.getStats is gated by Blink's WebTransportStats runtime feature (status: "experimental"; ChromeStatus targets Chrome 159 for desktop, Android and WebView). To try it now: open chrome://flags/#enable-experimental-web-platform-features, set it to Enabled and relaunch — or start Chrome with --enable-blink-features=WebTransportStats. There is no dedicated chrome://flags entry for the stats method itself. Reading statistics also needs a live HTTP/3 WebTransport session, which this site cannot host: use a public echo server or run your own (instructions on the feature page). Every number on this page comes from a real getStats() call — nothing is simulated.

what to look for

Over loopback, outgoing datagrams leave almost as soon as they are written, so expiredOutgoing may stay at 0 even with a 1 ms outgoingMaxAge. Try a distant server. droppedIncoming rises once the page stops reading and the echoes overflow the queue. In Chromium the incoming counters come from its DatagramQueue. If a member is missing from the result, the counter shows not returned rather than 0. Setter results differ between Chrome 153 and Chromium main: main's ValidateAndNormalizeMaxAge rejects negative values and NaN, which matches the editor's draft more closely.
