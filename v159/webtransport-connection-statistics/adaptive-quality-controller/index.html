Adaptive quality controller

This is the reason the stats exist. A live-streaming or cloud-gaming client picks its bitrate tier from estimatedSendRate. It treats smoothedRtt rising above minRtt as queueing delay, and growth in datagrams.lostOutgoing as loss. Both trigger a step down. The controller below runs that logic. Every input is labelled with where it came from: a live session, a recorded real trace, or numbers you typed in.

Behind a flag in Chrome 153–158. WebTransport.prototype.getStats is gated by Blink's WebTransportStats runtime feature (status: "experimental"; ChromeStatus targets Chrome 159 for desktop, Android and WebView). To try it now: open chrome://flags/#enable-experimental-web-platform-features, set it to Enabled and relaunch — or start Chrome with --enable-blink-features=WebTransportStats. There is no dedicated chrome://flags entry for the stats method itself. Reading statistics also needs a live HTTP/3 WebTransport session, which this site cannot host: use a public echo server or run your own (instructions on the feature page). Every number on this page comes from a real getStats() call — nothing is simulated.

    the decision rule

    function decide(s, prevLost) {
  if (s.estimatedSendRate === null) return { hold: "no estimate yet" };
  const budget = s.estimatedSendRate * headroom;           // bit/s
  const fit = ladder.findLast(t => t.bps <= budget) ?? ladder[0];
  const queueing = s.smoothedRtt - s.minRtt;                // ms
  const lost = s.datagrams.lostOutgoing - prevLost;
  if (lost > 0 || queueing > maxQueueMs) return stepDown(); // congestion signal
  return stepUpAtMostOneTierAfter(3, fit);                   // hysteresis
}

    The rule checks for null, because Chromium returns null when it has no estimate. It also checks that the RTT members exist, because Chromium leaves them out until QUIC has an RTT sample. Without those checks the controller would read undefined as zero and pick the wrong tier.
