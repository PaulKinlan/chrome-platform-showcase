WebTransport connection statistics

Is the session slow because the network is slow, or because your app is slow? Chrome 159 ships WebTransport.getStats(): one asynchronous call that snapshots the underlying connection's health — minRtt, smoothedRtt, rttVariation, an estimatedSendRate when one is available, and a datagram ledger of expired, lost, and dropped counts. Statistics remain readable after a clean close; a failed connection rejects instead. Chromium does not currently expose the spec's byte or packet totals.

concepts

  1. The exact surface, probed at both moments

    Probe 'getStats' in WebTransport.prototype and its property descriptor, then construct a real session to a dead endpoint and call getStats() twice — once while the session is still connecting (the spec says the promise waits), and once after it has failed (the spec says reject with InvalidStateError). Both settled outcomes shown verbatim, timestamps included.

  2. Live stats monitor: poll a real session once a second

    Connect to a WebTransport endpoint you can reach, then watch minRtt / smoothedRtt / rttVariation / estimatedSendRate / atSendCapacity tick in a live table with an RTT sparkline — the troubleshooting loop the feature exists for. Disconnect works mid-flight, and every connection failure is surfaced with the real error and a retry.

  3. Datagram ledger: make expiry happen, then count it

    Set datagrams.outgoingMaxAge low, queue a burst of datagrams, and read getStats().datagrams before and after: expiredOutgoing, lostOutgoing, droppedIncoming, expiredIncoming as deltas between real snapshots — the four counters that tell unreliable-delivery apps what actually happened to their packets.

  4. After the end: closed resolves, failed rejects

    The spec draws a sharp line through terminal states: after a clean close() the promise resolves with the most recent stats; on a failed connection it rejects with InvalidStateError. The failed branch runs for real against a dead endpoint; the clean-close branch runs against any endpoint you can reach.

  5. Field coverage: the spec dictionary vs this browser

    All fourteen WebTransportConnectionStats members and all four WebTransportDatagramStats members from the spec, matched against a real resolved stats object from your browser — which fields come back, which are null, and which Chromium currently withholds (the byte and packet totals, per the ChromeStatus entry).

why it shipped

A WebTransport application sees its own symptoms — late messages, slow transfers, dropped datagrams — but not their cause. Before getStats() there was no way to tell connection latency, congestion, or datagram loss apart from application-side delay: the QUIC stack knew, and the page did not. One asynchronous snapshot call exposes the connection's health so senders can adapt (shrink payloads when expiredOutgoing climbs, back off when atSendCapacity is true) and developers can troubleshoot with numbers instead of guesses.

The surface is deliberately narrower than the spec's full dictionary: Chromium currently reports the RTT trio, the estimated send rate, atSendCapacity, and the datagram counters, but not the connection byte/packet totals (bytesSent, packetsReceived, …). Pooled sessions are narrower still — only stats marked pooled in the spec (the RTT measurements) are reported, because sharing a connection's totals across origins would leak cross-site activity. The W3C Working Group has flagged bytesAcknowledged as a feature at risk for the same implementability reasons.

the API

const transport = new WebTransport("https://example.com:4433/wt");
await transport.ready;

const stats = await transport.getStats();
stats.minRtt;            // DOMHighResTimeStamp (ms)
stats.smoothedRtt;       // RFC 9002 §5.3 smoothed RTT
stats.rttVariation;      // mean RTT variation
stats.estimatedSendRate; // bits/s estimate, or null when unavailable
stats.atSendCapacity;    // true when the connection is send-limited
stats.datagrams;         // { expiredOutgoing, lostOutgoing,
                         //   droppedIncoming, expiredIncoming }

transport.close();
await transport.closed;
await transport.getStats(); // still resolves: most recent stats
// …but on a FAILED connection getStats() rejects with InvalidStateError.

getStats() takes no arguments and returns a promise. Called while the session is connecting, the promise waits for the state to change. The method lives on WebTransport itself — the per-stream WebTransportSendStream.getStats() is a different, older surface with its own dictionary.
