WebTransport connection statistics

A video call stutters. Was it the network, the congestion controller, or your own code not reading fast enough? transport.getStats() answers that for a WebTransport session. It resolves to a WebTransportConnectionStats snapshot: round-trip times (smoothedRtt, rttVariation, minRtt), the congestion controller's estimatedSendRate when it has one, and datagram counters that separate datagrams the network lost from ones that expired in a queue or that your page never read. The snapshot is still available after the session closes. Chromium's ChromeStatus entry says it does not expose byte or packet totals; the snapshot page lets you check that against your own browser.

Chrome 159 enables this by default. On earlier builds, enable chrome://flags/#enable-experimental-web-platform-features, or launch with --enable-blink-features=WebTransportStats. The runtime feature is WebTransportStats in runtime_enabled_features.json5, with Finch feature WebTransportStats. Every concept also needs an HTTP/3 WebTransport server reachable over UDP. This showcase cannot host one (its host serves HTTP over TCP only), so the pages default to a public echo server and accept any URL. Run your own in 30 lines. When no session opens, the pages show the real error and the missing prerequisite. They never show invented numbers.

concepts

  1. Stats snapshot and member inventory

    The basic call, as an inspection tool. Open a session, call getStats(), and compare the result against all 17 spec members, each marked exposed or absent, with its unit and whether it is a pooled stat. Call it again to check the spec rule that a member, once exposed, never disappears later in the same session. An allowPooling switch shows how pooled sessions are limited to pooled stats.

  2. getStats() across connecting, failed and closed

    The edge cases, run for real. While connecting, the promise waits and then rejects with InvalidStateError if the handshake fails. Once failed, it rejects immediately. Once closed, it still resolves with the last stats. The first two runs need no server, because a port with nothing listening produces a real failure.

  3. Connection health monitor

    The product use case: poll getStats() on a timer with an adjustable datagram load, plot smoothedRtt, and choose a video bitrate tier from estimatedSendRate, stepping down when latency is high. When the estimate is null the monitor holds the current tier. It reads atSendCapacity to tell whether the estimate is a ceiling or only a floor.

  4. Datagram drop lab

    Combines the stats with the datagram queue settings. Shrink the receive queue (incomingMaxBufferedDatagrams) and stop reading, and droppedIncoming goes up. Run the same burst with a reader as a control. Set outgoingMaxAge or incomingMaxAge to 1 ms and watch the expiry counters. Each experiment reports a real before/after delta, including zero.

why it shipped

Before getStats(), a WebTransport application could only infer network health from the timing of its own reads and writes. A slow write might mean congestion, a slow server, or a busy main thread, and the application could not tell which. Adaptive media, cloud gaming and real-time collaboration need to know which one, because each calls for a different fix: send less, read faster, or tolerate jitter. The stats come from the QUIC connection itself. RTT follows RFC 9002, the send-rate estimate comes from the congestion controller (BBR in Chromium), and loss follows RFC 9002 §6.1. Calling getStats() does not open a connection and does not change how data is sent.

Privacy shapes the dictionary. A browser may withhold members, but must decide once per session, so a member never disappears between calls. When a session shares a pooled connection with other sessions, only the stats marked "pooled connection stats" are revealed, because the others would leak information about the other sessions on that connection.

the API

const transport = new WebTransport("https://example.com:4433/live");
await transport.ready;

const s = await transport.getStats();
s.smoothedRtt;          // ms (RFC 9002 §5.3)
s.rttVariation;         // ms
s.minRtt;               // ms (RFC 9002 §5.2)
s.estimatedSendRate;    // bit/s, or null when there is no estimate
s.atSendCapacity;       // true → estimate is a ceiling; false → may be app-limited
s.datagrams.droppedIncoming;   // your page did not read fast enough
s.datagrams.expiredOutgoing;   // older than outgoingMaxAge before it could be sent
s.datagrams.lostOutgoing;      // declared lost by the network (RFC 9002 §6.1)

// Spec-defined but optional: bytesSent, bytesReceived, packetsLost, …
// A member the browser does not expose is ABSENT, not 0.

The promise rejects with InvalidStateError when the session has failed. While connecting it waits for the outcome. After close() it resolves with the most recent stats.

run your own echo endpoint

Any HTTP/3 WebTransport server works. This one uses Deno's unstable QUIC API (Deno 2.2 or later) and echoes datagrams and bidirectional streams. Chrome only accepts a self-signed certificate through serverCertificateHashes when it is ECDSA and valid for 14 days or less, so generate one, print its SHA-256, and paste that hex into the concept pages together with https://127.0.0.1:4433/echo. This server was used to check the success path of every concept here.

openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -keyout key.pem -out cert.pem -days 10 -nodes -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
openssl x509 -in cert.pem -outform der | openssl dgst -sha256   # paste this hex

// echo.ts — deno run --unstable-net --allow-net --allow-read echo.ts
const cert = Deno.readTextFileSync("cert.pem");
const key = Deno.readTextFileSync("key.pem");
const endpoint = new Deno.QuicEndpoint({ hostname: "127.0.0.1", port: 4433 });
for await (const incoming of endpoint.listen({ cert, key, alpnProtocols: ["h3"] })) {
  (async () => {
    const wt = await Deno.upgradeWebTransport(await incoming.accept());
    await wt.ready;
    wt.datagrams.readable.pipeTo(wt.datagrams.writable).catch(() => {});
    for await (const bidi of wt.incomingBidirectionalStreams) {
      bidi.readable.pipeTo(bidi.writable).catch(() => {});
    }
  })().catch(console.error);
}
