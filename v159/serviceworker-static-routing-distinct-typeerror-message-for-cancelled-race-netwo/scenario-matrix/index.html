Scenario matrix

The new message is deliberately narrow. Chromium's implementation only substitutes it when all of these hold: the error is net::ERR_ABORTED, the request carries a race-network-request token (it is fetch(event.request) on a raced request), and the race loader was actually used. Everything else must keep saying "Failed to fetch". This matrix runs six real scenarios and tabulates the exact message each produced, so you can see the boundary.

reading the matrix

  • Fallback timer wins — the canonical case: cancelled before headers, so 159+ gives the distinct message.
  • Page aborts (no respondWith) — the client's AbortController cancels the request the race leg is serving; also ERR_ABORTED before headers.
  • Network wins / fast route — headers arrived, nothing cancelled: fetch() resolves.
  • Redirect loop — a genuine network error (ERR_TOO_MANY_REDIRECTS, not ERR_ABORTED; the worker answers the page with a JSON error page (served 200, marked x-served-by: sw-error-page) so the failure stays inside the worker): must stay "Failed to fetch" on every version, otherwise the change would hide real outages.
  • Page aborts (respondWith passthrough) — recorded as observed; Chromium may tear down the fetch event before the worker's promise settles, in which case no report arrives within the window.
