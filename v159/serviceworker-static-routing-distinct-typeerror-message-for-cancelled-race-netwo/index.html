ServiceWorker Static Routing: Distinct TypeError message for cancelled race-network-and-fetch-handler fetch() requests

When a service worker's static routing rule uses race-network-and-fetch-handler and its fetch handler calls fetch(event.request), Chromium deduplicates that call with the racing network request. If the race leg is cancelled before response headers arrive (net::ERR_ABORTED) — because an offline-fallback timer answered respondWith() first, or the client aborted — the handler's fetch() now rejects with TypeError("The service worker race-network-and-fetch-handler request was cancelled before 'fetch()' settled.") instead of the generic TypeError("Failed to fetch"). Apps can finally tell an expected race cancellation from a real network outage, as they already could with Navigation Preload.

How to test it. Proposed for Chrome 159 behind the base::Feature ServiceWorkerRaceNetworkRequestAbortedErrorMessage (declared in third_party/blink/common/features.cc, disabled by default until it ships). On a build that contains it, launch with --enable-features=ServiceWorkerRaceNetworkRequestAbortedErrorMessage. There is no chrome://flags entry and no Blink runtime flag. Every concept runs a real worker and prints the message this browser actually produced.

concepts

  1. Cancellation lab

    The canonical case with sliders: the server holds headers for N ms, the worker's offline-fallback timer fires after M ms. When the timer wins, the race leg is cancelled and you see the verbatim TypeError message, its classification, and the Resource Timing router fields (workerMatchedSourceType / workerFinalSourceType) proving the rule matched.

  2. Scenario matrix

    Inspection tool for the boundary: six real scenarios — timer wins, client abort, network wins, fast control, a redirect-loop genuine failure that must keep saying "Failed to fetch", and a passthrough abort recorded as observed — with the exact message each produced.

  3. Telemetry triage

    The motivating product use and the migration path: a burst of real requests feeds a naive and a triaging error pipeline. On builds with the change the triage suppresses expected cancellations and alerts only on the genuine failure; on older builds it shows the false-positive spike. Includes a classifier that also handles the Navigation Preload message.

use-case portfolio

  • Basic / canonical — cancellation-lab.
  • Inspection tooling — scenario-matrix (plus the Resource Timing router readout in the lab).
  • Practical product use — telemetry-triage.
  • Edge / failure / migration — scenario-matrix's genuine-failure and passthrough-abort rows; telemetry-triage's preload-to-static-routing classifier.
  • Advanced composition — the lab composes static routing with an offline-fallback race and Resource Timing router fields. A navigation-request variant was not built as its own page: in Chrome 153 a navigation whose fallback won did not cancel the race leg (it resolved from the network at ~2 s), so it would not exercise this message; the entry names navigation aborts only as one possible trigger, and the client-abort row covers the same ERR_ABORTED path for subresources.

what did not change

No IDL, no spec text, no new property — only the message string of an existing TypeError. It still is a TypeError, so instanceof TypeError checks keep working. Genuine network errors (DNS, connection reset, redirect loops) keep "Failed to fetch". Requests not routed through a race rule are unaffected.
