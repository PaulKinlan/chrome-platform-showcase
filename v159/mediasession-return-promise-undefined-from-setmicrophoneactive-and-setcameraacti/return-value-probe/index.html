What does the call actually hand back?

One behaviour change, three possible worlds: no method at all, the legacy Chromium behaviour (undefined), or the spec behaviour (Promise<undefined>). This page calls setMicrophoneActive() and setCameraActive() for real and reports exactly which world this build lives in — then shows the one-line pattern that is correct in all three.

The promise return ships in Chrome 159. On an earlier build the very same call usually returns undefined — that is the legacy behaviour this feature replaces, and the probe below reports it honestly rather than failing. No flag is documented for this change; on pre-159 builds chrome://flags/#enable-experimental-web-platform-features is the only lever worth trying.

Call both setters and inspect the return

Each call sets the state to its current value (a no-op state-wise) so the probe is side-effect-free, then restores. The interesting part is the returned value: its typeof, whether it is a Promise, and — if it is — what it settles with.

The both-worlds pattern

Wrapping the call in Promise.resolve() makes undefined and Promise<undefined> look identical to your code, while still surfacing the new rejection path on 159+:

try {
  await Promise.resolve(navigator.mediaSession.setMicrophoneActive(true));
  // accepted (or legacy build where acceptance was never reported)
} catch (err) {
  // Chrome 159+: InvalidStateError when the document is not fully active
  console.warn("capture state not applied:", err.name);
}
