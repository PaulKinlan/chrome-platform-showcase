v159 · media session · practical product use case

Video-call controls in sync with the browser

A call app owns two copies of its mute state: the button in its own UI and the browser's media-session controls (the Picture-in-Picture window's mic/camera/hang-up buttons, OS media hubs). setMicrophoneActive()/setCameraActive() push the app's state to the browser; the togglemicrophone, togglecamera and hangup action handlers pull the browser's requests back. With the promise return, the app can await the browser's acknowledgement before committing — and revert if a user agent refuses.

No permission is requested on load. Joining the "call" only calls the media-session methods — no capture starts. The optional Use my real camera and microphone button asks for capture only when you press it. There is no flag for the Promise return: Chrome 158 and earlier return undefined, and this page handles both shapes with await.

3 · Act as the browser's media-session UI

The browser invokes your registered handlers when a user presses its own mic/camera/hang-up buttons — which a page cannot trigger. These buttons call the exact handler function this page registered with setActionHandler(), labelled as a stand-in for that browser button press, so you can watch the round trip: handler → app state → setXActive() back to the browser.

the pattern

async function setMic(on) {
  micButton.setAttribute('aria-busy', 'true');
  try {
    await navigator.mediaSession.setMicrophoneActive(on); // Promise (159+) or undefined (≤158)
    state.mic = on;                                         // commit only after the UA accepted
    stream?.getAudioTracks().forEach((t) => { t.enabled = on; });
  } catch (e) {
    // A UA may reject (NotAllowedError / InvalidStateError): keep the old state
    announce(`Browser refused: ${e.name}`);
  } finally {
    micButton.removeAttribute('aria-busy');
    micButton.setAttribute('aria-pressed', String(state.mic));
  }
}
navigator.mediaSession.setActionHandler('togglemicrophone', () => setMic(!state.mic));
