Capture pause-policy lab

Why a promise at all? The spec lets a user agent implement a capture pause policy: when the page calls setMicrophoneActive(false), the browser pauses every microphone input and, after updating its UI, sets the matching MediaStreamTracks' muted state — then resolves. Unmuting may wait for a prompt, or be refused. This lab composes the two APIs for real and timestamps the promise's settle time against each track's mute/unmute events, so you can see what your browser actually does.

Capture is opt-in. Nothing is requested on load; Start capture calls getUserMedia() only when you press it. The setter buttons also work without capture. Chromium's implementation (media_session.cc) updates the browser's mic/camera state and resolves immediately — it applies no pause policy, so in Chrome expect muted to stay false. That is a real, reported observation, not a failure of this page. There is no flag for this change.

reading the timeline

With a pause policy (spec): mute events are queued after the browser updates its UI, in the same parallel steps that resolve the promise — so code that awaits the setter can read track.muted moments later instead of polling. Without one (Chromium today): the promise resolves in a microtask and the tracks keep flowing; an app that wants silence must still set track.enabled = false itself.

await navigator.mediaSession.setMicrophoneActive(false);
// spec pause policy: audio tracks soon fire 'mute' and report muted === true
// Chromium: muted stays false — so also do:
stream.getAudioTracks().forEach((t) => { t.enabled = false; });
