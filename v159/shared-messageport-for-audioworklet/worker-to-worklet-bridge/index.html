Worker → worklet bridge

Compose the shared port with MessageChannel transfer: the page hands one end of a fresh channel to a Dedicated Worker and the other end to the AudioWorkletGlobalScope through audioWorklet.port. From then on a 50 Hz worker “sequencer” talks to the audio thread without touching the main thread — so blocking the main thread for a full second does not stall it. Switch to relay mode to watch the same block freeze every tick.

Flag-gated in Chrome. The members are [RuntimeEnabled=AudioWorkletSharedPort] in Blink (status experimental; ChromeStatus: proposed for Chrome 159, already shipped in Firefox 138). To try the real path in a Chrome build that contains the implementation: enable chrome://flags/#enable-experimental-web-platform-features and relaunch, or launch with --enable-blink-features=AudioWorkletSharedPort (or --enable-features=AudioWorkletSharedPort, or --enable-experimental-web-platform-features). Chrome for Testing 153 does not contain the attribute even with those switches (verified) — use a current Canary. Without it, this page says so and runs the labelled old pattern instead.

why this matters

Audio apps often compute in a worker — sequencing, ML inference, decoding — and the main thread is the thing most likely to jank (layout, GC, framework work). Before the shared port, the only way to hand the worklet scope a direct channel was through a node's port. Now the context itself carries the control channel, so the scope can be wired to any number of workers at startup, before the first node exists. Where the shared port is missing, this page wires the same channel through a labelled bootstrap node — the old pattern.

const { port1, port2 } = new MessageChannel();
worker.postMessage({ type: 'config', mode: 'direct' }, [port1]);
ctx.audioWorklet.port.postMessage({ type: 'connect-worker' }, [port2]);
// scope.js
port.onmessage = (e) => { e.ports[0].onmessage = onTick; };
