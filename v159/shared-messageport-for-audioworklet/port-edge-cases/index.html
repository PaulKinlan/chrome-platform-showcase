Port edge cases

Ten real experiments on the shared port's contract: identity, per-context channels, read-only-ness, messages posted before addModule(), the start() rule for addEventListener, transfer lists, DataCloneError, close() — plus the migration row: feature-detect, and fall back to a bootstrap node only when the port is missing.

Flag-gated in Chrome. The members are [RuntimeEnabled=AudioWorkletSharedPort] in Blink (status experimental; ChromeStatus: proposed for Chrome 159, already shipped in Firefox 138). To try the real path in a Chrome build that contains the implementation: enable chrome://flags/#enable-experimental-web-platform-features and relaunch, or launch with --enable-blink-features=AudioWorkletSharedPort (or --enable-features=AudioWorkletSharedPort, or --enable-experimental-web-platform-features). Chrome for Testing 153 does not contain the attribute even with those switches (verified) — use a current Canary. Without it, this page says so and runs the labelled old pattern instead.

what the spec says (and what these rows check)

  • The MessageChannel is created in the AudioContext / OfflineAudioContext constructor: port1 becomes audioWorklet.port, port2 is transferred to the scope. So the port exists, and can be posted to, before any module loads — messages queue until the scope listens.
  • It is a plain HTML MessagePort: onmessage starts it implicitly, addEventListener('message') needs start(); transfer lists, cloning errors and close() behave exactly as they do for any port.
  • The spec's note asks authors who listen on either side to close() one end when done so resources can be collected.
