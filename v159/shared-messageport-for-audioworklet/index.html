Shared MessagePort for AudioWorklet

A direct line between the main thread and the audio rendering thread: audioContext.audioWorklet.port on one end, the port global inside AudioWorkletGlobalScope on the other. Until now, talking to the worklet global scope meant registering a do-nothing bootstrap AudioWorkletProcessor and smuggling messages through a node's port — Chrome 159 removes the detour.

concepts

  1. Port probe — the exact new surface: is audioWorklet.port a real MessagePort? Then a live round-trip: ping the global scope and get its sampleRate / currentFrame back, timed.
  2. Goodbye, bootstrap processor — the migration, run live: the old pattern (register a processor, build a node, message via node.port) and the new one (audioWorklet.port, no processor at all), side by side with what each had to construct.
  3. Global config fan-out — why you'd want it: one port message updates a module-global config that every processor instance reads. Three gain processors, one message, an offline render before and after — the output RMS proves the fan-out really happened on the rendering thread.

why it shipped

Requested in web-audio-api#2456 and specified in PR #2507: applications kept creating placeholder processors purely as message pipes — boilerplate, an extra node in the graph, and a per-node port when what they wanted was scope-level communication (loading shared WASM, broadcasting config, telemetry). The shared port pairs AudioWorklet.port with AudioWorkletGlobalScope.port so that channel simply exists.
