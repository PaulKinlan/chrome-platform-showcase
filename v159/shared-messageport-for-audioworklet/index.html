Shared MessagePort for AudioWorklet

Every AudioContext now carries a ready-made MessageChannel into its audio rendering thread: audioContext.audioWorklet.port on the main thread, and a global port inside the AudioWorkletGlobalScope. Modules can talk to the page — and share state across every processor they register — without creating a do-nothing “bootstrap” AudioWorkletNode just to get a port.

Flag-gated in Chrome. Blink runtime feature AudioWorkletSharedPort (status experimental). Enable chrome://flags/#enable-experimental-web-platform-features, or launch with --enable-blink-features=AudioWorkletSharedPort / --enable-features=AudioWorkletSharedPort, in a build that contains the implementation (current Canary). Chrome for Testing 153 lacks the attribute even with those switches (verified). Firefox 138+ ships it. Every concept detects the exact attribute and, when it is missing, runs the old pattern clearly labelled as such.

concepts

  1. Global-scope ping/pong

    Basic / canonical. Read audioWorklet.port before any module loads, let scope.js announce itself over the global port during evaluation, then ping/pong — with a live counter proving zero AudioWorkletNodes exist. A labelled button runs the old bootstrap-node pattern for contrast.

  2. Round-trip inspector

    Inspection tool. Bursts of 10–200 echoes, with selectable payload size, down the shared port and down a per-node AudioWorkletNode.port: full message log plus min / median / p95 / max round-trip table measured in this browser.

  3. Shared wavetable preload

    Practical product case. Transfer a wavetable once into the global scope (the main-thread buffer detaches) and spin up 1–8 voices that all read the same module-scope Float32Array. A ledger compares messages, bytes cloned vs transferred, and node count against the bootstrap-node and copy-per-voice patterns. Silent by default.

  4. Port edge cases

    Edge, failure and migration. Eleven real rows: identity, one channel per context (incl. OfflineAudioContext), read-only, messages queued before addModule(), use at module-evaluation time, the start() rule, ArrayBuffer and MessagePort transfer, DataCloneError, close(), and a feature-detect-then-fallback migration row.

  5. Worker → worklet bridge

    Novel composition. Hand a fresh MessageChannel end to a Worker and the other end to the scope through the shared port; a 50 Hz worker sequencer then reaches the audio thread directly. Block the main thread for one second and compare the largest tick gap against a main-thread relay.

why it shipped

Since AudioWorklet launched, the only MessagePort into the rendering thread belonged to an individual AudioWorkletNode/AudioWorkletProcessor pair. Libraries that needed scope-wide setup — loading WASM, wavetables or sample banks once, configuring a shared allocator, wiring a worker — had to instantiate a dummy processor purely as a messenger, keep it alive in the graph, and tear it down later (web-audio-api#2456). The Working Group added the shared port to the spec in PR #2507; Firefox shipped it in 138 and Chromium is catching up (ChromeStatus: “Chromium catches up”, low interop risk).

the exact API surface

[Exposed=Window, SecureContext]
interface AudioWorklet : Worklet {
  readonly attribute MessagePort port;
};

[Global=(Worklet, AudioWorklet), Exposed=AudioWorklet]
interface AudioWorkletGlobalScope : WorkletGlobalScope {
  // …registerProcessor, currentFrame, currentTime, sampleRate, renderQuantumSize
  readonly attribute MessagePort port;
};

// BaseAudioContext constructor (AudioContext and OfflineAudioContext):
//   messageChannel = new MessageChannel()
//   audioWorklet.port            = messageChannel.port1
//   AudioWorkletGlobalScope.port = messageChannel.port2 (transferred via a control message)
