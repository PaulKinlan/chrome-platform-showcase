Shared wavetable preload

A synth loads its wavetable once into the AudioWorkletGlobalScope — transferred, zero-copy, over audioWorklet.port — and every voice processor created afterwards reads the same Float32Array from module scope. Compare it, with real counts, against the two patterns apps use today: a bootstrap node that exists only to receive the table, and cloning the table into every voice's processorOptions.

Flag-gated in Chrome. The members are [RuntimeEnabled=AudioWorkletSharedPort] in Blink (status experimental; ChromeStatus: proposed for Chrome 159, already shipped in Firefox 138). To try the real path in a Chrome build that contains the implementation: enable chrome://flags/#enable-experimental-web-platform-features and relaunch, or launch with --enable-blink-features=AudioWorkletSharedPort (or --enable-features=AudioWorkletSharedPort, or --enable-experimental-web-platform-features). Chrome for Testing 153 does not contain the attribute even with those switches (verified) — use a current Canary. Without it, this page says so and runs the labelled old pattern instead.

    why this is the product case

    Synths, samplers and convolution engines carry large shared assets — wavetables, sample banks, impulse responses, WASM heaps. Before the shared port, getting one into the rendering thread meant either a do-nothing bootstrap node (an extra graph object to create, keep alive and tear down) or cloning the asset into each node. With AudioWorkletGlobalScope.port the asset goes to the scope once, ownership is transferred (the main-thread ArrayBuffer detaches to 0 bytes), and each voice looks it up by id.
