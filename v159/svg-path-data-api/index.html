SVG Path Data API

Chrome removed SVGPathSegList in Chrome 48 — and for ten years the only way to touch an individual path segment was to parse the d string yourself or ship a polyfill. Chrome 159 closes that gap with the SVG Working Group's replacement: getPathData() reads a path as an array of plain {type, values} objects, setPathData() writes one back, and getPathSegmentAtLength() answers "which segment is the pen in at this distance?". getPathData({normalize: true}) flattens everything to absolute M/L/C/Z — the four commands every morphing and interpolation library actually wants.

concepts

  1. Segment inspector: the d attribute, structured

    Type any d string and read it back through the real getPathData() — every segment as a {type, values} row next to the live rendering. Each of the three new methods is probed separately on SVGPathElement.prototype, because a build can ship some of the surface without the rest — and this page tells you exactly which you have.

  2. Normalize lens: twenty commands in, four out

    The same path read twice — raw, preserving relative/shorthand/arc commands, and with {normalize: true}, which converts everything to absolute M, L, C, Z. Both readings render side by side so you can see the geometry survive while the command vocabulary collapses: H/V become L, quadratics become exact cubics, arcs become approximated cubics.

  3. Path editor: every number gets an input

    Parse a path with getPathData(), get one labelled numeric input per segment value, and watch setPathData() re-serialize the d attribute and re-render on every edit — the structured read-modify-write loop that previously needed a parser library, now a native roundtrip.

  4. Segment at length: which command is the pen in?

    Drag a distance slider from 0 to getTotalLength() and the page asks getPathSegmentAtLength(distance) which segment owns that point, highlighting it in the table while the long-standing getPointAtLength() positions the marker dot. Also exercises the spec's clamping contract: negative distances clamp to the first segment, overshoot clamps to the last, NaN returns null.

  5. Morph toolkit: interpolation on normalized cubics

    The flagship use case the Chromium bug collected 45 upvotes for: normalize two different paths to absolute cubics with getPathData({normalize: true}), match their segment counts, then interpolate every value and write each frame back with setPathData() — a real path morph with no library and no string parsing in the hot loop.

why it shipped

Chromium removed the old SVGPathSegList API in January 2016 because it was overly complex — twenty-plus factory methods and live-mutation semantics — and poorly specified. The SVG Working Group specified a cleaner replacement, Firefox shipped it in Firefox 137 (April 2025), but Chrome never implemented it, leaving crbug 40441025 open for ten years with 45 upvotes, 31 comments, and five reopened Sheriffbot closures. Every SVG editor, data-visualization library, and path-animation tool on Chrome has been parsing d strings by hand or shipping the ~4 KB path-data-polyfill.

The new API uses plain {type, values} dictionaries rather than class instances — a deliberate decision confirmed by the SVG WG so that code written against the polyfill works unchanged against the native methods. Values are unrestricted float (NaN/Infinity accepted without throwing, matching SVG's lenient error model), and setPathData() validates in two levels: a segment missing type or values throws a TypeError structurally, while an unrecognized command letter or wrong value count is silently skipped — SVG's "render what you can" model, matching Firefox and the polyfill.

the API

const segments = path.getPathData();
// → [{type: "M", values: [10, 80]}, {type: "C", values: [40, 10, 65, 10, 95, 80]}, …]

const flat = path.getPathData({ normalize: true });
// → absolute M / L / C / Z only (H/V→L, Q/T→C exactly, S→C, A→C approximated)

segments[1].values[0] = 50;        // plain objects — edit in place
path.setPathData(segments);        // re-serializes the d attribute

path.getPathSegmentAtLength(50);   // → the {type, values} segment at distance 50
path.getPathSegmentAtLength(NaN);  // → null; negative clamps to first, overshoot to last

All twenty path commands (M m L l H h V v C c S s Q q T t A a Z z) round-trip through getPathData()/setPathData(). An empty or missing d reads as [], and setPathData([]) clears the attribute to the empty string (it stays present). getPathData() returns the base value, not the animated value — consistent with getAttribute('d').
