SVG Path Data API

Structured access to SVG path segments, ten years after Chrome 48 removed SVGPathSegList: path.getPathData() reads the d attribute as an array of plain {type, values} objects, path.setPathData(array) writes one back, and path.getPathSegmentAtLength(distance) tells you which segment sits at a distance along the path. getPathData({normalize: true}) reduces any path to absolute M, L, C and Z. All three operate on the attribute's base value — not on CSS d: or SMIL-animated geometry.

Gated by the Blink runtime feature SVGPathDataAPI (status experimental): enable chrome://flags/#enable-experimental-web-platform-features, or launch Chrome with --enable-blink-features=SVGPathDataAPI. Firefox 137+ ships it. Every concept probes each method separately and labels any JavaScript fallback as a fallback.

concepts

  1. Segment inspector

    Basic usage and inspection: pick or type any d string — shorthand S/T, relative h/v, arcs, implicit repeated commands, a mid-string error — and see the browser's own getPathData() table next to getPathData({normalize: true}). Focus a row to highlight that segment on the drawing.

  2. Point editor

    The practical editing tool: drag or arrow-key every end and control point; each move is a getPathData() → change one number → setPathData() round trip, with the browser-serialized d shown live. Numeric fields edit every value, and one button normalizes the whole path in place.

  3. Transform and build paths

    Product use cases without a parsing library: scale, rotate and flip any path (arcs and relative commands included) by transforming normalized point pairs — with an optional red overlay showing why the same math on raw segments goes wrong — and build a chart sparkline straight from numbers as segment objects.

  4. Segment at length

    Hit-testing and measurement: scrub or hover along a path and ask getPathSegmentAtLength() which segment is there, next to a labelled script answer for comparison; then call it for real with −10, 99999, NaN and an empty path. Honest "not available" where a build has the other two methods but not this one.

  5. Edge cases and migration lab

    Edge, failure and migration: ten setPathData() inputs (wrong arity, unknown type, NaN, missing moveto, [], [{}]) showing the throw-vs-valid-prefix rules; base value vs CSS d: vs SMIL; and the classic pathSegList operations ported to array operations, with a probe of what the removed API left behind.

why it shipped

Path animation, hit-testing, editors (Boxy SVG, SVG-Edit) and data-visualization morphing all need segment-level access, and since SVGPathSegList was removed — for its live-mutation model, twenty-odd factory methods and underspecified edge cases — Chrome developers have parsed and re-serialized d strings by hand or loaded a polyfill. The SVG Working Group specified a smaller replacement built on plain objects, Firefox shipped it in 137, and the Chromium implementation (crbug 40441025, 45 votes over ten years) aims for interop with Firefox and drop-in compatibility with path-data-polyfill. Plain WebIDL dictionaries mean setPathData() takes ordinary object literals; unrestricted float values keep SVG's render-what-you-can error model.

the API surface

// third_party/blink/renderer/core/svg/svg_path_data.idl (Chromium main)
dictionary SVGPathDataSettings { boolean normalize = false; };
dictionary SVGPathSegment {
  required DOMString type;
  required sequence<unrestricted float> values;
};
interface mixin SVGPathData {
  [RuntimeEnabled=SVGPathDataAPI] sequence<SVGPathSegment> getPathData(optional SVGPathDataSettings settings = {});
  [RuntimeEnabled=SVGPathDataAPI] undefined setPathData(sequence<SVGPathSegment> pathData);
  [RuntimeEnabled=SVGPathDataAPI] SVGPathSegment? getPathSegmentAtLength(float distance);
};
SVGPathElement includes SVGPathData;
