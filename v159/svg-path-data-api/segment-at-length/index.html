Segment at length: which command is the pen in?

getPointAtLength() has answered "where is the pen at distance d?" for years. The new getPathSegmentAtLength() answers the structural question — which segment owns that point — returning its {type, values} object, or null for an empty path (NaN and infinite distances throw a TypeError — the argument is a restricted float). Drag the slider: the dot moves via the long-standing API, the highlighted row comes from the new one.

Chrome targets the SVG Path Data API for Chrome 159 behind the SVGPathDataAPI runtime flag (--enable-blink-features=SVGPathDataAPI, or chrome://flags/#enable-experimental-web-platform-features). Note: a mid-implementation build can ship getPathData/setPathData while getPathSegmentAtLength is still absent — this page probes the method itself and says exactly which case you are in.

The clamping contract

The spec pins four edges: negative distances clamp to 0 — and because 0 falls exactly on the boundary between the zero-length moveto and the next segment, the spec's boundary rule hands back the later segment; overshoot clamps to the total length (final segment); NaN throws a TypeError before the lookup runs (restricted float argument); and an empty path returns null.

code path

const seg = path.getPathSegmentAtLength(50);
// → {type: "C", values: [45, 20, 85, 20, 115, 100]} — the segment the pen is in

path.getPathSegmentAtLength(-10);    // clamps to 0 → boundary → the segment AFTER the zero-length M
path.getPathSegmentAtLength(1e9);    // clamps to total → final segment
path.getPathSegmentAtLength(NaN);    // throws TypeError (restricted float)
emptyPath.getPathSegmentAtLength(1); // → null
