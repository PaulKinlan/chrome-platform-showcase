Segment inspector: the d attribute, structured

A d attribute is a twenty-command mini-language packed into one string. getPathData() reads it back as an array of plain {type, values} objects — no parser, no polyfill. Type any path below and inspect exactly what the browser hands you, next to the rendering the same string produces. The surface probe checks the three new methods separately, because a build can ship part of the surface before the rest.

Chrome targets the SVG Path Data API for Chrome 159 behind the SVGPathDataAPI runtime flag. On an earlier or unflagged build, launch with --enable-blink-features=SVGPathDataAPI, or flip chrome://flags/#enable-experimental-web-platform-features and relaunch. Firefox 137+ ships the same API unflagged.

The two levels of setPathData() validation

The explainer pins two levels: a segment missing type or values throws TypeError structurally, while an unknown command letter or wrong value count is handled leniently — the explainer says skipped, SVG's "render what you can" model. Run both against the real method and see what this build actually writes:

setPathData([{values: [1, 2]}]) — missing required type
…
setPathData([{type: "M", values: [5, 5]}, {type: "X", values: [1]}, {type: "L", values: [9, 9]}]) — unknown command mid-list
…

code path

const path = document.querySelector("path");
const segments = path.getPathData();
// → [{type: "M", values: [10, 80]}, {type: "C", values: [40, 10, 65, 10, 95, 80]}, …]

// Structural validation throws:
path.setPathData([{ values: [1, 2] }]);        // TypeError — "type" is required

// Semantic validation is lenient (explainer: unknown segments are skipped):
path.setPathData([{ type: "M", values: [5, 5] },
                  { type: "X", values: [1] },      // unknown command
                  { type: "L", values: [9, 9] }]);
// explainer contract → d becomes "M 5 5 L 9 9"; the probe above shows
// what YOUR build actually writes (mid-implementation builds truncate)
