Stream error code range lab

streamErrorCode is an unsigned long — 32 bits — but Chromium's original dictionary carried it as an octet. Both dictionaries use [Clamp], not [EnforceRange], so out-of-range values never throw: they saturate. This lab feeds 22 awkward values (and any you type) through both constructors for real and compares the result with the WebIDL [Clamp] conversion computed in script.

What this lab can and cannot show. The constructor conversion below is real. The other half of the change — carrying the full 32-bit code on the wire when you abort() a stream — needs a live HTTP/3 WebTransport server, which this site does not run, so no stream is aborted here. The HTTP/3 error code column is computed from the WebTransport-over-HTTP/3 mapping, labelled as such, and nothing is sent. If the standard form is missing in your browser its column shows the real TypeError; there is no flag that adds it (tested in Chrome 153 with --enable-experimental-web-platform-features).

reading the results

[Clamp] maps NaN to 0, saturates at the type's bounds (so -1 → 0, 2**32 → 4294967295, 300 → 255 for an octet) and rounds fractions to the nearest integer, ties to even (2.5 → 2, 1.6 → 2). Observed deviation: Chromium 153's legacy [Clamp] octet conversion truncates fractions instead (1.6 → 1, 1.5 → 1, 3.5 → 3) — the table marks those rows as differing rather than hiding it; whether the new unsigned long? member shares that conversion path in 159 is an open question this lab answers live on a build that has it. Integer inputs are unaffected. null is a real value for the nullable standard member — it is how a session-level error says “no stream code” — but for the legacy non-nullable octet it converts to 0. undefined means “not present”: the standard default is null, and the legacy constructor leaves the code null too. The old byte-sized limit is why any application protocol with codes above 255 could not round-trip them through Chromium before this change.
