Reconnect diagnostics

IndexedDB stores values with the same structured-serialization algorithm as postMessage, so a serializable WebTransportError can be saved as-is. A reconnecting client can persist the last failure, and after a reload or crash its diagnostics screen reads back a real WebTransportError — not a lossy string — to explain why the previous session died.

Nothing here touches the network — the “failure” is constructed locally, as a real session would reject with it (no HTTP/3 server is available). The IndexedDB write and read are real. Where serialization is unsupported (Chrome 153 tested — no flag enables it — or a newer build launched with the writer kill switch --disable-blink-features=WebTransportErrorSerialization), put() throws DataCloneError and the page stores a plain {name, message, source, streamErrorCode} record instead, labelled FALLBACK. Chromium keeps the reader permanently enabled, so a record written natively stays readable even after the kill switch disables writing.

why decoding is never switched off

The kill switch only gates the writer. If Chromium ever had to turn serialization off, values that sites had already written to IndexedDB (or other structured-clone storage) would otherwise become unreadable and break those sites' startup paths. Keeping the versioned decoder always on means a kill-switch flip can only stop new writes — the format version, source discriminant, has-code flag and payload length are all validated on read.
