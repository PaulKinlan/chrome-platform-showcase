Constructor inspector

Fill in a message, a source and a streamErrorCode, pick which constructor form to call, and this page runs new WebTransportError(…) for real and reads every field back off the object it got — or shows the exception it threw. No WebTransport session is opened: the constructor is a plain script call.

No flag turns this on. The standard (message, options) constructor ships unflagged in Chromium builds that contain the alignment change (ChromeStatus targets Chrome 159). ChromeStatus lists enable-experimental-web-platform-features, but Blink's WebTransportErrorSerialization runtime feature is already status: "stable" and the constructor change has no runtime flag at all — launching Chrome 153 with --enable-experimental-web-platform-features --enable-blink-features=WebTransportErrorSerialization was tested and changes nothing. A browser without the change throws TypeError for the standard form; that outcome is shown verbatim below, not hidden.

what to look for

The spec's constructor steps set name to "WebTransportError", copy message, and store options.source and options.streamErrorCode in the [[Source]] and [[StreamErrorCode]] slots. The name has no legacy mapping, so error.code is 0. Try a code of 70000 in both forms: the standard form keeps it, the legacy form clamps it to 255. Pick "session" with the legacy form and the source still reads "stream". More edge values live in the code range lab.
