Worker error relay

A common WebTransport architecture keeps the session in a dedicated worker so the UI thread never janks on stream I/O. When a stream or the session fails, the worker has to tell the UI why. With serializable WebTransportError it can just postMessage(error) and the UI receives a real WebTransportError — instanceof, source and the full 32-bit streamErrorCode intact — and can branch on them directly.

No network session is opened. A real WebTransport session needs an HTTP/3 server, which this site does not run, so the worker constructs the error a failing session or stream would reject with. Everything after that — the worker's postMessage, the structured clone, the type of the received value — is real. In a build without serializable WebTransportError (Chrome 153 tested; no flag enables it) the worker's postMessage throws DataCloneError and it falls back to an app-level {name, message, source, streamErrorCode} wire shape — shown below as FALLBACK, never as native.

why this matters

Before, a worker-based client had to flatten every error into a plain object and every consumer had to agree on that shape — and anything above 255 had already been lost in Chromium's byte-sized code. Now the error crosses the thread boundary as itself, so shared error-handling code (if (e instanceof WebTransportError && e.source === "session")) works the same in the worker and on the UI thread.
