Serialization across channels

WebTransportError is now [Serializable]: the structured-clone algorithm copies its message, source and nullable streamErrorCode and rebuilds a real WebTransportError on the other side. Before, Chromium threw DataCloneError. Send one through four real channels and see exactly what arrives.

Kill switch, not a flag. Serialization is on by default in builds that contain it; Blink's WebTransportErrorSerialization runtime feature (status: "stable") exists only as a writer-side kill switch. To watch the off state in such a build, launch with --disable-blink-features=WebTransportErrorSerialization: writing then throws DataCloneError again, while reading already-stored values keeps working (see the IndexedDB diagnostics demo). In a build without the change (Chrome 153 tested, with and without --enable-experimental-web-platform-features), every channel below reports the real DataCloneError. The “wire-shape fallback” is ordinary app code and is labelled as such wherever it runs.

what the serializer preserves

Chromium's writer emits a versioned record — format version, UTF-8 message, a reserved (empty) stack field, a source discriminant, a has-code flag and a 32-bit code — and the reader validates every field before constructing the object. The stack is not carried yet, and the received object's name comes from the interface, not from the payload. The nullable code survives as null, distinct from 0; the contrast button shows that a plain DOMException was always cloneable — it was only the subclass that failed.
