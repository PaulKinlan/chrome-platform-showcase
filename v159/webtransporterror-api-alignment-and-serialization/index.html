WebTransportError API alignment and serialization

Chromium's WebTransportError predates the final WebTransport spec. This change adds the standard new WebTransportError(message, {source, streamErrorCode}) constructor while keeping the shipped dictionary constructor as a compatibility overload, carries the full unsigned long stream error code instead of an 8-bit one, and makes the error structured-clonable — so it survives postMessage(), structuredClone() and IndexedDB with its message, source and nullable streamErrorCode intact.

How to try it: there is no flag to flip. The constructor and code-width changes are unflagged, and Blink's WebTransportErrorSerialization runtime feature is status: "stable" — on by default, kept only as a writer-side kill switch (--disable-blink-features=WebTransportErrorSerialization turns writing off; reading stays on). ChromeStatus lists enable-experimental-web-platform-features, but Chrome 153 launched with it (and with --enable-blink-features=WebTransportErrorSerialization) behaves exactly like default 153: the standard form throws TypeError and cloning throws DataCloneError. You need a Chromium build containing the change (ChromeStatus: Chrome 159 desktop and Android). Every demo detects the behaviour itself and labels its fallback.

concepts

  1. Constructor inspector

    Basic: set message, source and streamErrorCode, choose the standard or legacy form, and read every field — name, message, source, streamErrorCode, the legacy code (0), instanceof DOMException — off the object you actually got, or the exception you actually got.

  2. Constructor compatibility matrix

    Inspection + migration: ten constructor calls run live and compared against three reference behaviours (spec-only, legacy-only Chromium, aligned Chromium), exposing how WebIDL overload resolution treats an object, null, a number or a trailing argument — plus a runnable feature-detecting helper for libraries that must span both builds.

  3. Stream error code range lab

    Edge cases: 22 values (256, 65535, 232−1, 232, −1, 1.6, 2.5, NaN, "0x10", null…) through both constructors, compared with WebIDL [Clamp] for unsigned long? vs octet, with the HTTP/3 error code each would map to (computed, not sent). Surfaces a real deviation: Chromium's octet conversion truncates fractions (1.6 → 1) where WebIDL rounds.

  4. Serialization across channels

    The serialization contract: send an error through structuredClone(), MessageChannel, BroadcastChannel and a same-origin iframe (a separate realm) and see whether a real WebTransportError arrives — or the real DataCloneError, with an opt-in labelled wire-shape fallback.

  5. Worker error relay

    Practical architecture: a connection-manager worker reports stream/session failures to the UI thread by posting the WebTransportError itself; the UI branches on source and the full 32-bit code. Also UI → worker cancel reasons. No network session is opened — the worker constructs the error, the clone is real.

  6. Reconnect diagnostics

    Practical persistence: store the last failure in IndexedDB, reload, and a diagnostics panel reads back a real WebTransportError — demonstrating why Chromium keeps the decoder permanently on even if the writer kill switch is ever flipped.

why it shipped

The motivation on ChromeStatus is interoperability: Chromium accepted only a dictionary constructor, narrowed outgoing application stream error codes to 8 bits although the attribute is an unsigned long, and threw DataCloneError for a type the spec marks [Serializable]. Firefox already ships the aligned API including serialization (and contributed the WPT coverage); WebKit has landed the constructor and code-width changes; the rest is tracked in Interop 2026. Applications that move errors between workers or persist them can now do so without custom conversion; the legacy constructor stays, measured by a UseCounter, so no existing code breaks. The intentional observable changes: codes above 255 are no longer truncated, and cloning now succeeds instead of throwing.

the API surface

// W3C WebTransport §12 (+ Chromium's compatibility overload)
[Exposed=(Window,Worker), Serializable, SecureContext]
interface WebTransportError : DOMException {
  constructor(optional DOMString message = "", optional WebTransportErrorOptions options = {});
  // Chromium only, [MeasureAs=WebTransportErrorLegacyConstructor]:
  constructor(WebTransportErrorInit init, optional any legacyIgnored);
  readonly attribute WebTransportErrorSource source;
  readonly attribute unsigned long? streamErrorCode;
};
dictionary WebTransportErrorOptions {
  WebTransportErrorSource source = "stream";
  [Clamp] unsigned long? streamErrorCode = null;
};
dictionary WebTransportErrorInit {        // legacy
  [Clamp] octet streamErrorCode;
  DOMString message;
};
enum WebTransportErrorSource { "stream", "session" };

const e = new WebTransportError("quota exceeded", { source: "stream", streamErrorCode: 70000 });
worker.postMessage(e);                     // arrives as a WebTransportError
const copy = structuredClone(e);           // copy.streamErrorCode === 70000
