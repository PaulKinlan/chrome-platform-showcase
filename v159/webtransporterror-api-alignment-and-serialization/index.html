WebTransportError API alignment and serialization

Chrome 159 brings WebTransportError up to the current spec: the standard (message, options) constructor arrives (the shipped dictionary-only constructor stays for compatibility), the stream error code carries the full unsigned-long range end to end, and the error becomes structured-clonable — so it can cross postMessage boundaries with its message, source, and nullable streamErrorCode intact.

concepts

  1. Constructor alignment — construct the error every way the old and new IDL allow, live, and compare what this build accepted: the legacy dictionary form, the standard (message, options) form, and the properties each produces.
  2. Full code range — the unsigned-long contract: sweep streamErrorCode through 0, mid-range, and 4294967295, construct a real error for each, and verify the value reads back unclamped — plus what WebIDL conversion does to out-of-range input.
  3. Clone across threads — serialization at work: structuredClone() and a real round-trip through a dedicated Worker, checking that message, source, and error code survive — or an honest DataCloneError on builds that can't serialize it yet.

why it shipped

Chromium shipped WebTransportError early, with a dictionary-only constructor and a clamped error-code path, and the spec moved on: a standard DOMException-style (message, options) signature, the full 32-bit application error-code space from the wire to the API, and serializability so errors can be reported across workers. Serialization writes are enabled by default behind a writer-side runtime kill switch, while decoding stays permanently enabled for forward compatibility.
