Declarative Menu Basics

Probe how this browser parses <menubar>, <menulist>, <menuitem>, and <submenu>, then open a real declarative menu from a button.

Behind a flag. The runtime feature is MenuElements (status experimental in Blink's runtime_enabled_features.json5; there is no dedicated chrome://flags entry). To try the real elements in Chrome 143+ (Canary/Dev): enable chrome://flags/#enable-experimental-web-platform-features and relaunch, or launch with --enable-blink-features=MenuElements.

1 · Element parsing probe

The honest support discriminator: an implemented element parses to its own interface, an unimplemented one parses to HTMLUnknownElement. This probe can — and on browsers without the flag, does — return "not supported".

2 · Invoke a <menulist> from a button

In the shipped Chromium implementation, <menulist> is always a popover (type auto) and is invoked through the standard popover commands — this demo uses command="toggle-popover" commandfor="actions-menu". (The explainer also proposes a dedicated toggle-menu command, which is not in Chromium's command parser yet.) The invoking button gets implicit aria-haspopup=menu and aria-expanded, and focus moves into the menu when it opens.

Native menu disabled in this browser. This browser parses <menulist> as HTMLUnknownElement, so it has no popover behavior, no menu role, and no keyboard model — the live menu above is hidden rather than shown broken. Enable the flag (banner at the top) in Chrome 143+ and reload to use it. The ARIA-pattern concept on this feature has a fully working fallback menu you can use in any browser.
