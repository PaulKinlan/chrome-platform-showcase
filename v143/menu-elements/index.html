Menu elements

Application menus — menubars, dropdown command lists, checkable options, nested submenus — have always meant hand-rolling the whole ARIA menu pattern. The new <menubar>, <menulist>, <menuitem> and <submenu> elements ship the pattern natively: implicit menubar/menu/menuitem roles, the APG keyboard model, popover + anchor-positioning behavior, and checkable radio/checkbox items via <fieldset checkable> — all from markup.

concepts

  1. Element family probe

    Detect all four interfaces and every shipped member — and diagnose which iteration this engine carries: none, the early MenuElements dev-trial surface (menubar/menulist/menuitem with ID-reference submenus, as in Chromium 141), or the current explainer surface with <submenu> nesting, defaultChecked, and fieldset.checkable.

  2. Application menubar

    A full File/View menubar in current-spec markup rendered live where supported — beside a hand-rolled ARIA Authoring Practices menubar (roving tabindex, arrow keys, popover-powered dropdowns) that works in every modern browser, so you can feel exactly what the elements replace.

  3. Checkable state lab

    The state model under <fieldset checkable=single|multiple>: live reflection probes for the checkable keyword normalisation, the deliberately non-reflected checked IDL vs the reflected defaultchecked, and a working manual menuitemradio/menuitemcheckbox implementation with a state ledger on engines without the elements.

  4. Button-invoked menulist

    The one-off dropdown: <button command=… commandfor=…> invoking a standalone <menulist> — with a live matrix of which command keywords (toggle-menu, the generic popover commands…) this engine actually honours, and the plain-[popover] baseline that works today showing exactly what menulist inherits.

why it shipped

The legacy <menu> element is a <ul> with a different name — no menu role, no command behavior, no keyboard model. Every real application menu on the web is therefore a bespoke re-implementation of the ARIA menu pattern, and most get focus order, aria-expanded, checkable state, or light dismiss subtly wrong. Because the new elements build on the Popover API, Invoker Commands, and CSS anchor positioning, the platform already had every underlying behavior — these elements bundle them with the correct implicit semantics so an accessible application menu is just markup. Navigation menus are explicitly out of scope (links are disallowed in the content model).

enabling it

In developer trial (behind a flag) as of Chrome 143; the MenuElements runtime feature is experimental in runtime_enabled_features.json5. Launch with --enable-blink-features=MenuElements or enable chrome://flags/#enable-experimental-web-platform-features. The surface is still evolving: builds around 141–143 carry the early iteration (no <submenu> element, no fieldset.checkable IDL, ID-reference submenus via commandfor), while the current explainer adds nested <submenu>, defaultchecked, and the toggle-menu command — the probe tells you which one you're holding.
