Menu elements

New built-in <menubar>, <menulist>, <menuitem>, and <submenu> elements give command menus real platform semantics: native menu/menubar accessibility roles, a disabled IDL attribute with :enabled/:disabled pseudo-class support, checked/defaultChecked state, and command/interest invoker wiring — everything today's role="menubar" ARIA patterns hand-build by hand. In developer trial behind chrome://flags/#enable-experimental-web-platform-features or --enable-blink-features=MenuElements at Chrome 143.

concepts

  1. Element & interface probe

    Real falsifiable checks per element: does createElement produce the dedicated interface or HTMLUnknownElement, is the disabled/checked IDL present, and does menuitem:disabled actually match?

  2. Menubar ARIA bridge

    A fully working WAI-ARIA-practices menubar (roving tabindex, arrow keys, Escape) beside the equivalent declarative markup rendered live — so you see exactly what the new elements replace and what your browser does with them today.

  3. Button-invoked menulist

    The explainer's button → menulist invocation: probes the real command/commandfor invoker surface on this browser and drives a clearly-labelled fallback toggle where the native path is unavailable.

why it shipped

The legacy <menu> element is just a list — it exposes no menu semantics to assistive tech, and every product rebuilds menus with ARIA roles, roving tabindex, and hand-rolled keyboard code. Dedicated elements make the correct pattern the default one.
