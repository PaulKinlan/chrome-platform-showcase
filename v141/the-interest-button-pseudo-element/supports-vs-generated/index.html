@supports is not enough

Chromium's selector parser recognises ::interest-button even when the runtime feature that generates the box is off. So @supports selector(::interest-button) and CSS.supports() both report true in a browser that will never draw the button. A fallback that hides itself behind @supports then leaves touch users with no affordance at all. This page measures that gap in your browser and compares three migration strategies.

the lesson

  • Parsing and generation are separate in Chromium. The selector map in css_selector_parser.cc has no feature gate, while Element::UpdatePseudoElement(kPseudoIdInterestButton) only runs when HTMLInterestForInterestButtonPseudo is enabled.
  • So a fallback must key off observed behaviour: set content, then read the pseudo-element's used width. Do not set an explicit width on it, or the computed value will be your declared width instead of auto.
  • Strategy C is legitimate where the information is truly secondary, because long-press then "Show details" still works. The explainer says designers sometimes prefer no button.
  • The fallback buttons use tabindex="-1", which mirrors the pseudo-element staying out of the tab order. The link itself is the keyboard path, since focus shows interest.
