The ::interest-button pseudo element

An opt-in, button-like pseudo-element that the browser generates right after an interest invoker (an <a href> or <button> with interestfor) once you give it a content value. It is mainly for touchscreens: there is no hover, long-pressing a link opens the browser's context menu, and finding "Show details" in that menu takes a second tap. Tapping the ::interest-button shows interest straight away, with no delay: the target popover opens and the link does not navigate. It is part of Interest Invokers (the interestfor attribute), which already has its own demos. These pages cover only the pseudo-element.

Behind a runtime flag. The Blink feature is HTMLInterestForInterestButtonPseudo with status experimental. ChromeStatus lists it as "Proposed" with no shipped milestone. To try it, enable chrome://flags/#enable-experimental-web-platform-features and relaunch. You can also launch Chrome with --enable-blink-features=HTMLInterestForInterestButtonPseudo or --enable-features=HTMLInterestForInterestButtonPseudo. We verified all three on Chrome 153. Watch out: without the flag, Chrome 153 still parses the selector (CSS.supports('selector(::interest-button)') is true) but never generates the box. Every page here checks for a generated box, not for selector parsing.

concepts

  1. Tap for the hovercard

    The canonical pattern from the spec and explainer: profile and issue links with popover=hint hovercards, plus a[interestfor]::interest-button { content: "ⓘ" / "" }. Switch between "always", "coarse pointer only" (the spec's @media (any-pointer: coarse) recipe) and "off". Tap or click the ⓘ. A live log records each interest and loseinterest event with its source, shows whether the link navigated, and shows which box the popover is anchored to.

  2. Styling inspector

    The pseudo-element is fully styleable. Pick the glyph and its alt text, size, spacing, shape and a colour pair from the design tokens, turn on an ::after to see the box order, and add an :interest-source highlight. The page writes out the exact CSS rule. It also reads back getComputedStyle(el, '::interest-button') and the measured box, so you can see the UA defaults (24px minimum, cursor: help) and the contrast ratio.

  3. Comment thread: mentions & glossary

    A product scenario: a code-review thread with @mentions that open rich profile cards (with a working Follow button) and glossary terms that open plain hints. The ⓘ buttons appear only on coarse-pointer devices, or when you turn on the touch preview. If the box isn't generated, real <button popovertarget> fallbacks are added instead, each one labelled as a fallback.

  4. Generation rules & edge cases

    When is the box generated? This is a live matrix with the spec's expected answer and the measured answer for each case: a valid link, no interestfor, a missing target id, an <a> without href, a disabled button, a <span>, an <input type=button>, display: contents, a non-popover target and content: none. You can change attributes and watch the box appear or disappear. The page also traces the keyboard Tab order (the pseudo is not focusable) and reads out the pointer media queries.

  5. @supports is not enough

    A migration lesson. @supports selector(::interest-button) returns true while the box is not generated, so a naive fallback leaves touch users with no affordance at all. Compare three strategies side by side: naive @supports, a behavioural probe with a real <button popovertarget> fallback, and the pseudo only. A live readout shows which affordance each visitor actually gets.

why it is proposed

Interest invokers bring hovercards to every input mode. A mouse shows interest by hovering, a keyboard by focusing, and a touchscreen by long-pressing. On a link, a long press opens the browser's context menu, where "Show details" is one item among several. It works, but users rarely find it. The CSSWG settled on an opt-in pseudo-element (Open UI "Option 3.5", CSSWG issue 12437) instead of an automatic button. Designers wanted to keep constrained layouts uncluttered, and secondary information does not always justify an extra control. The pseudo-element is deliberately left out of the focus order and the accessibility tree. Keyboard focus already shows interest, and a second tab stop that does the same thing would only add noise.

the surface

/* Opt in: the UA stylesheet sets no content, so nothing renders until you do. */
@media (any-pointer: coarse) {
  a[interestfor]::interest-button {
    content: "ⓘ" / "";        /* glyph / alt text (the pseudo is not in the a11y tree) */
  }
}

/* UA defaults Chromium ships (html.css): */
[interestfor]::interest-button {
  display: inline-block; vertical-align: middle; color: inherit;
  background-color: transparent; box-sizing: border-box;
  min-inline-size: 24px; min-block-size: max(24px, 1lh);
  align-content: center; text-align: center; user-select: none; cursor: help;
}
[interestfor]::interest-button:hover  { background-color: color-mix(currentColor 10%, transparent); }
[interestfor]::interest-button:active { background-color: color-mix(currentColor 20%, transparent); }
