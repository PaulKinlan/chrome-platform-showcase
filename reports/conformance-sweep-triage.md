# Conformance sweep — triage

Companion to `reports/conformance-sweep.json` / `.md`. The sweep is generated by
`deno task conformance-sweep` (or `node scripts/conformance-sweep.mjs`); read the generated report for the
full per-assertion list, and this file for what the numbers mean and what to do next.

## What the numbers are

- **4961 assertions** across every committed `conformance.json`, run in real headless Chrome 152
  (`/opt/google/chrome/chrome`, stable channel, this machine) via the site's own
  `/conformance/run-all/` page, then every failure re-run on the suite's own conformance page.
- **Pass 4316 · Fail 291 · Blocked 3 · Future 351.** `future` means the assertion belongs to a
  milestone newer than the running Chrome; the run-all page marks those `future` and they are not
  failures. 4961 = 4316 + 291 + 3 + 351.
- **After re-check: 282 real fail · 3 real blocked · 9 instrument false positives.**
  A suite is written against the environment of its own page. Nine pass-1 failures pass on their own
  suite page: five `v134/attribution-reporting-…` assertions fetch a relative route (`../trigger-context-id-builder/...`) that
  resolves incorrectly from `/conformance/run-all/`, and four read the page's response headers
  (`document.featurePolicy`) or its DOM, which `/conformance/run-all/` does not provide.
  **Never count a pass-1 failure as a demo bug without the pass-2 re-check.**

## Cause rollup (real failures)

| cause | count | what it means |
|---|---:|---|
| `api-surface-absent-in-this-chrome` | 142 | This Chrome build does not expose the member the spec defines. Not a demo bug by itself. |
| `behavioural-assertion-failed` | 115 | The surface exists but behaves differently from the assertion. Triage individually. |
| `css-property-absent-in-this-chrome` | 26 | `CSS.supports()` is false for the spec keyword in this Chrome. |
| `needs-user-mediation` | 2 | Needs a user gesture / permission (window controls, window state). |

Most of these are **browser state, not demo defects**: 105 of the 106 features with real failures
already carry a flag / capability / fallback note in their demo pages. The catalogue is honest about
what Chrome 152 does not implement; the conformance suites record the spec contract that is not met.

## Demos that needed an actual change (done in this branch)

- `v149/image-rendering-crisp-edges` — `image-rendering: smooth` is in CSS Images 3
  (`auto | smooth | high-quality | pixelated | crisp-edges`) but Chrome 152 does not implement
  `smooth` or `high-quality` (`CSS.supports` false; a `smooth` declaration silently computes to
  `auto`). Four concept pages presented a `smooth` sample with no note, so the sample looked like an
  `auto` sample. Each of `pixel-art-gallery`, `scaling-compare`, `canvas-rendering` and
  `icon-set-comparison` now carries the repo's `.unsupported-banner` note, hidden by
  `@supports (image-rendering: smooth)` where the keyword is real. The suite assertion
  `image-rendering-smooth-supported` stays **red in Chrome 152** — that is the correct, honest result;
  the assertion is not wrong and was not touched.
- `v149/image-rendering-crisp-edges/icon-set-comparison` — the four-mode comparison grid is a fixed
  4 × 150px grid; at 360px it pushed the document to 680px wide while `body { overflow-x: hidden }`
  clipped it, so the third and fourth modes were unreachable on a phone. The grid now scrolls inside
  its own box (`overflow-x: auto`) and is focusable (`role="region"`, `aria-label`, `tabindex="0"`).
  Measured: 360px viewport, document overflow 320px → 0; grid 308px client / 654px scroll region.
- `v147/js-profiling-in-dedicated-workers` — no page named the Blink flag for the worker half of JS
  Self-Profiling, so the feature index gained an "enabling it" section and `worker-profile`'s fallback
  and the explorer's worker notice name `ProfilerAPIForDedicatedWorker` and both enable routes. While
  verifying that, the demo turned out to have a real bug: `worker.js` had no `try`/`catch` around
  `new self.Profiler(...)`, so the flag-on `NotSupportedError` (Document Policy not enabled for the
  worker context) was swallowed and the page sat on `running…` forever. Construction and `stop()` are
  now wrapped and the page reports the exact reason. Evidence, per configuration, driving the demo's
  own click: flag off → `Profiler not available in this worker …`; flag on → `Worker Profiler API is
  present (ProfilerAPIForDedicatedWorker is enabled) but construction failed: NotSupportedError …`.
  This correction is also why `reports/devtools-mcp/js-profiling-worker-flag-check.spec.mjs` was
  rewritten: its first version asserted "the table has a row", which the `running…` placeholder
  satisfied, so it passed on the hang (bead `chrome-platform-showcase-aa5`). It now asserts that the
  table leaves the in-flight state with either a positive sample count or a named reason, and it
  fails on the old behaviour.

## Follow-ups this sweep surfaced (not fixed here)

1. **Concept pages have no responsive matrix coverage.** `deno task responsive-check` only drives
   `v<N>/<feature-slug>/` (the feature index); the ~850 concept pages beneath them — where most of
   the interaction lives — are never measured. `icon-set-comparison` (above) is the proof: the
   feature index passes the matrix while its concept page was 320px wider than a phone. Extending the
   harness to concept pages, or recording concept-level support, is the next coverage step.
2. **Flag names for the biggest absent surfaces** (from Chromium main
   `third_party/blink/renderer/platform/runtime_enabled_features.json5`): `MenuElements`
   (v143/menu-elements, experimental), `GamepadButtonTypes` (v147, experimental),
   `CSSMediaElementPseudos` (v150/media-element-pseudo-classes, experimental),
   `SvgPathLengthCssProperty` (v149/150 path-length, experimental), `CSSImageAnimation`
   (v152/css-image-animation, test), `CSSWindowDrag` (v151/152/window-drag, stable in main — not in
   152), `CSSTextDecorationSkipSpaces` (v150, stable in main — not in 152). Demos behind these should
   name the exact `--enable-blink-features=` / `chrome://flags/#…` step; several already do.
3. **`v147/js-profiling-in-dedicated-workers`** — both pass 1 and pass 2 fail
   `profiler-supported-in-dedicated-worker` (`false`). The assertion builds a **Blob** dedicated
   worker and looks for `Profiler` inside it. The worker half of JS Self-Profiling is the Blink
   feature `ProfilerAPIForDedicatedWorker` (status: experimental) while the main-thread `ProfilerAPI`
   is stable, and Chrome 152 stable does not enable it, so a Blob worker cannot see `Profiler`
   regardless of what the page sends. (`Document-Policy: js-profiling` *is* sent on the feature's demo
   and conformance routes; three sibling assertions pass because of it, which is why they show up as
   instrument false positives.) Driving the demo with the flag on does **not** produce a worker
   profile: the worker global exposes `Profiler`, and construction then throws
   `NotSupportedError: Failed to construct 'Profiler': Document Policy is not enabled for this
   context` — the policy is not active in the dedicated-worker context in this build. The assertion is
   not wrong (it describes the spec contract) and it is not reachable in Chrome 152 by any flag
   route we found, so it is **flagged for a human** rather than edited. The demo's own bug in this
   area — a swallowed constructor rejection that left the page on `running…` forever — is fixed above,
   and 7 of the 8 real assertions in this feature's suite pass, so the feature is otherwise
   demonstrated honestly (main-thread profiling works).
