Session-bound secrets in practice

Both TLS endpoints can run the same exporter with the same inputs and arrive at the same bytes, so the derived value works as proof of "I am this session" without ever crossing the wire. Fill in the three inputs, and the page performs the genuine exportKeyingMaterial() call on a freshly constructed session and prints whatever really happened. The companion panel shows what the server does with its matching copy.

This showcase cannot reach an HTTP/3 server, so on Chrome 158+ the live call finishes with the spec's InvalidStateError after the dead-endpoint session fails; argument handling still runs for real. Builds before 158 lack the method and the result panel reports that plainly. Enable on older builds via --enable-blink-features=WebTransportExportKeyingMaterial or chrome://flags/#enable-experimental-web-platform-features.

The server half of the handshake

# server pseudocode (any QUIC stack exposing the TLS exporter)
material = tls.export_keying_material(
    label   = b"EXPORTER-showcase-auth",
    context = b"account:12345" + connect_stream_id,  # see below
    length  = 32)
assert hmac(material, challenge) == value_from_client  # same bytes, both ends

Chromium folds the WebTransport CONNECT stream ID into the HTTP/3 export context. Several WebTransport sessions pooled on one HTTP/3 connection therefore derive different material per session — a server must account for that stream ID when computing its copy. The client never sends the material itself; it sends an HMAC over a server challenge, keyed by the material.
