WebTransport keying material export

TLS has long had a side door for applications that need a shared secret: the keying material exporter (RFC 5705 / RFC 8446 §7.5), which derives bytes from the session's master secret so both endpoints can compute the same value without ever sending it. Chrome 158 exposes it to WebTransport as transport.exportKeyingMaterial(label, context, outputLength) — a Promise<Uint8Array> of key material cryptographically bound to this session, ideal for channel binding, token binding and application-layer authentication.

concepts

  1. The validation ladder, in spec order

    The method validates before it looks at connection state: a label over 255 bytes rejects with RangeError, so does an oversized context, and so do outputLength of 0 or above the implementation ceiling (at least 4096 — exactly 4096 in Chromium); only then does a closed or failed session earn its InvalidStateError. Every rung probed with real calls on real session objects, including the ordering proof: oversized label on a failed session is a RangeError, not an InvalidStateError.

  2. Design a channel binding

    The use case the exporter exists for: prove to your server that the client speaking the application protocol is the same one that holds the TLS session. Compose a real call — label, context, output length — fire it against a live session attempt, and read the honest outcome; alongside it, the server-side recipe (the matching export plus Chromium's CONNECT-stream-ID binding) that makes the two ends meet.

  3. The surface, precisely

    What exactly shipped: a 3-argument method on WebTransport.prototype returning a fresh promise per call ([NewObject]), absent entirely on pre-158 builds. Probes the prototype placement, arity, BufferSource acceptance (ArrayBuffer and views both), and the state race the spec writes out — a still-connecting session's export settles only when the connection does.

why it shipped

Applications running over WebTransport routinely need to authenticate the channel, not just the user: a bearer token stolen from one connection should be useless on another. The TLS exporter is the standard answer — both sides derive Exporter(label, context, length) from the session secrets, so possession of the derived bytes proves you are the TLS peer, not a replaying middlebox. Native QUIC applications have always had this; the browser did not expose it, so web apps fell back to replayable tokens. exportKeyingMaterial() closes that gap with the exact IETF primitive, asynchronously (key schedules may live in another process), and with Chromium adding the WebTransport CONNECT stream ID to the export context so that multiple WebTransport sessions pooled over one HTTP/3 connection still derive distinct material per session.

The limits are part of the contract: labels and contexts up to 255 bytes (the RFC 5705 wire format carries them as 8-bit lengths), output from 1 byte up to an implementation ceiling that must be at least 4096. Chromium supports exactly 255/255/4096.

the API

const transport = new WebTransport("https://app.example:4433/session");
await transport.ready;

const enc = new TextEncoder();
const material = await transport.exportKeyingMaterial(
  enc.encode("EXPORTER-my-app-auth"),   // label — namespaced, ≤255 bytes
  enc.encode(accountId),                // context — binds the derivation, ≤255 bytes
  32,                                   // outputLength — 1..4096 in Chromium
);
// material: Uint8Array(32), identical on the server side —
// send HMAC(material, challenge), never the material itself.

Rejections: RangeError for oversized label/context or an out-of-range length (checked first), InvalidStateError for a closed/failed session — including a session that closes while the export is in flight.
