The validation ladder, in spec order

The spec writes the method as a ladder, and the order is observable: argument validation (three RangeError rungs) comes before the state check (InvalidStateError). So an oversized label rejected on an already-failed session proves the ordering — you get the RangeError, not the state error. Every rung below is a real call on a real session object; this page never predicts, it reports.

Chrome ships the method in Chrome 158 (flag WebTransportExportKeyingMaterial on earlier builds, or chrome://flags/#enable-experimental-web-platform-features). On a build without the method, every rung reports "method absent" — the honest state, never a simulated rejection. The session under test targets a dead local endpoint, so after its ready rejects, its state is reliably "failed" for the ladder.

const t = new WebTransport("https://127.0.0.1:44443/never");
try { await t.ready; } catch {}            // state is now "failed"

const big = new Uint8Array(256);           // one byte too many
await t.exportKeyingMaterial(big, ctx, 32);      // RangeError  (label > 255)
await t.exportKeyingMaterial(lbl, big, 32);      // RangeError  (context > 255)
await t.exportKeyingMaterial(lbl, ctx, 0);       // RangeError  (length 0)
await t.exportKeyingMaterial(lbl, ctx, 1 << 20); // RangeError  (length > ceiling ≥ 4096)
await t.exportKeyingMaterial(lbl, ctx, 32);      // InvalidStateError (failed session)
// note: the RangeErrors fire even though the session is failed —
// validation precedes the state check.
