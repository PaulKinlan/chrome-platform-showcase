MediaSession: Return Promise<undefined> from setMicrophoneActive() and setCameraActive()

When setMicrophoneActive() and setCameraActive() shipped in Chrome 93 their WebIDL return type was undefined — fire-and-forget. The W3C Media Session spec was later updated so both methods return a Promise<undefined>: resolved once the user agent has acted on the capture-state change, rejected with an InvalidStateError DOMException when the document is not fully active. Chrome 158 aligns the implementation with that spec — a tiny signature change with a classic migration hazard attached.

concepts

  1. Return-shape probe: what does this build hand back?

    Call the real navigator.mediaSession.setMicrophoneActive(false) and setCameraActive(false) and inspect exactly what comes back: undefined on a pre-158 build, a Promise on 158+ — and when it is a promise, await it and show that it resolves with undefined, as the spec requires.

  2. Migration: chaining code that survives both shapes

    Three strategies run against the live API: naive .then() chaining (throws a TypeError on pre-158 builds — watch it happen for real), Promise.resolve() normalisation that works on every version, and an explicit thenable-shape check. Return-shape drift is a confirmed regression class in this showcase; this page is the antidote.

  3. Call console: toggles, action handlers and the acknowledgement

    A believable in-call control bar wires "togglemicrophone" / "togglecamera" action handlers together with setMicrophoneActive() / setCameraActive() calls, logging each call's real settled result — the promise is how a 158+ page knows the user agent has acknowledged the state it declared.

  4. The one rejection the spec pins down: not fully active

    Capture a removed iframe's mediaSession, then call setMicrophoneActive(true) on it. Per spec, a document that is not fully active must get a promise rejected with InvalidStateError. On a pre-158 build there is no promise to reject — this page runs the sequence for real and labels exactly which contract this browser honoured.

why it shipped

These methods let a page tell the user agent what it considers the current microphone and camera capture state, so browser and OS media UI (a tab's mute indicator, a video-call hub) can stay truthful. As shipped in Chrome 93 they returned nothing, so a page could not know when — or whether — the user agent had acted on the declaration, and had no channel for the failure case. The spec's update capture state algorithm was updated (w3c/mediasession PR #312, cited by the ChromeStatus entry) to return a promise: resolved with undefined once the capture-state UI has been updated, rejected with an InvalidStateError DOMException when the associated document is not fully active, and — where a user agent applies a pause policy — rejectable with NotAllowedError when the user agent denies the change.

Chrome 158 closes the gap between the 2021 implementation and the current spec. The risk of such a change is not the new capability but old code: anything that assumed undefined keeps working, while code written against the new spec (.then(), await … .catch()) breaks on older builds — the exact return-shape drift this showcase tracks as a recurring defect class.

the API

// Chrome 93–157 (as originally shipped):
undefined setMicrophoneActive(boolean active);
undefined setCameraActive(boolean active);

// Chrome 158+ (current spec):
Promise<undefined> setMicrophoneActive(boolean active);
Promise<undefined> setCameraActive(boolean active);

// Fully active document  → promise resolves with undefined.
// Not fully active       → promise rejects with InvalidStateError.
await navigator.mediaSession.setMicrophoneActive(false);

The promise is produced by the spec's update capture state algorithm, shared by setMicrophoneActive, setCameraActive and (in the spec, not in this Chrome feature) setScreenshareActive. The migration-safe call for code that must run on both sides of 158 is await Promise.resolve(navigator.mediaSession.setMicrophoneActive(active)).
