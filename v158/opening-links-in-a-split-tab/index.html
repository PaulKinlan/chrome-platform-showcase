Opening links in a split tab

Browsers can tile two tabs side-by-side in one window, but a page had no way to ask for that: _blank gives a new full-size tab and the popup feature gives a detached window. This feature adds a third request — window.open(url, "_blank", "split,splitposition=right,splitsize=40") — plus a declarative windowfeatures attribute on <a>, <area> and <form>. It is only a request: the browser may ignore it (narrow window, mobile, already split) and fall back to a normal tab, and the page is never told which happened.

To actually get a split tab

Chromium ships this behind the Blink runtime feature WindowOpenSplitTab (status experimental, also an origin trial named WindowOpenSplitTab). There is no dedicated flag page entry. Enable it with, in order of preference:

  1. chrome://flags/#enable-experimental-web-platform-features → Enabled, relaunch.
  2. Launch with --enable-blink-features=WindowOpenSplitTab.
  3. Or --enable-features=WindowOpenSplitTab (overriding the base feature drives both renderer and browser side).
  4. Or --enable-experimental-web-platform-features.

You also need a desktop browser window wide enough to split, a click (user activation — popup blockers apply), and a tab that is not already in a split. On Android there is no split surface: the request is still parsed and falls back to a new tab.

concepts

  1. Feature string builder

    The canonical call. Compose split, splitposition, splitsize, the popup=0 guard and noopener, watch the exact string, then press the button to make the real window.open() call and read back what the opened pane can observe.

  2. BarProp fallback matrix

    The inspection tool. Each row opens one feature string and records the opened page’s locationbar.visible — the only signal that separates “popup” from “tab or split”. It exposes the legacy trap ("split" opens a popup in engines that do not know it) and why "popup=0,split" is the safe migration string.

  3. Declarative windowfeatures

    No JavaScript: <a windowfeatures="split">, <area> and <form>. Live attribute/IDL reflection, the implied target="_blank", rel still deciding the opener, and an existing named frame winning over the features.

  4. Search results side-by-side

    The explainer’s headline use case: a results page whose links are real anchors with windowfeatures="split,splitsize=50" — middle-click and the context menu still work — and the opened article tells the results list which one you are reading.

  5. Live preview through the handle

    Advanced composition: an editor opens a named preview pane with "popup=0,split,splitposition=right,splitsize=40", keeps the returned handle, streams edits with postMessage, re-uses the pane by name, contrasts split,noopener (handle is null) and closes the split with handle.close().

why it exists

Split tabs ship in Chrome, Edge, Firefox, Arc, Whale and Vivaldi, and the common reason to use one is “open this link next to what I am reading”: a search result next to the results page, a product next to the listing, a reference next to a tutorial, a live preview next to an editor, an assistant next to the page it is driving. The original Microsoft proposal used a new target="_split"; the reworked explainer moves the request into the extensible windowFeatures string so it can carry position and size hints, keeps the opener relationship intact (so previews and assistants can coordinate), and avoids colliding with frames already named _split.

Two privacy decisions shape every demo here: there is no navigator.splitTabSupported, and no event saying whether the split happened. Pages can detect API support ('windowFeatures' in HTMLAnchorElement.prototype) but never the outcome.

the API

New window features and the declarative attribute
surfacevaluesmeaning
splitbooleanRequest a split tab beside the opener. Wins over popup; falls back to a tab (or to the popup if both were given).
splitpositionleft right top bottomSide for the new content. Ignored without split.
splitsizeinteger %Share for the new content; invalid values ignored, Chromium clamps to 10–90.
windowfeatures / windowFeaturesfeature stringContent attribute + reflected IDL on a, area, form.
 
// Split where supported, ordinary tab everywhere else:
const pane = window.open("/article", "_blank", "popup=0,split,splitsize=40");
pane?.postMessage({ hello: true }, location.origin);  // opener is preserved

// Declarative (rel decides the opener; target="_blank" is implied):
<a href="/article" windowfeatures="split,splitposition=right">Read beside</a>

// API detection only — the outcome is never exposed:
const hasApi = "windowFeatures" in HTMLAnchorElement.prototype;
