Opening links in a split tab

Many browsers can now show two tabs side by side in one window, but a page has had no way to ask for that. The _blank/_self/_parent/_top targets cannot express it, and popup opens a detached window instead. This proposal adds three window features: split, splitposition and splitsize. You use them with window.open(url, '_blank', 'split,splitposition=right,splitsize=40'), or declaratively with a new windowfeatures attribute on <a>, <area> and <form>. It is only a request. The browser may decline, and it then falls back to an ordinary new tab.

Not shipped. ChromeStatus: developer trial in M158, origin trial M160–M170. The runtime flag is WindowOpenSplitTab (Blink status experimental). To enable it, launch Chrome with --enable-experimental-web-platform-features, --enable-blink-features=WindowOpenSplitTab, or --enable-features=WindowOpenSplitTab. There is no chrome://flags entry. Even with the flag on, the browser needs a split-view UI (Chrome desktop's split view). On mobile or in a narrow window the request falls back to a normal tab, and the demos say so.

concepts

  1. Split request playground

    Basic. Build a split request from real controls (position, size, popup=0 guard, noopener) and send it with a real window.open(). The opened view reports how it was presented (toolbar.visible, its opener, its viewport), and you can close it again with the returned handle's close().

  2. Feature-string inspector

    Inspection tool. Type any window-features string and see it tokenized with the HTML Standard's algorithm. The tool predicts what a browser without split support does with it (a bare "split" opens a popup) and what a supporting browser does with each hint, including invalid or out-of-range values.

  3. Search results with windowfeatures links

    Practical product. The search-results use case from the explainer, built with plain <a target="_blank" windowfeatures="split,…"> links and a <form windowfeatures>. It shows live IDL reflection, the rel="opener" rule for declarative splits, and a JS "open beside" enhancement that is safe in older browsers.

  4. Fallback and edge-case lab

    Edge / failure / migration. Seven real calls cover each fallback rule in the explainer: legacy "split" becomes a popup, the popup=0 guard, split plus popup, noopener returning null, named-target reuse ignoring features, invalid hints, and a call made after transient activation has expired.

  5. Live preview editor

    Advanced composition. The editor and live-preview use case from the explainer. The page opens its preview in a split as a real top-level tab (not an iframe), keeps the handle, streams edits to it over origin-checked postMessage, receives the preview's viewport reports, and collapses the split with preview.close().

why it is proposed

The explainer's use cases include search results opened beside the results page, an in-page agent that drives a page it opened next to itself, editor/live-preview tools, video next to a feed, document previews in email, and docs beside tutorials. Window Management was rejected as the answer: it needs a permission prompt and places windows on screens, with no notion of a split inside one window. The proposal keeps the opener relationship (as any window.open() does), so "split,noopener" or COOP are how to sever it. It exposes no API that reports whether a split happened, because that would add a fingerprinting surface. The only sanctioned detection is of API support: 'windowFeatures' in HTMLAnchorElement.prototype.
