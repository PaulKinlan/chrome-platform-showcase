OfflineAudioContext incremental rendering

OfflineAudioContext.startRendering() used to be all-or-nothing: one call, one giant AudioBuffer allocated up front — an hour of stereo at 44.1 kHz is over a gigabyte of floats. Chrome 158 makes rendering incremental: startRendering(chunkSize) now returns the next chunk as its own small buffer and may be called again and again, and the context can even be constructed with no length at all for indefinite rendering. Faster-than-real-time audio processing stops being memory-bound.

concepts

  1. The chunk loop, timed and trimmed

    Render a one-second graph in 2048-frame chunks and watch the loop that the new contract makes legal: every call returns its own buffer, currentTime advances chunk by chunk, requested sizes round up to the render quantum, and the final chunk is trimmed to exactly the remaining frames. A real behavioral probe first — the returned buffer's length, not wishful feature detection — decides whether your browser chunks or one-shots.

  2. No length, no limits (and the error ladder)

    Chrome 158 makes OfflineAudioContextOptions.length optional: omit it and you get an indefinite context whose length attribute reads null, rendering for as long as you keep asking. This page drives that constructor change — a TypeError on every older build, honestly shown — plus the full error ladder: chunkSize: 0, a chunk larger than the implementation allows, and the InvalidStateError once a finite context has rendered every frame.

  3. A mixdown exporter with real progress

    The product this unlocks: an offline mixdown that reports progress and streams its output. A three-second multi-oscillator arrangement renders in chunks behind a live progress bar and an incrementally-drawn waveform, accumulating WAV bytes as it goes — and the finished file is downloadable either way, with the legacy one-shot path clearly labelled when chunking isn't available.

why it shipped

Offline rendering is how the web does faster-than-real-time audio work: bounce a DAW project, pre-render game stingers, batch-process podcast audio, run analysis over a long recording. The old contract allocated the entire output AudioBuffer before the first sample was computed, which put long renders out of reach of exactly the constrained devices that benefit most from offline processing — and made progress reporting a hack (suspend/resume at timed offsets). The Microsoft Edge team's explainer proposed incremental delivery; the shipped shape keeps startRendering() itself as the chunk pump: pass a chunkSize, get a promise for that many frames (rounded up to a render quantum boundary, trimmed at the end), call again for the next chunk. Omit length at construction for an indefinite session — the attribute then reads null — and each chunk defaults to one render quantum.

The memory math is the whole story: a one-hour stereo render at 44.1 kHz is ~1.27 GB as a single buffer, but a 16384-frame chunk is 128 KB — the application decides how much to keep, convert, or stream to disk between chunks.

the API

// Finite render, chunk by chunk (Chrome 158):
const ctx = new OfflineAudioContext({ numberOfChannels: 2, sampleRate: 44100, length: 44100 * 60 });
buildGraph(ctx);
let rendered = 0;
while (rendered < ctx.length) {
  const chunk = await ctx.startRendering(16384);   // ≤ 16384 frames, quantum-aligned
  rendered += chunk.length;
  report(rendered / ctx.length);                   // real progress, small buffers
}

// Indefinite render — length is now optional:
const live = new OfflineAudioContext({ numberOfChannels: 1, sampleRate: 44100 });
live.length;                                       // null
const next = await live.startRendering();          // one render quantum per call

Legacy behavior is preserved: with no argument on a finite context, startRendering() still renders all remaining frames in one buffer, and pre-158 rules (single call only) apply where the feature is absent.
