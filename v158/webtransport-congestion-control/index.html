WebTransport congestion control

A cloud-gaming client and a bulk uploader want opposite things from the same congestion controller: one wants packets out now, the other wants the pipe full. Chrome 158 adds the congestionControl option to the WebTransport constructor — "default", "throughput", or "low-latency" — plus a read-only attribute of the same name that reports which preference the user agent actually satisfied.

why it shipped

Congestion control decides how fast a sender ramps up and how it reacts to loss. Algorithms tuned for throughput (BBR-family) keep the pipe full at the cost of queueing delay; loss-based or latency-aware behaviour keeps queues short at the cost of peak bandwidth. Before this feature a WebTransport application had no way to say which trade-off it wanted — every session got whatever the browser's QUIC stack defaulted to. The congestionControl option lets the application state its preference without naming (or being promised) a specific algorithm, which RFC 9002 explicitly allows endpoints to choose freely.

The read-only attribute closes the loop: the constructor resolves the request immediately, so transport.congestionControl reports "throughput" or "low-latency" only when the user agent actually has an algorithm optimised for it, and "default" otherwise. The spec marks the option itself a feature at risk, because at the time of writing no browser ships an algorithm genuinely optimised for low latency — which makes honest readback, rather than blind trust in the request, the whole point of the attribute.

the API

const transport = new WebTransport("https://example.com:4433/game", {
  congestionControl: "low-latency",   // "default" | "throughput" | "low-latency"
});

// Resolved in the constructor — no need to await ready:
transport.congestionControl;
// "low-latency"  → the user agent satisfied the preference
// "default"      → requested but not satisfied (or never requested)

The option is a member of WebTransportOptions with default "default"; the attribute is a readonly accessor on WebTransport.prototype returning the WebTransportCongestionControl enum. An unknown string in the option position is a WebIDL enum violation and throws TypeError before any connection is attempted.
