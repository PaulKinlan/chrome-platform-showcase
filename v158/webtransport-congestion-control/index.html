WebTransport congestion control

A game sending position datagrams and a backup tool pushing gigabytes want opposite things from the same congestion controller: the game wants the shortest queues, the backup wants the fullest pipe. Chrome 158 adds the congestionControl constructor option — "default", "throughput", or "low-latency" — plus a readonly attribute of the same name that reports which preference the user agent actually honored for the session. RFC 9002 explicitly permits a sender to choose its congestion controller; this is that choice, surfaced to the web.

concepts

  1. Ask, then read back what you got

    Construct three real sessions — one per enum value — and read transport.congestionControl straight off each object. The spec sets the internal slot at construction (before any connection exists), with one twist worth seeing live: a preference the user agent cannot optimize for is silently downgraded to "default" at construction time, and the attribute is how you find out.

  2. Pick the profile for the workload

    The product decision the enum encodes: match six real workloads — cloud gaming input, voice, live camera, file sync, log shipping, media VOD — to a profile, see why queue depth or goodput wins in each, and construct a real session with your chosen option to read back what this browser honors. The mapping table is the take-home.

  3. Dictionary edges and the readonly attribute

    The contract's sharp corners, each probed for real: an invalid enum string must throw a TypeError at construction; the attribute is a readonly accessor on the prototype (a strict-mode write must throw); and on a pre-158 build the option is an ignored unknown dictionary member while the attribute is absent — this page refuses to call that support.

why it shipped

Congestion control is the algorithm that decides how much unacknowledged data may be in flight. Loss-based algorithms in the Reno/CUBIC family probe for bandwidth until queues overflow — great for throughput, terrible for the latency of whatever shares the queue. Delay-sensitive algorithms (BBR-family, and the GoogCC-style controllers WebRTC uses) back off before queues build. A QUIC implementation ships several; before this feature a WebTransport session simply got the platform default, and a cloud-gaming service had no way to say "I would rather lose bandwidth than add 50 ms of queueing". The option is a hint by design: the spec requires the UA to fall back to "default" when it has no optimizing algorithm for the request, and the readonly attribute makes that negotiation observable instead of silent.

Chromium wires the two non-default preferences to its QUIC stack's algorithm choices (BBR-family for throughput-leaning, BBRv2/delay-aware tuning for low-latency), subject to platform and Finch configuration — which is exactly why reading the attribute back matters more than remembering a mapping table.

the API

const transport = new WebTransport("https://game.example:4433/session", {
  congestionControl: "low-latency",   // "default" | "throughput" | "low-latency"
});

transport.congestionControl;
// → "low-latency"  if the UA honored the preference (slot set at construction)
// → "default"      if it had no algorithm optimizing for the request

new WebTransport(url, { congestionControl: "fastest" });
// → TypeError: not a valid WebTransportCongestionControl enum value

The attribute is readable immediately — unlike reliability, it never waits for establishment, because the algorithm choice is made when the session object is created.
