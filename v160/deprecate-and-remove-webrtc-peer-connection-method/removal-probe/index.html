← Deprecate and remove WebRTC peer connection method

v160 · webrtc · removal probe + working replacement

Is createDTMFSender() gone from this browser?

Three real checks, in order: does RTCPeerConnection.prototype still expose the legacy method; what does calling it on a genuine audio sender return today (and which errors does it raise); and does the standard replacement, RTCRtpSender.dtmf, actually send tones over a live loopback call in this page.

No microphone, no sound. The audio track comes from a Web Audio oscillator at zero gain routed only into a MediaStreamAudioDestinationNode. Both peer connections live in this tab; nothing leaves your machine.

No flag to flip. Chromium has no runtime flag or kill switch for this removal (there is no DTMF entry in runtime_enabled_features.json5), so there is nothing in chrome://flags to enable or disable. What you see is simply which Chrome version you run: 159 and earlier still have the method, 160+ do not.

2 · Call the legacy method on a real sender

Creates a peer connection, adds the silent audio track with addTrack(), then calls pc.createDTMFSender(track) inside try/catch. In Chromium the legacy method was always a thin alias: it looks up the RTCRtpSender for the track and returns that sender's .dtmf object. A ReportingObserver listens for the deprecation report Chromium attaches to the call (id RTCPeerConnectionCreateDTMFSender, added for milestone 160).

reading the result

On Chrome 159 and earlier the probe reports the method present and the call returns the very same object as sender.dtmf — proof the migration is a one-line change with identical behaviour. On Chrome 160+ the property is gone, the call throws TypeError: pc.createDTMFSender is not a function, and only section 3 works. Firefox and Safari never shipped the method, so they show the removed state too.
