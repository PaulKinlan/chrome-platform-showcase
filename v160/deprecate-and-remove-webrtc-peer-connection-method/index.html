v160 · webrtc · deprecation & removal

Deprecate and remove WebRTC peer connection method

The method is RTCPeerConnection.prototype.createDTMFSender(track). It returns an RTCDTMFSender for sending telephone keypad tones (DTMF) on a call, but it was never in the WebRTC standard and only Blink implemented it. Chrome 160 removes it on Windows, macOS, Linux, ChromeOS and Android, as part of Interop 2026. The standard replacement has existed for years: RTCRtpSender.dtmf, which in Chromium returns the very same object.

No flag. This is a removal; before 160 the method is present and logs a deprecation warning (the IDL carries DeprecateAs=V8RTCPeerConnection_CreateDTMFSender_Method). There is nothing to enable: the probe tells you whether your browser still has it, and every other page uses only the standard replacement.

concepts

  1. Removal probe

    Is createDTMFSender still on the prototype? If so, call it on a live loopback call and compare it with sender.dtmf (same object), plus its legacy SyntaxError failure cases. If not, see the TypeError real code will hit.

  2. DTMF keypad

    The replacement in a real product shape: a softphone keypad on a live call, sending IVR tones with sender.dtmf.insertDTMF(), adjustable duration and gap, sequences with pauses, cancel, and a tonechange event log.

  3. Migration rewriter

    Paste code, find every createDTMFSender() call and rewrite it to the standard form, then prove on a live call that the rewritten expression returns the same object the legacy call did.

  4. DTMF edge cases

    Twelve real checks against the spec: null for video senders, InvalidStateError before negotiation and after close, InvalidCharacterError, uppercasing, cancel, timing clamps, comma pauses, and canInsertDTMF after a direction change.

use-case portfolio

  • Basic / canonical: removal-probe (is it gone, and what replaces it).
  • Inspection / migration tooling: migration-rewriter.
  • Practical product use: dtmf-keypad (softphone IVR dialing with the replacement).
  • Edge / failure / migration: dtmf-edge-cases.
  • Advanced composition: not built separately. Sending DTMF has no further API to compose with in the browser: received telephone-events are not exposed to script, so a "decode on the far end" demo would need a server. Source: webrtc-pc §7 (RTCDTMFSender is send-only).
