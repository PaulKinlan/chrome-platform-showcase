Deprecate and remove WebRTC peer connection method

Chrome 160 removes RTCPeerConnection.createDTMFSender(track) on Windows, macOS, Linux, ChromeOS and Android. It was a Blink-only, non-standard way to get a DTMF (telephone keypad tone) sender for an audio track. The standard replacement has been available all along: the dtmf attribute of the track's RTCRtpSender, an RTCDTMFSender with insertDTMF(tones, duration, interToneGap), toneBuffer, canInsertDTMF and tonechange events. Every concept below runs a real in-page loopback call, so you can see the replacement working, not just read about it.

concepts

  1. Removal probe

    Is createDTMFSender still on RTCPeerConnection.prototype in this browser? Calls it for real on a genuine audio sender (showing that it returns the very same object as sender.dtmf), runs its legacy error matrix (video track, unattached track, closed connection), listens for the deprecation report with a ReportingObserver — and pairs all of it with the standard replacement sending 159# over a negotiated loopback.

  2. Migration side-by-side

    Legacy code and standard code in two columns, both executed against the same live call. Plus a drop-in getDTMFSender(pc, track) helper that reproduces every legacy exception with standard API only, and a table comparing the two on four inputs in your browser.

  3. IVR keypad

    The product use case: an accessible 16-key phone keypad driving a phone menu over a real call. Keys append to the queued toneBuffer as the spec prescribes, a validated dial-string field surfaces the real InvalidCharacterError, duration and gap sliders show where the spec clamps, and an opt-in quiet sidetone plays genuine DTMF frequency pairs.

  4. canInsertDTMF inspector

    Step through offer, answer and ICE one call at a time, then break the call (inactive encoding, null track, stopped transceiver, closed connection; or recvonly / no telephone-event codec from the start). Each row compares the browser's canInsertDTMF with what the spec's six-condition algorithm predicts — and flags where Chromium deviates.

  5. Tone buffer edge lab

    Eight real experiments with a measured timeline: minimum and maximum duration/gap clamping proven from tonechange timestamps, replacing the buffer mid-playout, cancelling with insertDTMF(""), the 2-second comma, lower-case normalisation, InvalidCharacterError, and InvalidStateError before negotiation.

why it is being removed

The method does not exist in the WebRTC specification and Blink is the only engine that ever shipped it, so code using it only ever worked in Chromium. Removing it is part of Interop 2026 (WPT webrtc/historical.html asserts the method is absent). Usage is very low and the migration is mechanical: Chromium's implementation simply looked up the RTCRtpSender for the track and returned its .dtmf, so pc.getSenders().find(s => s.track === track).dtmf is behaviourally identical. The rollout is to all users, with no origin trial or kill switch announced; enterprise admins were notified from Chrome 154.

the API surface

// Removed in Chrome 160 (non-standard, Blink-only):
partial interface RTCPeerConnection {
  RTCDTMFSender createDTMFSender(MediaStreamTrack track);   // gone
};

// Standard replacement (webrtc-pc):
partial interface RTCRtpSender {
  readonly attribute RTCDTMFSender? dtmf;   // null for video senders
};
interface RTCDTMFSender : EventTarget {
  undefined insertDTMF(DOMString tones,
                       optional unsigned long duration = 100,      // clamped 40–6000 ms
                       optional unsigned long interToneGap = 70);  // clamped 30–6000 ms
  attribute EventHandler ontonechange;
  readonly attribute boolean canInsertDTMF;
  readonly attribute DOMString toneBuffer;
};
interface RTCDTMFToneChangeEvent : Event { readonly attribute DOMString tone; };

// Migration:
const sender = pc.addTrack(audioTrack, stream);    // keep this reference
sender.dtmf.insertDTMF("1234#", 100, 70);
