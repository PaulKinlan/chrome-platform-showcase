How it works

  1. buildChain(depth) constructs depth nested <nest-layer> custom elements. Each layer creates an open shadow root, names its own badge nest-node-<k>, and mounts layer k + 1 inside its shadow tree.
  2. When Include all intermediate shadow roots is unchecked, only the first and last roots are passed in shadowRoots. Per Chromium’s view_transition_style_tracker.cc, participation does not cascade automatically to nested shadow roots, so middle nodes are skipped.
  3. Toggling Toggle Popover layer opens a top-layer [popover] hosting an independent <nest-layer> (popover-chip) and adds its shadow root to the array.
  4. Arming Inject duplicate view-transition-name adds nest-node-1 to a visible light-DOM node. When layer 1’s shadow root is also listed, both names collide in one shared namespace and transition.ready rejects with InvalidStateError.

Findings

Chromium’s implementation in view_transition_style_tracker.cc populates a flat set of participating tree roots from the scope tree plus each explicitly listed ShadowRoot. Two practical consequences follow directly from that design:

  • No transitive discovery: listing an outer component’s shadow root does not opt in nested shadow trees inside it. Deep component hierarchies (depth 1–8 here) must collect and pass every participating root explicitly.
  • Single flat name namespace: once a shadow root is listed, its view-transition-name declarations share one namespace with the document and every other listed root. A duplicate name across trees aborts the transition instead of scoping per tree.
  • Browser verification status: pre-160 builds (Chrome for Testing 153 and Chromium 157, checked 2026-11-22) do not read shadowRoots. Capture latency across depths 1–8 with ViewTransitionShadowRoots enabled is not verified in Chrome 160 here; run the harness in Chrome 160+ (or Canary with --enable-blink-features=ViewTransitionShadowRoots) to record live performance.now() latency in the table above.
