Voice-activity leak

SRTP has always encrypted your voice. It never encrypted the RTP header extension that says how loud each packet is: urn:ietf:params:rtp-hdrext:ssrc-audio-level (RFC 6464), which is what powers RTCRtpReceiver.getSynchronizationSources()[i].audioLevel and every “who is speaking” indicator. Two real calls run side by side here, one negotiated with cryptex and one without. Your app sees identical levels in both — the difference is whether anyone on the network path can read them too.

what this proves, and what it cannot

The page can prove, from the real descriptions, which call negotiated a=cryptex and which extension id carries ssrc-audio-level; and from the real receivers, that the level reaches the app either way. A web page cannot see the packets on the wire, so the “readable by an on-path observer” line is a consequence of RFC 6464 + RFC 9335, not a capture. To see it yourself, record chrome://webrtc-internals RTP dumps or a packet capture of a real call: without cryptex, one-byte extension id N with the level is visible after the 0xBEDE profile; with cryptex the profile becomes 0xC0DE and the block is ciphertext.

The same encryption covers the CSRC list: when an SFU or mixer forwards audio, CSRCs identify the contributing speakers (getContributingSources()). In this direct two-peer call that list is empty: —.
