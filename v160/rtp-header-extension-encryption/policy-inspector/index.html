Policy inspector

The whole web-facing surface of this feature is one RTCConfiguration member: rtpHeaderEncryptionPolicy, an enum of "disable", "negotiate" (the default) and "require". This page constructs real RTCPeerConnections with each value, reads back getConfiguration(), tries to change the policy with setConfiguration() (the spec says that must fail), and counts the a=cryptex lines in each real offer.

Flag. Blink runtime feature RtcRtpHeaderEncryptionPolicy (status experimental in runtime_enabled_features.json5; Finch name RtcRtpHeaderEncryptionPolicy). If the probe below says unsupported, enable chrome://flags/#enable-experimental-web-platform-features and relaunch, or launch Chrome with --enable-blink-features=RtcRtpHeaderEncryptionPolicy, or --enable-features=RtcRtpHeaderEncryptionPolicy, or --enable-experimental-web-platform-features. ChromeStatus lists it as enabled by default in Chrome 160 desktop and Android.

1 · Is the member really implemented?

An unknown dictionary member is silently ignored, so a constructor that does not throw proves nothing. Support here means: the value is reflected by getConfiguration() and an invalid value is rejected with TypeError.

3 · The policy is fixed at construction

The spec adds a step to set the configuration: if rtpHeaderEncryptionPolicy differs from the old configuration, fail (InvalidModificationError), the same rule as rtcpMuxPolicy. Choose a starting policy and a new one, then try it.

what this shows

The explainer's code sample is just new RTCPeerConnection(): header-extension encryption is offered by default and falls back to cleartext when the other side does not support it, so most apps change nothing. The inspector exists for the cases where you do care: auditing what your build actually offers, checking whether "disable" (added to the enum after the first implementation) is accepted yet, and proving a policy cannot be weakened after construction.
