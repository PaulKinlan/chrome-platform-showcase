RTP Header Extension Encryption

WebRTC has always encrypted the audio and video payload with SRTP but left the RTP header in the clear, including its header extensions (per-packet audio level, media id, transport sequence numbers) and the contributing-source (CSRC) list that says whose voices were mixed. Chrome 160 implements RFC 9335, "cryptex", which extends the same SRTP encryption to cover those fields. It is negotiated with one SDP line, a=cryptex, and controlled by one new RTCConfiguration member, rtpHeaderEncryptionPolicy: "disable", "negotiate" (the default, which falls back to cleartext against peers that do not support it) or "require".

Try it today: the Blink runtime feature is RtcRtpHeaderEncryptionPolicy (experimental). Enable chrome://flags/#enable-experimental-web-platform-features, or launch with --enable-blink-features=RtcRtpHeaderEncryptionPolicy, --enable-features=RtcRtpHeaderEncryptionPolicy or --enable-experimental-web-platform-features. Every page probes the real surface and says plainly when the member is being ignored.

concepts

  1. Loopback negotiation lab

    The canonical use. Two real peer connections in one tab with a live audio track; pick each side's policy, connect, and read the highlighted a=cryptex lines in the actual offer and answer. A one-click matrix runs all caller × callee pairings as real exchanges.

  2. Policy inspector

    Inspection tooling for the exact surface: a support probe that cannot be fooled by an ignored dictionary member (reflection via getConfiguration() plus TypeError on a bad value), per-value acceptance (shows whether the later-added "disable" is in your build), the offer each policy produces, and proof that setConfiguration() cannot change the policy.

  3. Voice activity leak

    The practical reason it exists. A real call where you "talk" with a tone and watch the per-packet ssrc-audio-level the receiver decodes: the timeline anyone on the path could draw without cryptex. Compare cryptex, a legacy peer, and the alternative mitigation of removing the extension with setHeaderExtensionsToNegotiate().

  4. Require gate

    Failure modes and downgrade. Strip a=cryptex from the offer or answer in transit and see "negotiate" connect silently in cleartext while "require" rejects in setRemoteDescription() with InvalidAccessError, with a step log showing exactly where.

use-case portfolio

  • Basic / canonical: loopback-negotiation.
  • Inspection tooling: policy-inspector.
  • Practical product use: voice-activity-leak (active-speaker metadata privacy).
  • Edge / failure / migration: require-gate (downgrade, legacy peers, InvalidAccessError).
  • Advanced composition: voice-activity-leak composes the policy with RTCRtpTransceiver.setHeaderExtensionsToNegotiate() and RTCRtpReceiver.getSynchronizationSources(). CSRC encryption specifically is not demonstrated: browsers never send CSRCs themselves (they are written by mixers/SFUs), so a browser-only loopback cannot produce them. Source: RFC 9335 §1 and the explainer.

the surface

// webrtc-extensions
enum RTCRtpHeaderEncryptionPolicy { "disable", "negotiate", "require" };
partial dictionary RTCConfiguration {
  RTCRtpHeaderEncryptionPolicy rtpHeaderEncryptionPolicy = "negotiate";
};

// Default: offer cryptex, fall back to cleartext. No code change needed.
const pc = new RTCPeerConnection();

// Only talk to peers that encrypt header extensions:
const strict = new RTCPeerConnection({ rtpHeaderEncryptionPolicy: "require" });
// setRemoteDescription() rejects with InvalidAccessError if a=cryptex is absent.
