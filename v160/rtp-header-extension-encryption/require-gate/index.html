Require gate

"negotiate" quietly falls back to cleartext header extensions when the other side does not say a=cryptex. That fallback is also what a tampering signalling server would exploit: delete one SDP line and the call still connects, just less private. "require" closes that gap: the spec adds a check to setRemoteDescription() that rejects with InvalidAccessError when the remote description does not offer cryptex. Tamper with the SDP below and watch where each policy stops.

when to use require

Only when every endpoint you talk to is known to support cryptex: your own SFU, or browsers you control. Against the general WebRTC ecosystem it turns a privacy improvement into a connection failure. A middle path is to keep "negotiate" and check the remote description for a=cryptex yourself, warning the user (or refusing in app logic) when it is missing.
