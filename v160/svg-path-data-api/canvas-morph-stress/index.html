How it works

  1. Two synthetic shapes — a star built with L segments and a scalloped ring built with elliptical arcs (A) and quadratics (Q) — are generated on offscreen <path> nodes and normalized with getPathData({ normalize: true }).
  2. Because { normalize: true } expands arcs into multiple cubics, raw segment counts differ between shapes. Both arrays are converted to cubics (L → C) and subdivided via de Casteljau splitting until both hit the chosen target count (64, 256, 512, or 1,024).
  3. Each frame interpolates the normalized arrays, calls svgTarget.setPathData(blended), and constructs new Path2D(svgTarget.getAttribute("d")) to paint the matching frame onto Canvas 2D.
  4. When prefers-reduced-motion: reduce is active, Play switches to discrete quarter-step updates instead of continuous 60 Hz oscillation.

Findings

  • Arc expansion under normalization: calling getPathData({ normalize: true }) converts each A segment into one or more C segments, so segment indices and counts change relative to the authored d string and must be equalized before morph interpolation.
  • Per-frame allocation pressure: setPathData() takes a fresh sequence of { type, values } plain dictionaries (1,024 objects + 1,024 six-float arrays per frame at the top stress tier) and serializes back to the d attribute, which new Path2D(d) then re-parses for Canvas 2D.
  • Browser verification status: Chrome 153 behind --enable-blink-features=SVGPathDataAPI verified getPathData/setPathData (without getPathSegmentAtLength) on 2026-11-22. Default-enabled Chrome 160 frame-time measurements at 64–1,024 segments are not verified in Chrome 160 in this authoring environment; run the controls above in Chrome 160+ (or Firefox 137+) to measure live frame times on your hardware.
