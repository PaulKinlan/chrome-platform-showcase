Connect data probe

When a page calls new SharedWorker(), the worker receives a connect event: a MessageEvent whose ports[0] talks back to that page. The HTML spec's run a worker and SharedWorker constructor steps fire it with data initialised to the empty string. Chromium used to leave it null; Chrome 160 changes it to "", matching Firefox and Safari. This page starts a real shared worker and prints every field of the event it actually received.

1 · Start a fresh shared worker and read its connect event

Each click uses a new worker name, so a brand-new instance starts and fires a brand-new connect event. The worker snapshots the event synchronously in its listener and posts the snapshot back over e.ports[0].

2 · Why "" and not the MessageEvent default?

The MessageEventInit dictionary defaults data to null, so a script-constructed new MessageEvent("connect") has data === null. The empty string comes specifically from the browser-fired event's initialisation. This button constructs one in this page and one inside the worker for comparison.

what to do in your code

Do not read e.data in a connect handler at all: it carries no payload. Branch on e.type (or use separate connect and message listeners) and take the port from e.ports[0]. Code that used e.data === null to tell connects from messages will stop matching in Chrome 160; the legacy sniffing audit runs ten such patterns against the real event.

// worker.js
self.addEventListener("connect", (e) => {
  const port = e.ports[0];      // always present
  // e.data === "" in Chrome 160+, Firefox, Safari; null in older Chromium
  port.onmessage = (m) => handle(m.data);
});
