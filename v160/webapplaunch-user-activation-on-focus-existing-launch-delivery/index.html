WebAppLaunch: user activation on focus-existing launch delivery

Installed web apps can declare "launch_handler": {"client_mode": "focus-existing"} so that a click on a shortcut, file, link or share brings the existing window forward instead of opening a duplicate, and the target URL arrives as LaunchParams on window.launchQueue. Until now that consumer ran with no user activation, so it could not call window.open() or requestFullscreen(), even though a user action caused the launch. Chrome 160 grants transient user activation to the window at delivery, the same as a click on a page's own Notification. Apps can now keep one window per workspace and still open a separate one when a launch belongs elsewhere.

Where it can be observed: only in an installed app window launched from the OS (desktop Chrome, and Android where launch handling is supported). A browser tab never receives launches, so the pages label that part as manual observation and show the activation mechanics with real clicks instead. ChromeStatus Finch name: WebAppLaunchHandlerUserActivation (browser-side; not a Blink runtime feature; no entry found in Chromium's feature lists on main at research time). If your build has it off, --enable-features=WebAppLaunchHandlerUserActivation is the conventional switch for a Finch feature of that name, unverified here.

concepts

  1. Workspace app

    The real thing, ready to install: a manifest with focus-existing and three workspace shortcuts, and a consumer that opens a separate window when a launch targets another workspace. Every real delivery is logged with isActive and the actual window.open() result; an in-tab rehearsal (clearly marked simulated) shows both activation states.

  2. Activation inspector

    Inspection tooling: the Launch Handler surface in your browser (launchQueue, LaunchParams, display mode), a registered consumer, a live navigator.userActivation readout, a real expiry timer and a consumption test.

  3. Activation-gated APIs

    Edge cases: run window.open(), requestFullscreen(), showPicker() and vibrate() immediately, after expiry, or after another call consumed the activation, and record the real outcomes. These are the rules a launch consumer now lives by.

use-case portfolio

  • Basic / canonical: workspace-app (the ChromeStatus scenario: open a separate window for a different workspace).
  • Inspection tooling: activation-inspector.
  • Practical product use: workspace-app, with a switch-in-place fallback when window.open() is blocked.
  • Edge / failure / migration: activation-gated-apis (expiry, consumption, the one-call budget) and the pre-160 rehearsal in workspace-app.
  • Advanced composition: not built as a separate page. The natural composition, file_handlers or share_target launches delivered with activation, needs an installed app with OS file associations that cannot be exercised or verified from a page. The workspace app's manifest shows where those members would go. Source: Web App Launch explainer, "launch_handler" and the file handling integration notes.

the pattern

// manifest.json
"launch_handler": { "client_mode": "focus-existing" }

// app window
launchQueue.setConsumer((params) => {
  const ws = new URL(params.targetURL).searchParams.get("workspace");
  if (ws === currentWorkspace) return showInPlace(params.targetURL);
  // Chrome 160: the launch counts as a user activation here.
  const win = window.open(params.targetURL, `workspace-${ws}`);
  if (!win) switchInPlace(params.targetURL); // older builds: popup-blocked
});
