User Agent Image Replacement API

Browsers are starting to replace images on the user's behalf — think a generative-AI "virtual try-on" that swaps a product photo for a render of you wearing the jacket. When that happens, surrounding page content (model dimensions, zoom widgets, size captions) can suddenly be wrong. This API lets the page observe replacement: two new HTMLImageElement events — uareplacestart and uareplaceend — plus a readonly boolean replacedByUserAgent, so authors can adapt the document while the user agent's substitute content is showing.

Chrome 152 status — proposed, nothing to flip in stable yet: the surface is gated behind the Blink runtime feature UAImageReplacementAPI (runtime_enabled_features.json5; it also names the origin trial: origin_trial_feature_name: "UAImageReplacementAPI", Intent to Experiment targets Chrome 152–157 desktop). There is no dedicated chrome://flags entry, and because the runtime feature has no status field, --enable-experimental-web-platform-features does not enable it either. To exercise it for real you need a Chrome build that contains the implementation (Canary/Dev in the 152 timeframe) launched with --enable-blink-features=UAImageReplacementAPI, or an origin-trial token once the trial opens. Every demo below probes the real surface first and reports exactly what it found; where the real UA-initiated path is unavailable, interactions use clearly-labelled synthetic dispatch that exercises your page-side handler code — never a faked browser replacement.

concepts

  1. Surface Probe

    The canonical feature check: does HTMLImageElement.prototype expose replacedByUserAgent, onuareplacestart, and onuareplaceend? Runs the exact IDL probes, prints property descriptors (readonly accessor vs event-handler pair), reads the live value off a real in-page <img>, and checks the explainer's rejected :replaced-by-user-agent pseudo-class alternative too.

  2. Try-On Storefront

    The explainer's e-commerce use case, working end-to-end: a product card whose zoom control and model-dimension caption are driven by real uareplacestart/uareplaceend listeners, with a labelled synthetic-dispatch control standing in for the user-initiated browser feature — plus the analytics feed the explainer says sites want, timing how long the substitute content was showing.

  3. Replacement Monitor

    The document-level tracking pattern the explainer recommends, as an inspection tool: a capturing listener on document watches a whole grid of images at once, and a side-by-side capture-phase vs bubble-phase counter proves why capture is required — Chromium creates these events non-bubbling (Event::Create in html_image_element.cc).

  4. Resilient Adoption

    Edge cases and safe patterns for code that must run everywhere today: undefined vs false on unsupported browsers, why addEventListener can never be a feature probe, the missed-event race that makes the readonly catch-up property necessary, and a hands-on look at the anti-fingerprinting guarantee — there is deliberately no author API to trigger or enumerate replacements.

why it shipped

A Chrome feature that offers user-initiated image replacement heard the same feedback from multiple websites: when the browser swaps an image, the page around it stops making sense — a "model is 6'1", wears size M" caption under a render of the visitor, or a zoom widget that magnifies the original photo. Sites also want to know, for their own analytics, how users of these features browse and buy. The proposal keeps the API deliberately tiny — two events and a readonly boolean on HTMLImageElement — so it degrades to existing behavior everywhere else, and keeps the user agent in control of privacy: replacement content is never exposed to the page, pages cannot trigger replacement, and the events only fire on explicit user intent, so the surface cannot be used to probe what the browser is capable of.
