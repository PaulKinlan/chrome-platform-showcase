Invoke the real window.subApps.add(), list(), and remove() surfaces, read the genuine outcome in this context, and learn the honest difference between "API absent" and "API present but this context is not eligible".

What this API needs before it will ever resolve

  • Chrome 152+ on desktop (Windows / macOS / Linux / ChromeOS). The Blink runtime feature SubApps is enabled by default in 152; on older builds relaunch with --enable-features=SubApps. ChromeStatus lists a chrome://flags/#enable-sub-apps entry, but current Chromium main has no such flag — the command-line switch is the reliable path.
  • An installed Isolated Web App. The IDL gates exposure with [IsolatedContext], so window.subApps is undefined in every normal tab — including this page — even in Chrome 152. To develop an IWA locally enable chrome://flags/#enable-isolated-web-app-dev-mode and install a signed bundle (or a dev-mode proxy) from chrome://web-app-internals.
  • The sub-apps permissions policy granted to the top-level document (default allowlist is self; a served header like Permissions-Policy: sub-apps=() revokes it and every call rejects with SecurityError).
  • A primary top-level browsing context. Iframes, fenced frames, prerendering pages, and sub-app windows themselves are rejected with NotSupportedError.

how to read the outcome

  • API absent, normal tab (this page): the property read yields undefined and the call throws TypeError. Expected in every browser here — it proves nothing about Chrome's version.
  • API absent inside an isolated-app:// window: that is the real "not supported" signal — Chrome < 152, or the SubApps feature disabled. Relaunch with --enable-features=SubApps.
  • API present but the call rejects: read the DOMException — SecurityError means the sub-apps permissions policy is missing; NotSupportedError means a non-eligible context (sub-app frame, removed app, not top-level); NotAllowedError means the user declined the install prompt.
