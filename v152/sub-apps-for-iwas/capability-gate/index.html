v152 · sub apps for iwas

Capability & context gate

In Chrome 152 the Sub Apps API is enabled by default — but the interface is declared [Exposed=Window, SecureContext, IsolatedContext], so window.subApps still only binds inside a secure Isolated Web App (an isolated-app:// origin) that holds the sub-apps permission policy. This probe checks each prerequisite live and tells you exactly which one is stopping the API here — instead of blaming your browser version.

To actually run Sub apps in Chrome 152: no feature flag is needed (the SubApps runtime feature is stable). You need an installed Isolated Web App — end-user available on ChromeOS; for development enable #enable-isolated-web-apps and #enable-isolated-web-app-dev-mode in chrome://flags, then install the bundle via chrome://web-app-internals. Inside that IWA the page's origin is isolated-app://<bundle-id> and window.subApps is defined. On this ordinary https:// origin it is undefined by design.

what each gate measures

  • Secure context — window.isSecureContext. [SecureContext] interfaces never bind on insecure pages.
  • isolated-app:// scheme — location.protocol. An installed IWA's documents live on the isolated-app: scheme; an https: page can never be an isolated context, so this read tells you why the binding is absent here.
  • Isolated-context binding — 'subApps' in window. The interface is [IsolatedContext]-gated, so its mere presence proves you are inside an IWA. (Early explainer drafts hung the API off navigator; the spec puts it on Window — the probe reports both reads.)
  • Permission policy — document.featurePolicy.allowsFeature('sub-apps') when that introspection API exists. add() / remove() / list() all reject with SecurityError when the policy is missing.
  • Live method call — an actual window.subApps.list(). We surface its resolved value or the exact exception, never a fabricated result.
