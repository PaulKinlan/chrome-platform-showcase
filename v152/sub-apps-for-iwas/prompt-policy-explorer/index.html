v152 · sub apps for iwas

Prompt & policy explorer

Installing apps programmatically is powerful, so Chrome wraps subApps.add() in two consent layers: the call must be made with a user gesture (transient activation) and it shows a unified confirmation prompt — rejecting with NotAllowedError if the user declines. On managed ChromeOS (150+), three enterprise policies tune or waive that prompt per IWA origin. This page probes the real gates it can reach from here, then resolves the documented policy precedence for any origin you enter.

What is real on this page: the binding probe and the navigator.userActivation reads are live platform calls. The policy resolver evaluates the documented semantics from the Chromium policy definitions (ContentSettings/DefaultSubAppsWithoutPromptsSetting.yaml and friends) — a page cannot read a managed browser's actual policy values, so the resolver is labelled as documentation-driven, never as a live enterprise state.

Policy values (as an admin would set them)
Choose policy values, then resolve. The default scenario puts the calling origin on the allow list, so add() would skip the prompt.

the three policies (ChromeOS 150+, from the Chromium policy definitions)

DefaultSubAppsWithoutPromptsSetting
Global default for all IWAs. 1 = add without prompt (also bypasses the gesture requirement), 2 = block adding, 3 or unset = allow with user confirmation.
SubAppsWithoutPromptsAllowedForOrigins
List of isolated-app:// origins that may add sub apps without the prompt. Overrides the default setting.
SubAppsWithoutPromptsBlockedForOrigins
List of origins that must always show the prompt. Overrides both the default setting and the allow list.

Separately, SubAppsAPIsAllowedWithoutGestureAndAuthorizationForOrigins (ChromeOS 123+) can waive the transient-activation and confirmation requirements for listed origins.
