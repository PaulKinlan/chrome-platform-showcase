Sub apps for IWAs

Sub apps let one Isolated Web App install several distinct apps — each with its own name, icons, shelf identity and OS integrations — under a single install and update process. Chrome 152 is the milestone where the API (window.subApps.add(), list(), remove()) is enabled by default: the blink runtime feature SubApps is now stable, so no #enable-sub-apps flag is needed. The gate that remains is the interface itself — [Exposed=Window, SecureContext, IsolatedContext] — so it only binds inside an installed Isolated Web App at an isolated-app:// origin with the sub-apps permission policy. These demos call the real API and honestly report which prerequisite is missing when it is not met.

why it shipped

A large Isolated Web App can be a whole suite — mail, docs, sheets — but users expect each of those to be a first-class app with its own icon, window and file-type associations, not one monolithic entry point. Sub apps let a single signed IWA bundle present those as separate installable apps while keeping one unified install, update and trust boundary. Chrome 152 turns the API on by default for IWAs, adds spec-level quotas (at most 20 installs per add() call and 50 sub apps per parent), and pairs it with three enterprise policies (DefaultSubAppsWithoutPromptsSetting, SubAppsWithoutPromptsAllowedForOrigins, SubAppsWithoutPromptsBlockedForOrigins, ChromeOS 150+) so admins control whether the install confirmation prompt is shown.

running it for real

In Chrome 152 the API needs no feature flag — the SubApps runtime feature is stable. What it does need is an Isolated Web App context: the interface is [SecureContext, IsolatedContext], so window.subApps only exists on an installed IWA's isolated-app:// origin that has the sub-apps permission policy. IWAs are end-user available on ChromeOS; for development, enable #enable-isolated-web-apps and #enable-isolated-web-app-dev-mode in chrome://flags, then install your bundle from chrome://web-app-internals (“Install IWA from Update Manifest” or the Dev Mode Proxy). Calls also require a prior user gesture (transient activation) and show a confirmation dialog unless an enterprise policy waives it. On an ordinary https:// origin like this one, window.subApps is undefined by design — the demos report that honestly rather than faking a result.
