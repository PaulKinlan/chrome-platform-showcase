Clear vs Encrypted + Rejection Lab

The spec is precise about the edges: a clear query must still carry keySystemAccess: null; the empty-string scheme is not the same as null; and malformed configurations must reject with TypeError, while keySystemConfiguration inside a worker rejects with InvalidStateError. Every probe below runs the real call and reports the real observed outcome next to the spec's expectation — a mismatch is shown as a mismatch.

Availability. encryptionScheme filtering is enabled by default from Chrome 152 (earlier: --enable-blink-features=KeySystemTrackConfigurationEncryptionScheme, or chrome://flags/#enable-experimental-web-platform-features / --enable-experimental-web-platform-features; builds predating the flag drop the member regardless). The rejection contracts probed here are older spec text and hold on any browser with decodingInfo(). This sandbox/headless Chromium has no Widevine CDM, so probes use ClearKey, which ships inside Chromium.

clear vs encrypted contrast

Same VP9 stream queried twice: once with no keySystemConfiguration (clear playback), once with ClearKey + encryptionScheme: "cenc". Per spec both results must carry all of supported, smooth, powerEfficient, and keySystemAccess — null for the clear query, a real MediaKeySystemAccess when the encrypted query is supported.
