Codec string support matrix

IAMF §6.3 defines the RFC 6381 codecs parameter as iamf.PPP.AAA.<codec> — PPP/AAA are the primary/additional profile as exactly three digits (000–255), and the trailing element is the substream codec: Opus, mp4a.40.2, fLaC, or ipcm. This matrix asks three different capability APIs about the same strings — including strings the grammar requires every browser to reject — and prints each API's raw answer.

Availability: IAMF decode targets Chrome 152 (desktop, Android, WebView) behind the IamfAudioDecoding media feature. There is no chrome://flags entry and no Blink runtime feature; if every valid row below reports unsupported, relaunch with --enable-features=IamfAudioDecoding — and note it also needs a Chrome build compiled with IAMF support (GN arg media_use_iamf_tools or enable_platform_iamf_audio), so builds without the decoder cannot turn it on at runtime.

how to read the three answers

canPlayType() is the HTMLMediaElement file-playback question and answers "" / "maybe" / "probably". MediaSource.isTypeSupported() is the MSE question — the pipeline IAMF actually ships through in Chrome 152 — and answers a hard boolean. decodingInfo() (Media Capabilities) answers supported plus performance hints. Note its two distinct failure shapes, both real and observable here: a grammar-invalid IAMF codecs string still parses as a MIME type, so it resolves with supported: false in every browser — while a configuration that is malformed at the dictionary level (like the muxed audio+video string passed as an AudioConfiguration) rejects with a TypeError.

code path

audio.canPlayType('audio/mp4; codecs="iamf.000.000.Opus"');
MediaSource.isTypeSupported('audio/mp4; codecs="iamf.000.000.Opus"');
await navigator.mediaCapabilities.decodingInfo({
  type: "media-source",
  audio: { contentType: 'audio/mp4; codecs="iamf.000.000.Opus"' },
});
