Enterprise Policy Lab

Two existing policies decide whether a managed user can ever see the new warning: SafeBrowsingProtectionLevel picks the protection tier, and SafeBrowsingAllowlistDomains exempts whole domains from Safe Browsing checks. Set both below against a test URL and trace the outcome — including the edge cases that surprise admins.

This lab executes the documented policy semantics client-side so you can explore them. Page JavaScript cannot read your browser's real policy values — verify those at chrome://policy (copy button below; chrome:// URLs cannot be opened from a web page link).

model a managed fleet

    verify on a real managed machine

    chrome://policy

    Open it in a new tab (paste into the omnibox) and search for SafeBrowsing to see the actual applied values and their source (platform, cloud, merged).

    // Example policy JSON (Linux /etc/opt/chrome/policies/managed/safebrowsing.json)
{
  "SafeBrowsingProtectionLevel": 2,
  "SafeBrowsingAllowlistDomains": ["intranet.example.com", "partner-portal.example"]
}

    edge cases worth knowing

    • Level 0 silences everything. It does not just remove the new pop-up — confirmed-threat red interstitials and download protection go too. Forcing 0 to "stop warning noise" removes real protection.
    • Level 1 already excludes this feature. The suspicious pop-up is Enhanced-protection-only, so a Standard-protection fleet never sees it — no allowlisting needed.
    • Allowlist matching is by domain suffix. example.com covers foo.example.com, but intranet.example.com does not cover example.com. Entries are hostnames, not URL patterns.
    • Allowlisting is total, not warning-specific. An allowlisted domain skips Safe Browsing checks entirely — if it gets compromised, users get no interstitial either.
