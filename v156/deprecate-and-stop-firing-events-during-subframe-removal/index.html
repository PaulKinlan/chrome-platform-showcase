Deprecate and stop firing events during subframe removal

When you remove an <iframe> from the DOM, Chrome — like Firefox and Safari — has always run the frame's pagehide, visibilitychange and unload handlers synchronously, in the middle of your removal call, while the iframe is still connected. The HTML Standard's "destroy a child navigable" fires none of them. Behind OmitSubframeDetachmentEventsOnRemoval, Chrome stops firing them, so a subframe that can script its ancestors can no longer re-enter and mutate the parent's DOM mid-removal. Navigating a frame still fires pagehide as before.

Try the new behaviour: launch Chromium 156 or later (Canary/Dev) with --enable-blink-features=OmitSubframeDetachmentEventsOnRemoval (equivalently --enable-features=OmitSubframeDetachmentEventsOnRemoval). There is no chrome://flags entry, and --enable-experimental-web-platform-features does not enable it. Every demo below detects the behaviour your browser actually has by removing a real probe frame — never from the version number.

concepts

  1. Removal event probe

    The canonical experiment: a same-origin iframe with all three listeners, iframe.remove(), and a sequence-numbered trace showing which events fired, in what order, whether they ran inside the call, and that frameElement.isConnected was still true while they did. Plus an opaque-origin sandbox="allow-scripts" contrast reported over a MessagePort with wall-clock timing.

  2. Detachment timeline explorer

    Inspection tool: choose listeners, nesting depth (up to three levels), origin, and the removal path — remove(), removing an ancestor, replaceChildren(), innerHTML, textContent, replaceWith(), an insertBefore() "move" — against the two contrasts that must not change: moveBefore() and navigating the frame.

  3. Cleanup that survives silent removal

    The product case and the migration: a draft-saving widget closed by its host with three strategies — legacy save-in-pagehide, a host-driven teardown handshake, and save-as-you-type — showing which drafts survive in your mode, a heartbeat proving a removed frame can never notice its own removal later, and the allow="unload 'none'" Permissions Policy contrast.

  4. Re-entrancy hazards during removal

    Edge and failure cases, run for real: a handler that re-inserts its own iframe (the caller's remove() throws and leaves a connected iframe with no browsing context), removes itself first, deletes a sibling, detaches the container running replaceChildren(), or reads a container while innerHTML = '' is mid-flight.

why it is changing

Blink dispatched the three events from Document::DispatchUnloadEvents while detaching a removed frame (FrameDetachType::kRemove), inside ContainerNode::RemoveChild. Script in a subframe that can access an ancestor's DOM could therefore mutate that DOM during node removal — a source of crashes and inconsistent DOM state — and it contradicts the HTML Standard, which destroys a removed child navigable silently (whatwg/html#10194). A compatibility study over the October 2026 HTTP Archive crawl plus 367 live mobile pages found 0 user-facing breakage: the handlers that do run on removal are mostly invisible telemetry beacons or benign cleanup (Auth0 lock release, Google Publisher Tags slot disposal, YouTube player state). To keep churn minimal, ChromeStatus scopes the change to subframes that can script an ancestor (SecurityOrigin::CanAccess on any ancestor), about 0.026% of mobile pages; checking only the parent would miss an A1 → B → A2 cross-site sandwich.

the exact surface

// Legacy (default Chrome, Firefox, Safari): these run INSIDE remove()
// child frame (same-origin with the host):
addEventListener('pagehide', (e) => { /* e.persisted === false */ });
document.addEventListener('visibilitychange', () => { /* visibilityState 'hidden' */ });
addEventListener('unload', () => { /* only where Permissions Policy allows unload */ });

// host page — any DOM removal path detaches the frame (FrameDetachType::kRemove):
iframe.remove();  wrapper.remove();  container.replaceChildren();
container.innerHTML = '';  container.textContent = '';  iframe.replaceWith(x);
other.insertBefore(iframe, null);   // a remove + insert: detaches and reloads

// With OmitSubframeDetachmentEventsOnRemoval: none of the listeners above run.
// Unchanged in both modes:
other.moveBefore(iframe, null);     // atomic move: no detach, no events, no reload
iframe.srcdoc = '…';                // navigation: pagehide/visibilitychange/unload still fire
