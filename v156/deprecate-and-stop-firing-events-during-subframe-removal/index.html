v156 · DOM · deprecation (developer trial, behind a flag)

Deprecate and stop firing events during subframe removal

When script removes an <iframe> (or <object>/<frame>) from the DOM, Chrome today runs the child document's pagehide, visibilitychange and unload handlers synchronously, inside the removal call. A same-origin child can then reach back into the parent's DOM while the parent is half-way through mutating it. The HTML Standard's destroy a child navigable fires none of these events, and Chrome is deprecating the behaviour for subframes that have script access to an ancestor's DOM.

Behind a flag, not shipped. ChromeStatus: developer trial from M156 and a deprecation trial planned for M160–M162. The Blink runtime flag is OmitSubframeDetachmentEventsOnRemoval (status test in runtime_enabled_features.json5), so --enable-experimental-web-platform-features does not turn it on, and there is no chrome://flags entry. To try the new behaviour, launch Chrome with --enable-blink-features=OmitSubframeDetachmentEventsOnRemoval. The Finch feature has the same name, so --enable-features=OmitSubframeDetachmentEventsOnRemoval also works. Each concept tells you which behaviour this browser actually showed. It never assumes from the version number.

concepts

  1. Removal event probe

    Basic. One real same-origin iframe and one iframe.remove(), with a timeline of every event the child reports and whether it ran inside the removal call. The page reaches a verdict (deprecated behaviour still active, or events omitted as the spec says) only after a control navigation shows that the child's listeners work.

  2. Removal method matrix

    Inspection tool. Runs ten real teardown paths: remove(), removing an ancestor wrapper, innerHTML = '', replaceChildren(), replaceWith(), <object>, a nested grandchild, an opaque sandbox frame (no ancestor access, so it is outside the deprecation's scope), and two controls (src navigation and moveBefore()). The result is a pass/fail grid of what fired, and when.

  3. Re-entrancy hazard

    Edge / failure mode. This is why the behaviour is going away. A host's "clear all widgets" loop is ordinary code, but a widget's pagehide handler that tidies its container re-enters the parent DOM mid-loop. The loop then throws NotFoundError, leaves stray nodes behind, or reads a half-torn tree. You can see each effect live, and each one disappears when the events stop firing.

  4. Widget teardown migration

    Practical product + migration. An embedded chat widget holds an unsent draft. You can compare three strategies on the same removal: saving in pagehide (the pattern this deprecation breaks), an explicit host→widget teardown handshake over a MessageChannel before removal, and eager save-on-input. The page shows which drafts survived in this browser.

  5. Re-parent with moveBefore()

    Advanced composition. A lot of "removal" is really re-parenting: layout changes, drag-and-drop, docking a player. appendChild() on a connected iframe detaches it, so the widget's teardown events fire and it reloads with its state lost. Element.moveBefore() moves it atomically, with no detach, no events and the state kept. The page counts reloads and events for each approach.

what changes, exactly

Chrome currently dispatches the events from Document::DispatchUnloadEvents when a frame owner element is disconnected (FrameDetachType::kRemove). With the flag on, it omits them when the removed subframe shares an agent with the document the node is removed from (that is, when it could synchronously script the ancestor DOM). Cross-origin out-of-process frames and opaque sandboxed frames keep their teardown handlers in the narrower "Option 2b" scope that the compat study recommends. Navigating a frame is unchanged: pagehide/unload still fire there. A related but separate flag, OmitBlurEventOnElementRemoval, stops blur on a focused element that is removed. The probe shows it but does not count it toward this feature's verdict.

Migration: do not rely on a subframe's pagehide/unload as a removal hook. Have the host tell the embedded document it is about to go (postMessage with an acknowledgement), persist state eagerly as it changes, send telemetry with fetchLater() or on visibilitychange of the top-level page, and use moveBefore() when you only mean to move the frame.
