Removal method matrix

Frameworks rarely call iframe.remove() directly. They clear a container, swap a subtree or replace a node. Each card below runs one real teardown path against a fresh widget frame and records which of pagehide / visibilitychange / unload fired, and whether they fired inside the DOM call. Each observation is matched against the two possible worlds: Chrome's deprecated behaviour and the spec behaviour that the flag enables.

Flag: --enable-blink-features=OmitSubframeDetachmentEventsOnRemoval (status test; no chrome://flags entry; developer trial M156, deprecation trial M160–M162). Two rows are controls whose outcome must be the same in both worlds. If a control disagrees, the harness is broken, and the page says so rather than counting it.

    reading the grid

    In scope rows involve a same-origin subframe, which can script this page's DOM. Under the deprecation their events stop. The opaque sandbox row (sandbox="allow-scripts" without allow-same-origin) cannot touch this page, so it has no re-entrancy risk. The Chromium flag only omits events when the subframe shares an agent with the remover, so this row is expected to keep firing, delivered here asynchronously by postMessage. The compat study calls this narrower scope "Option 2b".
