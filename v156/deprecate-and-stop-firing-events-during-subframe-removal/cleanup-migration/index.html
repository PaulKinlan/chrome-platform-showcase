Cleanup that survives silent removal

The code this change breaks is real: an embedded widget (editor, chat box, ad slot, auth helper) that flushes its state in pagehide or unload when the host page tears it out. Try the same draft-saving widget with three cleanup strategies, close it the way a framework would — iframe.remove() — and see which drafts survive in your browser's current mode.

Behind a flag: to see the strategies diverge, launch Chromium 156+ with --enable-blink-features=OmitSubframeDetachmentEventsOnRemoval (or --enable-features=OmitSubframeDetachmentEventsOnRemoval). In default Chrome all three strategies keep the draft — which is exactly why the legacy one looks safe today.

the migration checklist

  1. The host owns teardown. If the host page knows it is about to remove a frame, it tells the frame first (postMessage({type: 'teardown'}), or a direct call for same-origin), awaits an acknowledgement with a timeout, then removes. This works identically in both modes and in every engine.
  2. Persist incrementally. State that matters (drafts, cart contents, queue positions) is saved when it changes, not at the end of life. Nothing is lost if the frame is destroyed silently, crashes, or is killed in the background.
  3. Keep pagehide for navigation, not removal. Navigating the frame (or the top-level page) still fires pagehide; use it for back/forward-cache friendly cleanup, never unload.
  4. Do not try to detect removal from inside. A removed frame's document is destroyed: its timers stop, so a frameElement?.isConnected watchdog in a later task never runs — the heartbeat counter above stays at 0.
  5. Moving is not removing. If the frame is merely being re-parented, use moveBefore() (feature-detected) so it is never detached — see the timeline explorer.
  6. Telemetry beacons that used detach events should queue with fetchLater() (where available) as data is produced rather than fire at teardown.
