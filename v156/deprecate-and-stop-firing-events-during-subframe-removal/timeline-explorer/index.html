Removal is not one API. Frameworks clear containers with replaceChildren() or innerHTML = '', unmount a wrapper that contains the iframe, or "move" a frame with insertBefore() (which is a remove plus an insert). Pick the listeners, the nesting depth, the frame's origin and the removal method, run it, and read the real event timeline your browser produced — including the two contrasts that must not change: moveBefore() (no detach at all) and navigating the frame (a real unload, which still fires pagehide).

Behind a flag: compare a default launch with --enable-blink-features=OmitSubframeDetachmentEventsOnRemoval (or --enable-features=OmitSubframeDetachmentEventsOnRemoval), Chromium 156+. No chrome://flags entry exists and --enable-experimental-web-platform-features does not turn it on.

what to look for

  • Every DOM-removal path is the same algorithm. remove(), removing an ancestor, replaceChildren(), innerHTML, textContent, replaceWith() and the remove half of insertBefore() all reach Blink's frame detach with FrameDetachType::kRemove — so with the flag, all of them go silent, and in legacy mode all of them fire synchronously.
  • Nested frames are torn down outer-first in legacy mode: the outer document's pagehide/unload run, then each descendant's.
  • moveBefore() never detaches, so no events fire in either mode and the frame keeps its document — the right tool when you only meant to move.
  • Navigation still unloads. Swapping the frame's srcdoc commits a new document, so pagehide (persisted=false), visibilitychange and (where policy allows) unload fire in both modes — Chromium only skips them when the frame is not committing a new document.
