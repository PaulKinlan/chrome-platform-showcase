Widget teardown migration

An embedded chat widget holds a message the user has not sent. When the host page closes the widget by removing its iframe, can the widget still save that draft? Three real widgets use three strategies. The one that waits for pagehide works only while the deprecated behaviour exists. The two replacement patterns work in every browser: the host asks the widget to flush before removal, or the widget saves eagerly.

With --enable-blink-features=OmitSubframeDetachmentEventsOnRemoval (developer trial M156, deprecation trial M160–M162) the pagehide strategy loses the draft. The other two are unaffected. Drafts are stored in this origin's sessionStorage and cleared at the start of each run.

the replacement pattern

// host: ask first, then remove (with a timeout so a hung widget can't block)
async function closeWidget(iframe) {
  const { port1, port2 } = new MessageChannel();
  const acked = new Promise((resolve) => { port1.onmessage = () => resolve(true); });
  iframe.contentWindow.postMessage({ type: 'teardown' }, widgetOrigin, [port2]);
  await Promise.race([acked, new Promise((r) => setTimeout(r, 1000, false))]);
  iframe.remove();
}

// widget: flush on request, not on pagehide
addEventListener('message', (e) => {
  if (e.source !== parent || e.data?.type !== 'teardown') return;
  saveDraft();
  e.ports[0].postMessage({ type: 'teardown-ack' });
});

For analytics or telemetry, send data with fetchLater() when it changes (or on the top-level page's visibilitychange to hidden) rather than from a subframe's unload. The compat study found PayPal and Shop Pay beacons relying on removal-time events.
