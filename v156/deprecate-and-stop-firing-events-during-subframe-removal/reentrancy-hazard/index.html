Re-entrancy hazards during removal

The reason for this change: a same-origin subframe's pagehide handler runs inside the parent's DOM removal, while the iframe is still connected, and it can mutate the very tree being edited. Each experiment below arms a real subframe with a handler that does something hostile to the parent, then performs an ordinary removal. Read what your browser actually ended up with.

Behind a flag: run once in default Chrome and once in Chromium 156+ launched with --enable-blink-features=OmitSubframeDetachmentEventsOnRemoval (or --enable-features=OmitSubframeDetachmentEventsOnRemoval). With the flag the handlers never run, so every removal does exactly what the calling code asked.

why this matters

Every "Expected by the caller" outcome above is what a framework's reconciler assumes: after remove() the node is gone and nothing else moved. In legacy mode a subframe can break that contract from inside the removal — re-parenting a node mid-flight, making the caller's own call throw NotFoundError, deleting nodes the caller still holds, or leaving an iframe that is connected yet has no browsing context. In the engine these same paths have produced crashes and inconsistent DOM state; the compat study found Google Publisher Tags mutating ad-slot state from a friendly frame's pagehide during innerHTML = ''. With the flag, Document::DispatchUnloadEvents returns early for a removed subframe, so none of this can happen.
