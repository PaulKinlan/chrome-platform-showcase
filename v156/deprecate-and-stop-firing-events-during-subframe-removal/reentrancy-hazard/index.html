Re-entrancy hazard

The deprecation exists because a synchronous pagehide in a same-origin subframe lets that frame's code run in the middle of the parent's DOM mutation. In the compat study, Google Publisher Tags' friendly ad iframes ran slot clean-up from pagehide while a host cleared the ad container with innerHTML = ''. Here, a host clears a list of three widgets with ordinary code, and you choose what each widget's teardown handler does. Watch whether the host's invariant ("the list is empty afterwards, and the loop did not throw") survives.

This browser decides the outcome. With the deprecated behaviour (Chrome today) the handlers run inside the host's loop. With --enable-blink-features=OmitSubframeDetachmentEventsOnRemoval they never run on removal, and every scenario below stays clean. The handlers are attached by this page to each widget's window, the way a same-origin "friendly iframe" script would.

why this matters

DOM removal algorithms are written assuming the tree they are walking does not change underneath them. A synchronous event dispatched mid-removal breaks that assumption. Engines have to defend against re-entrancy with scattered special cases, and app code that iterates a snapshot ([...children]) gets NotFoundError when a handler has already removed the next node. The HTML Standard removed these events for exactly this reason, and Chromium follows by omitting them when the removed frame can script an ancestor.
