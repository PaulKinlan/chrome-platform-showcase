Badging & requireInteraction Changes

Attribution changes two existing contracts for installed PWAs on macOS: the Badging API silently no-ops without notifications permission, and app notifications stop honoring requireInteraction (the user's per-app macOS setting decides persistence). This page drives both real API surfaces and reports exactly what happens here.

Behind a flag, macOS only. The behavior changes apply on macOS Chrome 130+ with chrome://flags/#enable-mac-pwas-notification-attribution enabled (--enable-features=AppShimNotificationAttribution) and the PWA installed. On every other platform these APIs keep their previous behavior — the probes below still run for real and report honestly.

1 · Badging API, for real

navigator.setAppBadge() and navigator.clearAppBadge() are called directly — the promise result is reported as-is. A badge is only ever visible on an installed app's icon; under macOS attribution, if notifications permission is not granted the API resolves but the OS shows nothing (the documented silent no-op).

2 · requireInteraction, for real

Constructs a genuine new Notification() with the requireInteraction option and reads the value back off the live object. On most desktops true keeps the notification on screen until dismissed; on macOS with attribution the field is ignored for app notifications — persistence follows the user's per-app alert style (Banners vs Alerts) in System Settings.

code

await navigator.setAppBadge(3);   // resolves; visible only on an installed icon;
                                  // on macOS+attribution: no-op without notification permission
await navigator.clearAppBadge();

const n = new Notification('Build finished', { requireInteraction: true });
n.requireInteraction; // true in the DOM — but ignored by macOS app notifications
