Notification attribution for PWAs on macOS

Installed PWAs on macOS get real citizenship in Notification Center: their notifications carry the app's own name and icon instead of "Google Chrome", and users manage sounds, badges, alerts, and Focus modes per app. Two web-visible contracts change with it, aligning with WebKit: requireInteraction becomes advisory for app notifications (macOS decides persistence per app), and the Badging API is gated on notification permission — setAppBadge() silently does nothing without it.

concepts

  1. Attribution context probe

    Attribution only applies in a specific context: an installed PWA on macOS. This probe reads every relevant signal live — platform, display-mode via a reactive matchMedia listener, Notification support, and the current permission state via the Permissions API with change tracking — and tells you honestly which parts of this feature can even apply where you're standing.

  2. requireInteraction behavior lab

    Fire a real notification with requireInteraction on or off and learn the new contract: the dictionary member still exists everywhere (probed live), but for attributed app notifications macOS ignores it — persistence is the user's per-app choice in System Settings. The one probe that can't lie here is behavior, so the page labels persistence as a manual observation, never a fake pass.

  3. Badge permission gate

    A live Badging API playground — setAppBadge(n) / clearAppBadge() with real promise outcomes — wired to a live notification-permission readout. The new rule: no granted notification permission, no badge; the call succeeds and silently does nothing. The page makes the invisible gate visible.

why it shipped

Every PWA notification used to appear under the "Google Chrome" umbrella in macOS Notification Center — one icon, one settings entry, no way to silence a noisy app without silencing them all, and no Focus-mode integration per app. Attributing notifications to the PWA's app shim gives users the native per-app controls macOS already has, and brings Chrome in line with WebKit's behavior for web apps. The price of native integration is native rules: macOS owns notification persistence (hence advisory requireInteraction) and ties badges to notification authorization (hence the Badging API gate).

enabling it

Rolling out to installed PWAs on macOS (listed in the Chrome 130 dev-trial cycle; rollout completing in Chrome 152). Test path: on macOS, install a PWA (Chrome menu → Cast, save and share → Install page as app), check chrome://flags/#enable-mac-pwas-notification-attribution if the rollout hasn't reached your profile, then grant notification permission and observe Notification Center attributing to the app. Enterprise admins keeping centralized control need the origin-based NotificationsAllowedForUrls policy plus a macOS MDM configuration profile authorizing the PWA's bundle ID.
