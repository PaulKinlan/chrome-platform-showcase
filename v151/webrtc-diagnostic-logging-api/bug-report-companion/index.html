← WebRTC Diagnostic Logging API

v151 · WebRTC

Bug-report companion

When a user reports a broken call, you want the browser's diagnostics and your app's context lined up. Start a session with allowUpload: true so the user can share the log with the browser vendor, attach structured metadata, then finish with closing metadata — finishDiagnosticLogging() also accepts RTCDiagnosticLoggingOptions — and stamp the returned session ID onto your bug report. The spec caps metadata at 5 entries with keys/values ≤ 100 characters on both calls — exceed it and Chromium currently rejects with a RangeError (rtc.cc), while the WICG spec mandates a TypeError — a live spec/implementation divergence this demo surfaces as-is. Chromium measures the limit in UTF-8 bytes, so non-ASCII metadata can trip it sooner than the JavaScript character count below suggests.

The diagnostic logging API is not exposed in this browser.
Neither navigator.rtc (Chrome 151 origin-trial binding) nor RTCPeerConnection.startDiagnosticLogging (spec-draft static) is present. Launch Chrome 151+ with --enable-blink-features=RTCDiagnosticLogging, enable chrome://flags/#enable-experimental-web-platform-features, or register for the origin trial, then reload over HTTPS/localhost. The start button calls the real API and shows exactly what it returns; metadata validation still previews below.

Start a session to generate a bug-report stub.
const rtc = navigator.rtc ?? RTCPeerConnection;  // OT binding vs spec draft

const id = await rtc.startDiagnosticLogging({
  allowUpload: true,               // user may share the log with the vendor
  metadata: {                      // ≤ 5 entries, keys/values ≤ 100 chars
    app: "acme-meet",
    version: "4.7.1",
    callId: "c-88213",
  },
});

// … the problematic call happens …

await rtc.finishDiagnosticLogging({
  metadata: { outcome: "user-reported-freeze", ticket: "ACME-4471" },
});
fileBugReport({ rtcDiagnosticId: id });   // attach ID, like a crash ID
