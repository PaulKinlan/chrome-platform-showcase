WebRTC Diagnostic Logging API

A small API — startDiagnosticLogging(), finishDiagnosticLogging(), cancelDiagnosticLogging() — that lets an authorized app ask the browser to record internal WebRTC diagnostics to a local log file. Logs are never exposed to the page; the app only receives a session ID it can attach to a bug report. Optionally the user can authorize uploading the log to the browser vendor. Chrome 151's origin trial binds it as navigator.rtc; the current WICG draft has since moved it to static methods on RTCPeerConnection — the demos here handle both shapes.

concepts

  1. Logging lifecycle

    Drive the three-state machine with real calls: start returns a UUID session ID, finish finalises the local log, cancel discards it. Watch the session ID appear and the state transition live, with each button enabled only when it's valid to call.

  2. Bug-report companion

    The real-world use case: start a session with allowUpload and structured metadata, then finish with closing metadata — finishDiagnosticLogging() also accepts RTCDiagnosticLoggingOptions — and hand the returned ID to a bug report. Includes the spec's metadata limits — at most 5 entries, each key/value ≤ 100 chars — and shows the RangeError Chromium currently throws when you exceed them (the WICG spec mandates a TypeError; a live spec/implementation divergence).

  3. Capability & policy probe

    Feature-detect both known API shapes — Chrome 151's navigator.rtc origin-trial binding and the current spec draft's RTCPeerConnection statics — and understand the full gate: origin trial or the RTCDiagnosticLogging flag exposes the API, while production deployment additionally needs the enterprise policy WebRtcDiagnosticLogCollectionAllowedForOrigins. Honest reporting — no fake success when the API is absent.

  4. Loopback call capture

    The advanced composition: wrap a real in-page RTCPeerConnection loopback call — offer/answer, ICE, a data channel round trip, live getStats() — in a diagnostic-logging session. The call runs in any modern browser; the capture wrap engages only when the API is exposed. Also demonstrates the spec's privacy model: startDiagnosticLogging() resolves with a UUID even when no logging actually starts, so the page can never observe whether capture is happening.

why it shipped

WebRTC calls fail in ways that are painful to reproduce: NAT traversal quirks, codec negotiation, packet loss, jitter — all buried in the browser's internal state. Chrome has long had chrome://webrtc-internals and an internal event-logging pipeline, but a web app couldn't trigger a capture around a user-reported problem or correlate it with its own bug report. This API gives authorized apps a programmatic hook to start a capture, tag it with app metadata, and get back an ID — the same pattern as crash IDs — so a support engineer can line the browser's diagnostics up with the app's own logs. Critically, the diagnostics never flow back into the page, preserving user privacy: the spec deliberately provides no guarantees of success, so a page cannot even tell whether logging is authorized.

enabling it

Origin trial on desktop, Chrome 151–156 (chromestatus API, updated 2026-08-12; ship estimate 156, status “Proposed”). Registration is open on the Chrome origin trials console (trial name RTCDiagnosticLogging). To run locally today, launch Chrome 151+ with --enable-blink-features=RTCDiagnosticLogging or turn on chrome://flags/#enable-experimental-web-platform-features. The interface requires a secure context. For a real deployment the enterprise policy WebRtcDiagnosticLogCollectionAllowedForOrigins must also list the origin — per the blink-dev intent to experiment, that policy is what authorizes actual log collection. Every demo here feature-detects and shows these exact steps when the API is missing.

spec vs implementation — read this before coding against it

Two live divergences, both surfaced honestly by the demos (verified against Chromium main and the WICG draft, 2026-08-16):

  • Where the API lives. Chromium (and the Chrome 151 origin trial) binds an RTC interface at navigator.rtc (navigator_rtc.idl, gated RuntimeEnabled=RTCDiagnosticLogging). The current WICG draft instead specifies static methods on RTCPeerConnection — RTCPeerConnection.startDiagnosticLogging(). Feature-detect both.
  • What over-limit metadata throws. The spec mandates a TypeError when metadata exceeds 5 entries or a key/value exceeds 100 characters; Chromium main rejects with a RangeError (rtc.cc, RejectWithRangeError), measured in UTF-8 bytes.
