Press-and-release feedback

The ChromeStatus motivation for this change, built with the real EventTrigger interface: a press swells the control once, extra presses while it is held do nothing, and releasing shrinks it. Press both pads repeatedly and compare play-forwards, which does not auto-rewind, with replay, which always does.

Needs a flag in Chrome 151–158. The no-rewind behaviour ships in Chrome 151, but the script interface for event triggers, EventTrigger, is still behind the experimental EventTrigger runtime flag, and Chrome has no CSS event-trigger property yet. To run the pads:

  1. Open chrome://flags/#enable-experimental-web-platform-features, set it to Enabled, and relaunch; or
  2. launch Chrome with --enable-blink-features=EventTrigger.

      How it works

      1. Each pad gets a Web Animation (scale: 1 → 1.45, 600 ms, fill: both) that is created and immediately paused at 0 ms. Chromium's PerformPlay* functions only turn auto-rewind off when the animation is not idle (crbug.com/390314945), so pausing first is what makes the very first press honour the no-rewind rule.
      2. new EventTrigger({ eventType, eventTarget: pad }) registers an event listener on the pad. trigger.addAnimation(animation, "play-forwards") or "replay" picks the action.
      3. On every activation the page records currentTime in a capture-phase listener on the lane (before the trigger runs) and again in a bubble-phase listener (after it ran). A drop in currentTime with a positive playback rate is logged as a rewind.
      4. play-forwards on a finished animation calls play() with auto-rewind disabled, so it stays at 600 ms. Pressed during the release shrink, it flips the playback rate to positive and resumes from the current scale instead of jumping back to 0. replay uses forced auto-rewind, so every press restarts from 0.
      5. The release half is script. In Chrome 158 an animation can belong to only one trigger (addAnimation throws NotSupportedError for a second one), and EventTrigger ignores its deactivate action (the Invoke() TODO, crbug.com/441908430). A pointerup trigger with play-backwards is therefore not possible yet; the live checks below prove both limits.

      Findings

      • No rewind on repeated activation (verified): Chrome for Testing 158.0.8127.36 (Linux, headless) with --enable-blink-features=EventTrigger, 2026-11-25. After the swell finished at 300 ms (probe duration), a second pointerdown left it finished at 300 ms. A replay trigger on the same sequence restarted at about 17 ms.
      • Mid-release press resumes (verified): pressing while the animation was reversing at 200 ms set the playback rate to 1 and continued from 200 ms, then finished at the end.
      • One trigger per animation (verified): adding the same animation to a second EventTrigger threw NotSupportedError: Attaching multiple triggers to an animation is not allowed.
      • Deactivate action ignored (verified): addAnimation(anim, "play-forwards", "play-backwards") on an EventTrigger never ran the backwards action across repeated events.
      • Construction: a missing eventType throws TypeError; a missing eventTarget constructs a trigger whose eventTarget is null and that never fires.
      • Without the flag: AnimationTrigger and TimelineTrigger are exposed in Chrome 158 but EventTrigger is not, and CSS.supports("event-trigger", …) is false with or without the flag.
      • Real touch on an Android device: not verified.
