XML parsing in Rust for non-XSLT scenarios

Chrome is swapping its C-based XML engine (libxml2 lineage — a historical source of memory-safety CVEs) for a memory-safe Rust implementation across the common paths: DOMParser, XMLHttpRequest.responseXML, XML documents, SVG-as-XML. The web-facing contract is radical in its modesty: nothing may change. These demos turn that invisible swap into runnable checks.

concepts

  1. Compat battery

    Twelve tricky XML cases — namespaces, CDATA, predefined and character entities, processing instructions, xml:space, deep nesting — each parsed live by the real DOMParser and checked against its spec-required result. Green across the board is the whole point, on the old engine and the new one alike.

  2. parsererror anatomy

    XML failure has a strange contract: no exception — a document containing a <parsererror> element in a Mozilla-namespace. Break the XML in the live editor and inspect the exact error document your engine builds; a behavior the Rust engine must reproduce faithfully.

  3. Parser-surfaces inventory

    Which entry points route through the swapped engine? The page exercises each one for real — DOMParser, XMLHttpRequest.responseXML over a Blob URL, an XML-namespace SVG — and shows the deliberately excluded one: XSLT (XSLTProcessor keeps the old path for now).

why it shipped

XML parsers written in C have decades of CVE history — buffer overreads, use-after-free in entity handling — and every responseXML call runs one against attacker-supplied bytes. Rewriting in Rust removes the memory-corruption class outright if the new parser is perfectly compatible; that's why the observable contract of this change is "no observable change", and why it lands scoped to non-XSLT paths first (XSLT's libxslt coupling makes it the hard tail).
