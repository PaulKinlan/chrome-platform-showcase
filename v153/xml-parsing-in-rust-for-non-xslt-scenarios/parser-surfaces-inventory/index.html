Parser-surfaces inventory

"Non-XSLT scenarios" is a routing statement: some entry points hand bytes to the swapped Rust engine, one deliberately doesn't yet. Each card below exercises its surface for real — actual parses, an actual XHR, an actual namespaced SVG — so you can see every path that will silently change engines under your feet.

Runs automatically on load.

1 · DOMParser (application/xml) — swapped

…

The workhorse: feeds, configs, SVG strings. Result checked: namespaces + entities parse correctly.

2 · XMLHttpRequest.responseXML — swapped

…

A real XHR against a Blob URL served as application/xml; responseXML must be a parsed Document, not text.

3 · SVG parsed as XML — swapped

…

An image/svg+xml parse must produce a real SVGSVGElement root in the SVG namespace — the strictest namespace consumer most pages have.

4 · XSLTProcessor — NOT in this change

…

XSLT keeps the legacy path for now (the "non-XSLT" in the title). The probe reports whether the interface exists and runs a real one-template transform through it.

// All of these route through the (now Rust) XML parser:
new DOMParser().parseFromString(xml, "application/xml");
xhr.responseXML;                       // when the response is XML
new DOMParser().parseFromString(svg, "image/svg+xml");

// Deliberately NOT yet: XSLTProcessor / libxslt's coupled parsing.
