Capability elements: <camera> and <microphone>

Two new declarative HTML elements that each broker exactly one capability: <camera> requests a video track, <microphone> an audio track. Like the <usermedia> MVP they render browser-controlled UI so a real click precedes any permission prompt — but being single-capability, after the grant they become a trusted in-page toggle for the track, and they hand you a MediaStreamTrack via ontrack/.track instead of a whole stream.

concepts

  1. Element surface probe

    Detect the exact shipped interfaces — HTMLCameraElement / HTMLMicrophoneElement, the track/error properties, ontrack/onerror/oncancel handlers and setConstraints() — including the HTMLUnknownElement trap that catches naive tag sniffing, with the real CameraAndMicrophoneElements flag steps when absent.

  2. Single-capability toggle lab

    The elements' defining behavior: live <camera> and <microphone> markup wired to a video preview and an audio level meter, with a state ledger tracking every track/error/cancel event and the track's enabled/muted/ended transitions the element's post-grant toggle drives. Unsupported engines get an honest panel plus a clearly-labelled imperative rehearsal of the same monitoring contract.

  3. Constraints workbench

    Build the exact MediaTrackConstraintSet that setConstraints() accepts from real form controls, checked live against this browser's getSupportedConstraints() vocabulary — and learn the filtering rule: advanced/exact-required constraints are deliberately ignored so the element can never fail with a silent OverconstrainedError.

why it shipped

Permission prompts fired from JavaScript arrive with no context, and a user who once clicked "Block" falls into a permission hole only browser settings can fix. The Page-Embedded Permission Control work produced <usermedia> for combined capture; <camera> and <microphone> complete the set for the far more common single-capability cases. Because each element owns exactly one track, the browser can safely turn it into a stateful mute/unmute control after the grant — something <usermedia> deliberately doesn't do, since independent audio/video track states make one toggle ambiguous. The elements handle consent, run the underlying getUserMedia(), deliver the track, monitor its state, and offer in-page recovery from a previous "Block".

enabling it

Listed for Chrome 153 (status: Proposed) behind the CameraAndMicrophoneElements runtime feature — marked stable in current Chromium runtime_enabled_features.json5, so new builds have the elements on by default. On builds where they're absent, launch with --enable-blink-features=CameraAndMicrophoneElements (add UserMediaElement for <usermedia>), or enable chrome://flags/#enable-experimental-web-platform-features. The elements are additionally gated by the camera / microphone Permissions-Policy features of the embedding context.
