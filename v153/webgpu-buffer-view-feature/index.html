WebGPU: `buffer_view` feature

A WGSL language extension for reinterpreting data in variables. It adds an opaque host-shareable buffer type for storage, uniform, and workgroup variables, plus three built-in functions — bufferView, bufferArrayView, and bufferLength — that let a shader divide one variable into multiple logical variables and read the same bytes as multiple types, without copies and without extra bindings.

concepts

  1. Language feature probe

    Read the real navigator.gpu.wgslLanguageFeatures set, request a real adapter, and distinguish no-WebGPU from WebGPU-without-buffer_view.

  2. WGSL compile test bench

    Compile six minimal requires buffer_view; programs on your GPU and read the real getCompilationInfo() messages — including two programs that must fail everywhere.

  3. Type punning without copies

    A compute pass reads the same 16 bytes as vec4f and vec4u via bufferView and the readback is checked bit-for-bit against a CPU DataView reference.

  4. Subdividing one buffer

    Pack a header, an f32 array, and a u32 array into one storage buffer and split it in-shader with bufferArrayView + bufferLength.

why it shipped

WGSL had no way to reinterpret the bytes of a bound buffer as another type, so engines either bound the same GPUBuffer range several times with different declared types (each binding padded to 256-byte storage alignment) or burned bandwidth copying data between typed buffers. buffer_view adds an opaque type that can only be operated on by new built-in functions, which keeps the reinterpretation flexible for authors — type punning and logically sub-dividing one variable into multiple parts — while staying cheap to validate and safe to implement on Vulkan, D3D (ByteAddressBuffer), and Metal (char* casts).

availability & flags

ChromeStatus lists this for Chrome 153 (desktop, Android, WebView). In current Tint source the buffer_view language feature is gated as unsafe-experimental, so builds that have not yet flipped it on expose it only behind chrome://flags/#enable-unsafe-webgpu (command line: --enable-unsafe-webgpu; headless environments typically also need --enable-features=Vulkan to get an adapter at all). There is no origin trial. Detection is navigator.gpu.wgslLanguageFeatures.has('buffer_view') — it is a WGSL language feature, not a GPUFeatureName, so it never appears in adapter.features.
