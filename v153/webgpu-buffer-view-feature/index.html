WebGPU: buffer_view feature

A WGSL language feature (not a device feature): buffer_view lets a shader carve one uniform, storage, or workgroup variable into multiple logical views — and read the same bytes as different types — without extra bindings or copy passes. Discoverable through navigator.gpu.wgslLanguageFeatures and opted into per shader with requires buffer_view;.

concepts

  1. WGSL feature registry

    The honest detection surface, live: the page enumerates your browser's entire wgslLanguageFeatures set (a real setlike, no adapter needed) and highlights whether buffer_view is in it — alongside every other language feature your engine ships.

  2. requires-directive lab

    The per-shader opt-in, exercised for real: request an adapter and device, compile a module beginning with requires buffer_view;, and print the engine's actual getCompilationInfo() messages — success on supporting devices, the genuine error otherwise, and an honest no-adapter readout where WebGPU can't reach a GPU at all.

  3. Reinterpret visualizer

    What "same bytes, different types" means, byte by byte: edit 16 bytes and watch them read back live as u32, i32, f32, and 16-bit views (real typed-array reinterpretation — the CPU ground truth of what buffer_view does on the GPU), next to the WGSL you'd write with and without the feature.

why it shipped

Shaders constantly need one allocation seen many ways: a mixed-type particle buffer, a header followed by payload, packed data laid out for one pass and consumed by another. Without buffer_view, WGSL forces separate bindings (limited and costly), manual bitcast plumbing per element, or duplicate buffers. The proposal (gpuweb PR 6291) makes the reinterpretation declarative and validated by the compiler — and because it changes the language, it rides the WGSL language-feature mechanism rather than a GPUDevice feature flag.
