Joint Iteration

Zip, standardised: Iterator.zip(iterables) advances several iterators in lockstep and yields arrays of corresponding values; Iterator.zipKeyed(obj) does the same for named sources and yields objects. An options bag picks the length policy — "shortest" (default), "longest" with per-source padding, or "strict" which throws on mismatch.

concepts

  1. Zip playground

    Probe Iterator.zip and drive it live over editable lists: every run is the real static call, rendered row by row — or the genuine TypeError where the engine doesn't stage the proposal yet. Includes the decided edge case of zero sources (an already-completed iterator).

  2. Mode & padding explorer

    Same mismatched-length inputs, three policies: watch shortest truncate, longest pad each exhausted source with its own filler, and strict throw for real. The mode decisions come straight from the proposal's design-space table.

  3. zipKeyed dashboard

    The practical shape: three named "sensor" streams zipped into row objects with Iterator.zipKeyed, rendered as a live table — the keys of your object become the keys of every row, no positional bookkeeping.

why it shipped

Nearly every language ships zip (Python's zip/zip_longest/strict=True, Rust's Iterator::zip, C++ views::zip…), and a dozen JS libraries reinvent it with subtly different length policies. The TC39 proposal (Stage 4) settles the design space explicitly: 0+ sources, iterables only, both positional and keyed variants, per-source padding, and well-defined behavior when one source errors — first error wins, others get closed. Chrome 153 stages it behind the JavaScript-harmony flag.

enabling it

In developer trial in Chrome 153: chrome://flags/#enable-javascript-harmony, or --js-flags=--harmony-joint-iteration, or --enable-experimental-web-platform-features. Every demo calls the real statics and shows the true unsupported error otherwise.
