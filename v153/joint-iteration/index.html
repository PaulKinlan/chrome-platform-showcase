Joint Iteration

Two new static methods synchronise the advancement of multiple iterators — the operation most languages call zip. Iterator.zip takes an iterable of iterables and yields positional arrays; Iterator.zipKeyed takes an object of iterables and yields null-prototype objects keyed the same way. An options bag picks the length policy: "shortest" (default), "longest" with per-input padding, or "strict", which throws a TypeError on mismatch.

concepts

  1. Zip playground — editable inputs, a mode picker, and per-input padding driving real Iterator.zip() calls, with the yielded rows and any real TypeError shown as-is.
  2. Named series — the practical shape: Iterator.zipKeyed() merging separate time/temperature/humidity series into named rows for a live table, including the null-prototype detail that trips up hasOwnProperty habits.
  3. Mode lab — the three length policies run against the same mismatched inputs, side by side: shortest truncation, longest with padding vocabulary, and strict's real thrown TypeError, plus the invalid-mode and primitive-input error contracts.
  4. Lazy conveyor — zip over two infinite instrumented generators with .take(), proving pull-based laziness and that closing the zip closes every underlying source (the spec's IteratorCloseAll).

why it shipped

Positionally-aligned sequences are everywhere — labels and values, parallel arrays out of columnar data, several generators advancing in lock-step — and JavaScript had no standard way to walk them together: developers indexed arrays manually or pulled in lodash/itertools ports. The proposal reached TC39 stage 4 in 2026 after settling the design questions its README documents (iterable-of-iterables input, both positional and keyed variants, length policy as an option, per-input padding). Chrome 153 ships both methods on the Iterator constructor, composing with the shipped iterator helpers like take, map, and toArray.
