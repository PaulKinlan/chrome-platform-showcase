Joint Iteration

Walking several sequences in lock-step — zip — is a fixture of every iterator library and most languages; JavaScript finally gets it natively. The TC39 Joint Iteration proposal (Stage 4) adds two statics: Iterator.zip combines an iterable of iterables into tuples, and Iterator.zipKeyed combines an object of iterables into keyed records. An options bag picks how length mismatches resolve: shortest (default), longest (with per-input padding), or strict (throw). These demos call the real statics when your engine ships them and fall back to a clearly labelled spec-model when it doesn’t.

concepts

  1. Zip basics

    The canonical call: two or three live-edited sequences zipped into tuples, then chained straight into the shipped iterator helpers — because Iterator.zip returns an Iterator Helper, .map().take().toArray() just works.

  2. Mode matrix

    The options bag, inspected: the same unequal-length inputs run through shortest, longest, and strict side by side, with editable longest-mode padding — including proof (via a getter spy) that padding is only ever read in longest mode.

  3. Columnar records

    The practical case for zipKeyed: turn column-oriented data (arrays per field) into row records without index bookkeeping — plus the two contract details that surprise people: result objects have a null prototype, and undefined-valued keys are skipped entirely.

  4. Edge & failure lab

    The rejection and cleanup contract: strings and other primitives throw, zero inputs finish immediately, invalid modes and padding throw, shortest closes the losers, and a consumer return() closes every open input — in reverse order.

why it shipped

Positionally-aligned sequences are everywhere — parallel arrays from an API, columns from a data file, coordinates and labels, streams that advance together. Before this proposal every codebase reinvented zip (the proposal’s prior-art table lists 16 JS libraries shipping one), each with different answers to the hard questions: what happens when lengths differ, are the leftovers closed, can you pad, does a mismatch throw? The standard answers all of them with one options bag — shortest matches Python’s zip, longest matches itertools.zip_longest with per-input padding, strict matches zip(…, strict=True) — and adds the keyed variant no positional API can express. It reached Stage 4 (ecma262 PR #3802), and V8 ships it on by default (js_joint_iteration) in the engine Chrome 153 carries.

the shape

Iterator.zip(iterables, options?)       // iterable of iterables -> iterator of arrays
Iterator.zipKeyed(iterables, options?)  // object of iterables  -> iterator of records

options: {
  mode: "shortest" | "longest" | "strict",   // default "shortest"
  padding,   // longest mode only — iterable (zip) or keyed object (zipKeyed)
}

Iterator.zip([[0, 1, 2], [3, 4, 5]]).toArray()
// [[0, 3], [1, 4], [2, 5]]

Iterator.zipKeyed({ a: [0, 1], b: [2, 3] }).toArray()
// [{ a: 0, b: 2 }, { a: 1, b: 3 }]   — records have a null prototype

Both statics return an Iterator Helper, so every existing helper — map, filter, take, toArray, even the new join — chains directly off a zip.

running it today

Pure V8 language feature: no chrome://flags entry, no Blink runtime flag — it lives in v8/src/flags/flag-definitions.h as js_joint_iteration, already in the shipped set for the V8 in Chrome 153. Earlier Chromes may simply lack the implementation: Chromium 141 ignores --js-flags=--js-joint-iteration entirely (verified 2026-08-16). Outside the browser, deno run --v8-flags=--js-joint-iteration runs the real statics today (verified on Deno 2.9.5 / V8 15.0). Every demo probes typeof Iterator.zip first and labels each result native or spec-model.
