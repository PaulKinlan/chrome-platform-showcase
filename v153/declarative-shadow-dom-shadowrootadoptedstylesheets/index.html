Declarative Shadow DOM 'shadowrootadoptedstylesheets'

The shadowrootadoptedstylesheets attribute on <template shadowrootmode> lets a declarative shadow root adopt stylesheets at parse time — no script. It takes a space-separated list of specifiers; each is fetched exactly like a JavaScript import with module type "css" and its CSSStyleSheet is added to the shadow root's adoptedStyleSheets in the specified order.

Availability: enabled by default from Chrome 153 (this was the Chrome 148 Declarative CSS module scripts origin trial — see the v148 OT-era demos for the companion inline <style type="module" specifier> syntax, which remains experimental). On Chrome 148–152: enable chrome://flags/#enable-experimental-web-platform-features, or launch with --enable-blink-features=ShadowRootAdoptedStyleSheet (attribute only) or --enable-blink-features=DeclarativeCSSModules (attribute + inline CSS modules), or register for the DeclarativeCSSModules origin trial. There is no dedicated chrome://flags entry.

concepts

  1. Zero-Script Adoption

    A component styled entirely by <template shadowrootmode="open" shadowrootadoptedstylesheets="./card.css"> with zero JavaScript. A live probe reads shadowRoot.adoptedStyleSheets length and rule counts, checks the HTMLTemplateElement.prototype.shadowRootAdoptedStyleSheets IDL reflection, and parses a fresh test template on demand — honestly reporting unsupported when the attribute is ignored.

  2. Shared-Sheet Fan-Out

    Spawn N declarative components that all name the same specifier, prove they adopt the same CSSStyleSheet object (identity check), then mutate that one sheet and watch every component restyle at once — the memory/consistency use case.

  3. FOUC vs Script Upgrade

    Side-by-side replay of the same server-rendered component styled declaratively at parse time versus upgraded by script after a configurable delay — the visible flash of unstyled content the attribute exists to remove, plus the <link rel="modulepreload"> guidance for late-fetch avoidance.

  4. Script Interop

    The declaratively populated adoptedStyleSheets is the same mutable ObservableArray script has always had: append a constructed sheet, remove and reorder entries, and dynamically import(…, { with: { type: "css" } }) the same specifier to prove both paths share one module-map entry.

  5. Import-Map Resolution

    Because specifiers resolve exactly like JavaScript imports, a bare specifier such as showcase-theme works when an import map maps it — and fails honestly when it doesn't. Probe both, and compare against dynamic import() of the same bare specifier.

the syntax

<link rel="modulepreload" href="/styles/card.css" as="style"> <!-- avoid a late fetch -->

<my-card>
  <template shadowrootmode="open"
            shadowrootadoptedstylesheets="/styles/card.css /styles/theme.css">
    <h2>Styled with zero script</h2>
  </template>
</my-card>

Each specifier is imported with module type "css": relative (./, ../) and root-relative (/) URLs resolve against the document base, bare specifiers require an import map entry, and the response must be served as text/css. The attribute value is parsed as an ordered set of unique tokens; a fetch failure leaves an empty CSSStyleSheet in place rather than shifting the order.

why it shipped

"Styling and Customization" is the #1 reported pain point for Web Components. Before this attribute, sharing one set of styles across declarative shadow roots meant imperative CSS modules (script after parse — defeating declarative SSR), duplicated <style> blocks (more parser work, drift risk), or per-root <link> tags (FOUC). shadowrootadoptedstylesheets closes the gap: parse-time adoption, one shared CSSStyleSheet per specifier, no script, no flash. It ran as the Declarative CSS Modules origin trial from Chrome 148 and ships by default in 153.
