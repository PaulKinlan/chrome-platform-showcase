WebTransport headers and responseHeaders

WebTransport's CONNECT handshake finally speaks headers both ways: new WebTransport(url, { headers }) sends custom request headers (auth tokens, metadata) with the extended CONNECT, and the new transport.responseHeaders attribute exposes the server's reply headers — null until the session is established, a real Headers object after. Behind the WebTransportHeaders flag in Chrome 153.

concepts

  1. Surface probe

    The honest detector is the readable half: 'responseHeaders' in WebTransport.prototype. The request-side headers option can't be probed by construction (unknown dictionary members are silently ignored — demonstrated live), which makes the prototype read the only trustworthy signal.

  2. CONNECT handshake lab

    Compose real request headers (a bearer token, custom metadata), open a genuine WebTransport session to an endpoint of your choice, and read responseHeaders back when it establishes — every step reporting its true outcome, including the network realities of HTTP/3 reachability.

  3. null-until-ready contract

    The lifecycle rule made observable: construct a real transport and read responseHeaders immediately — the spec says null before establishment (which is why the IDL's original [SameObject] label was wrong, per the comment in Chromium's own IDL). The read, the state transition, and cleanup are all real.

why it shipped

Real deployments gate WebTransport endpoints the same way they gate WebSockets: token auth, tenant routing, protocol metadata — decisions that belong at the handshake, not smuggled through the first datagram after paying a round trip. HTTP/3's extended CONNECT always carried header fields; this change simply lets pages populate them (within fetch's forbidden-header rules) and read the server's back, closing a gap WebSocket-over-HTTP filled years ago.

enabling it

In developer trial in Chrome 153 behind WebTransportHeaders (experimental): launch with --enable-blink-features=WebTransportHeaders, or enable chrome://flags/#enable-experimental-web-platform-features. Actually exercising the handshake also needs an HTTP/3 endpoint that speaks WebTransport — the lab defaults to the public echo server and reports connection failures honestly.
