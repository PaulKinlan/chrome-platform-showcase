The runScripts option

Today only createContextualFragment can execute scripts in dynamically-inserted markup. The renewed API adds {runScripts: true} to SetHTMLUnsafeOptions, so any unsafe setter can opt in — while every setter stays script-inert by default, and safe variants never get the option at all.

Flag required in Chrome 153 for the runScripts lane. Blink runtime features SetHTMLCanRunScripts + NewHTMLSettingMethods (experimental). Enable chrome://flags/#enable-experimental-web-platform-features in Chrome/Canary 153+ and relaunch, or launch with --enable-blink-features=NewHTMLSettingMethods,SetHTMLCanRunScripts,TrustedTypesCreateParserOptions. Lanes 1 and 3 work in every current Chromium — so you can compare real behaviour today.

script-execution shoot-out

Each lane inserts the same markup: a paragraph plus an inline <script> that pushes a marker into window.__rhismMarks and stamps its own sandbox. The verdicts below are read from that marker — they can and do come back "did not run".

1 · setHTMLUnsafe(html) — default

Spec: inserted scripts are inert. Expected: marker absent.

not run yet

2 · setHTMLUnsafe(html, {runScripts: true})

New in this feature: the script should execute after insertion, like createContextualFragment.

3 · createContextualFragment(html)

Today's only script-running inserter — the quirky precedent this option regularises.

code

// inert by default — nothing new here:
el.setHTMLUnsafe('<p>hi</p><script>boom()</script>');       // boom never runs

// explicit opt-in (unsafe setters only, Chrome 153 + flag):
el.setHTMLUnsafe(markup, { runScripts: true });                 // script executes after insertion

// the old way this replaces:
el.append(document.createRange().createContextualFragment(markup));
