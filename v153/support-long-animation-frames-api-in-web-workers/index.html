Support Long Animation Frames API in Web Workers

LoAF (Chrome 123) reports main-thread frames that blew their budget — but a worker's event loop can jank too, delaying every message queued behind a long task, and nothing reported it. This change extends long-animation-frame performance entries to workers: a long task blocking a worker's loop becomes an observable entry inside that worker. All demos here spawn real workers.

concepts

  1. Worker support probe

    Spawn a real worker and ask it the honest questions: what's in its PerformanceObserver.supportedEntryTypes, and does observing long-animation-frame there succeed or throw? Both answers come back over postMessage from the actual worker context.

  2. Blocked-worker monitor

    Inject a real 300ms synchronous block into a live worker and watch two instruments: the LoAF entries the worker reports (on Chrome 153), and a message round-trip latency meter that spikes on every engine — the observable pain LoAF-in-workers finally attributes.

  3. Main-vs-worker parity

    The same deliberate jank run on both threads: the main thread's LoAF observer (shipped since 123) reports real entries with duration and blocking time, while the worker column reports whatever its loop can see — a live parity table of the gap this feature closes.

why it shipped

Teams moved heavy work off the main thread exactly because of LoAF-style metrics — and then lost observability: a worker handling input decode, wasm inference, or OffscreenCanvas paints can starve its own queue for hundreds of milliseconds with no field signal. Extending LoAF (per the delayed-message-timing / congested-moments explainer) reuses the vocabulary developers already ship RUM pipelines for, now anchored to the worker's event loop instead of rendering frames.
