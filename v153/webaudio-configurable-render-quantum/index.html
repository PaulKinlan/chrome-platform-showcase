WebAudio: Configurable render quantum

In Chrome 153 the renderSizeHint option on AudioContext and OfflineAudioContext ships enabled by default — no more origin trial or flag. Pass "default" (128 frames), "hardware" (let the browser match the output device's buffer), or an integer to pick the render quantum yourself; read the granted value back from BaseAudioContext.renderQuantumSize, and observe it from inside an AudioWorkletProcessor via the new renderQuantumSize global and the block size process() actually receives.

concepts

  1. Worklet-Verified Quantum

    Don't trust a single readout: for each renderSizeHint value this page cross-checks four independent observations — the main thread's renderQuantumSize, the AudioWorkletGlobalScope.renderQuantumSize global, the length of the outputs[0][0] block process() receives, and the currentFrame delta between consecutive callbacks — and reports honestly whether they agree and what your browser actually granted, including non-power-of-two and out-of-range requests.

  2. Underrun Stress Lab

    The practical trade-off, measured live: a worklet synthesises a tone while you dial up synthetic DSP load per sample and hammer the main thread with jank. Live meters show the render deficit — wall-clock elapsed minus audio rendered — plus stall episodes, an honest underrun proxy. Run the same load at a small and a large quantum and compare the recorded runs side by side.

  3. Hardware Hint Report

    What does renderSizeHint: "hardware" actually negotiate on this device? Builds default and hardware contexts (at both latencyHint extremes), reads back renderQuantumSize, baseLatency and outputLatency, states plainly whether "hardware" made any difference here, and produces a copyable device report.

  4. Offline Quantum Grid

    OfflineAudioContext has no hardware, so the spec says "hardware" behaves like "default" there — verify it. Then see the render quantum become an observable timing grid: suspend() rounds up to the next quantum boundary, so the same 10 ms suspension lands on different frames at 128, 512, and 2048-frame quanta. Includes the spec's out-of-range NotSupportedError probes.

why it shipped

Web Audio rendered in fixed 128-frame blocks since its first release. Real audio hardware doesn't: Android devices commonly use 192 or 240-frame native buffers, Windows WASAPI defaults to 10 ms (441/480 frames), and CoreAudio varies by device. When 128 doesn't divide the hardware buffer, the renderer must run an uneven number of quanta per hardware callback — peak CPU roughly doubles on alternating callbacks, capping graph complexity and causing avoidable glitches. renderSizeHint lets an app align the quantum with the hardware ("hardware"), or trade latency for throughput with a large explicit quantum (batch-style AudioWorklet processing at 1024/2048 frames amortises per-call overhead). The feature ran as an origin trial from Chrome 145 and ships enabled by default in Chrome 153.

the API surface

  • new AudioContext({ renderSizeHint }) / new OfflineAudioContext({ …, renderSizeHint }) — (AudioContextRenderSizeCategory or unsigned long), default "default"
  • "default" → 128 frames; "hardware" → the browser picks a size appropriate to the output device (same as default for OfflineAudioContext)
  • Integer → used as the render quantum size; values outside [1, 6 × sampleRate] must throw NotSupportedError
  • BaseAudioContext.renderQuantumSize — the granted size, readable on every context
  • AudioWorkletGlobalScope.renderQuantumSize — the same value visible inside worklets, matching the outputs[0][0].length that process() receives
