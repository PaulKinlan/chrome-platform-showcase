Abort reason basics

The plumbing this feature builds on, live: pass any value to controller.abort(reason) and a still-pending fetch() promise must reject with that exact value — not a copy, not a wrapper. Pick a reason kind, abort a real request to this site, and check the identity yourself. This half shipped in Chrome 98; the Chrome 153 change extends the same reason into the Response body consumers (see the mid-stream probe).

Every run below performs a real fetch("/features") and aborts it, so DevTools will log an intentionally cancelled request (net::ERR_ABORTED). That is the demo working, not a bug.

The reason lives on the signal too

Once aborted, the reason is retained as signal.reason, and signal.throwIfAborted() throws it. A pre-aborted signal (AbortSignal.abort(reason)) makes fetch() reject with the reason before any network I/O happens at all — this run makes no request.

the code

const controller = new AbortController();
const pending = fetch("/features", { signal: controller.signal });

const reason = new Error("user closed the search panel");
controller.abort(reason);

try { await pending; }
catch (err) {
  err === reason;                 // true — the exact value, by identity
  controller.signal.reason === reason;   // true
  controller.signal.aborted;             // true
}

// No argument? The spec mints an "AbortError" DOMException for you:
const c2 = new AbortController();
c2.abort();
c2.signal.reason instanceof DOMException; // true, name === "AbortError"
