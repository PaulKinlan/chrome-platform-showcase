Mid-stream forwarding probe

This page exercises the one contract Chrome 153 changes. It fetches a genuinely chunked response from this site, waits for the headers (so the fetch() promise has resolved), reads one chunk, then calls controller.abort(sentinel) while the body is still in flight. The Fetch Standard says the pending reader.read() must reject with the sentinel itself; pre-153 Chromium substitutes a generic AbortError. The verdict below is whatever your browser really did.

Chrome ≤152? The forwarding lives behind the Blink runtime feature ForwardReasonToFetchBodyAbort (status experimental, crbug.com/502133195 — no dedicated chrome://flags entry). Relaunch with --enable-blink-features=ForwardReasonToFetchBodyAbort, or --enable-experimental-web-platform-features, to see the forwarded path before 153. Firefox already forwards the reason. Running the probe cancels a request on purpose, so DevTools will show one net::ERR_ABORTED entry per run.

Same probe through response.text()

The forwarding applies to every body consumer, not just raw stream reads. This variant lets response.text() start buffering the chunked body, then aborts with a structured object reason { code: "SUPERSEDED", by: "newer-query" }.

the code

const controller = new AbortController();
const res = await fetch(STREAM_URL, { signal: controller.signal }); // resolves at headers
const reader = res.body.getReader();
await reader.read();                       // chunk 1 arrived — body still open

const sentinel = new Error("showcase-sentinel: panel closed at chunk 1");
const pendingRead = reader.read();         // in flight…
controller.abort(sentinel);

try { await pendingRead; }
catch (err) {
  err === sentinel;
  // Chrome 153+ / Firefox: true  — the reason was forwarded to the Response
  // Chrome ≤152:           false — generic DOMException "AbortError"
}
