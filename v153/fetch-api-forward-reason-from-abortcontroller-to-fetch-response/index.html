Fetch API: Forward reason from AbortController to fetch Response

Since Chrome 98 you can call controller.abort(reason) and a still-pending fetch() promise rejects with exactly that reason. But once the promise has resolved — headers in, body still streaming — Chromium threw the reason away: response.text(), response.blob() and response.body reads rejected with a generic AbortError. Chrome 153 closes that spec gap: the abort reason now propagates all the way into the Response object’s consumers, matching the Fetch Standard (and Firefox). These demos abort real streaming fetches and report what this browser actually forwards.

concepts

  1. Abort reason basics

    The part that already shipped: pick a reason (default AbortError, an Error, a string, a structured object), abort a real pending fetch, and inspect the rejection’s identity, signal.reason, and throwIfAborted().

  2. Mid-stream forwarding probe

    The exact contract Chrome 153 fixes: fetch a chunked response, read one chunk, abort with a sentinel reason, and see — with a timeline — whether reader.read() rejects with your reason (v153 behaviour) or a generic AbortError (pre-153).

  3. Consumer rejection matrix

    An inspection table over every Response consumer — text(), json(), arrayBuffer(), blob(), bytes(), a body reader — crossed with each reason kind, every cell filled from a real aborted fetch.

  4. Cancellable download

    Why it matters in a product: a streaming download whose catch handler branches on the forwarded reason (“you cancelled at 4,096 bytes” vs a timeout), with the signal.reason workaround pre-153 code still needs.

why it shipped

The Fetch Standard’s abort steps say the deserialized abort reason is used both to reject the fetch() promise and to error the response’s body. Chromium only implemented the first half, so error-handling code at the consumption site — often far away from the code that owns the AbortController — saw an anonymous AbortError with no way to tell a user cancel from a timeout from a navigation teardown. Firefox is already compliant; Chrome 153 makes Chromium match, behind the Blink feature ForwardReasonToFetchBodyAbort (on by default at 153).

the shape

const controller = new AbortController();
const res = await fetch(url, { signal: controller.signal }); // headers arrived

const textPromise = res.text();          // body still streaming…
controller.abort(new DOMException("User closed the panel", "TimeoutError"));

try { await textPromise; }
catch (err) {
  // Chrome 153+: err IS the reason you passed to abort()
  // Chrome ≤152: err is a generic "AbortError" DOMException
}

running it today

On Chrome 153+ the forwarding is on by default. On earlier Chromium the Blink runtime feature exists behind --enable-blink-features=ForwardReasonToFetchBodyAbort (it has no dedicated chrome://flags entry; --enable-experimental-web-platform-features also enables it, status experimental in runtime_enabled_features.json5, tracked as crbug.com/502133195). The probes here never assume: they run the real abort and report the rejection they actually received.
