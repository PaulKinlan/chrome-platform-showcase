Fetch API: Forward reason from AbortController to fetch Response

When you abort a fetch you can pass a custom abort reason. If the fetch promise is still pending, that reason already surfaces as the rejection. But when the abort lands after the headers arrived — while response.text(), response.blob(), or the response.body stream is still reading — Chromium used to throw the reason away and substitute a generic AbortError. Chrome 153 forwards the real reason to every body-read surface, matching the Fetch spec (and Firefox).

concepts

  1. Reason relay — the canonical litmus: one real streamed fetch, aborted mid-body with a marked custom reason, and a verdict on whether your browser forwarded it to response.text() or swapped in a generic AbortError.
  2. Two-phase timeline — an inspection tool that runs the abort in both windows — before the headers resolve the fetch promise, and after, mid-body — and shows per-phase which rejection carried your reason. The first phase has worked for years; the second is what ships in 153.
  3. Cancel diagnostics — the product use case: a download UI with a user cancel button and an AbortSignal.timeout() deadline combined via AbortSignal.any(). With reason forwarding the catch handler can tell the user why the download stopped; without it, both causes collapse into the same generic error.
  4. Stream teardown — the edge matrix: what reader.read(), reader.closed, and a parallel clone().arrayBuffer() each reject with, what a non-Error abort reason (a plain string) looks like on arrival, and the default AbortError you get when abort() is called with no reason at all.

why it shipped

Applications increasingly use rich abort reasons — AbortSignal.timeout() produces a TimeoutError, user cancellations carry app-specific errors — and branch their error handling on them. That contract silently broke the moment a response started streaming: the fetch promise had already resolved, so the abort surfaced on the body-read promises, where Chromium substituted a generic AbortError. Firefox followed the spec here; Chromium, Edge, and Safari did not. Chrome 153 closes the gap so the reason survives end-to-end, whichever side of the headers the abort lands on.
