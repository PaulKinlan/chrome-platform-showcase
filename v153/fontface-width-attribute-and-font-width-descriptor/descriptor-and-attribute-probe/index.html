what each probe does

  1. Prototype attribute — "width" in FontFace.prototype. The spec IDL is [BindingAlias="stretch"] attribute CSSOMString width; before 153 the prototype simply has no width.
  2. Constructor dictionary member — new FontFace("t", "url(x)", { width: "75%" }). WebIDL ignores unknown dictionary members silently, so the check is whether the resulting face actually carries 75% (read back via .width, falling back to .stretch which names the same attribute).
  3. Alias binding, JS side — construct with { stretch: "condensed" }, then confirm .width reads "condensed", then set .width = "expanded" and confirm .stretch follows. One attribute, two names.
  4. @font-face descriptor — inject @font-face { … font-width: 87.5%; } into a real stylesheet and read it back through the CSSOM. A parser that drops the declaration returns an empty string.
  5. font-width property (related, tracked separately) — CSS.supports("font-width", "75%") next to CSS.supports("font-stretch", "75%"). The ChromeStatus entry covers the loading-API surfaces above; the property rename is the same CSS Fonts 4 change and is probed here so the page reports the whole picture honestly.

the code

// 2 — dictionary member (ignored members don't throw; read back to know)
const f = new FontFace("probe", "url(data:,)", { width: "75%" });
const took = ("width" in f ? f.width : f.stretch) === "75%";

// 4 — descriptor parse + CSSOM read-back
sheet.insertRule('@font-face { font-family: p; src: url("data:,"); font-width: 87.5%; }');
const rule = sheet.cssRules[0];
rule.style.getPropertyValue("font-width");   // "87.5%" when supported, "" when dropped
