v153 · speechrecognitionresult timestamps

Result-object capability probe

Feature-detecting these attributes has a trap: SpeechRecognitionResult is declared [LegacyNoInterfaceObject], so there is no window.SpeechRecognitionResult constructor to probe. You must inspect a live result instance. This demo runs the real checks and shows the correct detection recipe alongside the one that silently fails.

Enable it: the attributes sit behind the Blink runtime flag WebSpeechTimestamps. In Chrome 153–159 it is experimental: turn on chrome://flags/#enable-experimental-web-platform-features, or launch Chrome with --enable-blink-features=WebSpeechTimestamps. Chromium main (after the M159 branch) enables it by default on Windows, macOS and Linux; Android and ChromeOS still need the flag. The names changed on the way: Chrome 153–155 expose an earlier draft, audioStartTime / audioEndTime (nullable milliseconds on the page's time origin). Chrome 156+ and the editor's draft (web-speech-api PR #192) use speechStartTime / speechEndTime — non-nullable double seconds on the session audio timeline, where 0 is the first audio frame the recognizer consumed. This page reads the spec names first and reports the draft names, labelled as such, if that is all your build has. Real values also need a recognition backend that supplies segment timing.

Live result inspection

The only reliable check is on a real SpeechRecognitionResult. This starts a short recognition and inspects the first result's own properties — honestly reporting whatever your engine returns.

Idle. Inspecting requires microphone access and a recognition backend; in headless or blocked-mic environments this reports the error instead of a fake result.

detection recipe

Does not work — there is no constructor, so this throws or is always false:

'speechStartTime' in SpeechRecognitionResult.prototype   // ReferenceError: not defined

Works — probe a real result instance inside onresult:

recognition.onresult = (event) => {
  const result = event.results[event.resultIndex];
  if ('speechEndTime' in result) {              // spec name, Chrome 156+
    const startS = result.speechStartTime;       // seconds on the session audio timeline
    const endS = result.speechEndTime;
  } else if ('audioEndTime' in result) {        // earlier draft, Chrome 153–155 only
    const endMs = result.audioEndTime;           // ms on the time origin, may be null
  }
};

The spec leaves precision implementation-defined; the explainer says implementations such as Chromium coarsen raw engine timestamps (for example to 2 ms buckets) to reduce fingerprinting, mirroring HTMLMediaElement.currentTime. Do not expect sub-millisecond timing.
