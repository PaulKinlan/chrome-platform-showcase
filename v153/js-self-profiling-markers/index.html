JS Self-Profiling Markers

The JS Self-Profiling API lets a page sample its own call stacks on real user devices — but a field trace is full of unexplained gaps where the browser was doing style, layout, paint, or garbage-collection work that stack sampling cannot see. The Chrome 153 origin trial adds a marker to each sample — script, gc, style, layout, paint, or other — so those gaps become attributable. These demos probe every prerequisite honestly, attempt the real API, and teach the trace format interactively.

concepts

  1. Policy & marker probe

    Each prerequisite checked separately with a real call: the Profiler global and its prototype shape, the actual Document-Policy response header this route was served with, crossOriginIsolated (markers require it), and a live new Profiler(…) attempt surfacing the exact result.

  2. Live trace lab

    The real thing, attempted: profile a mixed workload (hot JS, forced layout, allocation storm), then analyse the returned trace — frames, stacks, samples, and the marker histogram — or an honest blocked panel naming exactly what stopped it.

  3. Marker anatomy

    An interactive walk through the trace format using a clearly-labelled recorded example: click samples to resolve their stackId chains, filter by marker, and see why a missing marker means idle and why markers sit behind cross-origin isolation.

why it shipped

Stack sampling profiles only the page’s JavaScript. Some browser work (GC especially) interrupts stack execution and is invisible to it; rendering work between tasks shows up as unexplained dead time. Teams shipping the Self-Profiling API in the field — the API exists since Chrome 94 — kept hitting traces they could not interpret. A per-sample marker attributes that time to the browser activity that actually ran: script, gc, style, layout, paint, or other, with GC timing deliberately coarsened (10 ms resolution, post-hoc) so the marker is not a GC side-channel.

the shape

// Served with:  Document-Policy: js-profiling
const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10_000 });
// … work happens …
const trace = await profiler.stop();

trace.samples[0];
// { timestamp: 1551.734, stackId: 2, marker: "script" }   ← the new field
// { timestamp: 1601.905 }              ← no stack, no marker: idle
// { timestamp: 1620.001, marker: "gc" }  ← stackless browser work, now attributed

// enum ProfilerMarker { "script", "gc", "style", "layout", "paint", "other" }
// IDL: [CrossOriginIsolated] ProfilerMarker? marker  — markers need COOP+COEP

running it today

Three independent gates, all probed live by the demos: (1) the response header Document-Policy: js-profiling — this showcase route does not currently send it (a server-side TODO is recorded for the reviewer; the v147 worker-profiling demo is served with it today), so the constructor demos here surface the real DOMException Chrome throws without it. (2) the marker field itself: Chrome 153 runs the JSSelfProfilingMarkers origin trial; locally, launch with --enable-blink-features=ExperimentalJSProfilerMarkers (no dedicated chrome://flags entry; --enable-experimental-web-platform-features also enables it). (3) cross-origin isolation (crossOriginIsolated === true, via COOP+COEP headers) — the IDL gates marker on it.
