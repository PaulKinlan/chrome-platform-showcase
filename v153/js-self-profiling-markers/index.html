JS Self-Profiling Markers

The Self-Profiling API (new Profiler(...)) samples your own call stacks on real user devices — but a trace full of gaps tells you nothing about why the thread was busy. Markers fix that: each sample gains an optional marker field naming the engine activity at capture time — script, gc, style, layout, paint, or other — so gaps become attributable. These pages run real profiling sessions on this very origin (the server sends the required Document-Policy: js-profiling for them).

concepts

  1. Marker gates probe

    Three real gates stand between you and a marked sample: the js-profiling document policy (probed by constructing a real Profiler), crossOriginIsolated (the marker field is COI-gated in the proposal), and the engine actually implementing markers (probed by inspecting a genuine trace). Each gate reports its live state.

  2. Live trace explorer

    Run a real ~600ms profiling session while the page deliberately burns script, thrashes layout, and paints — then parse the returned ProfilerTrace: sample count, stack coverage, and a histogram of marker values (or the honest "no marker field in any sample" on engines that predate the feature).

  3. Gap-attribution workbench

    The motivating story: samples with no stack used to be unexplainable gaps. The workbench renders your real trace as a timeline strip — each sample a tick, coloured by marker when present — and counts how many stackless samples the markers managed to attribute versus how many remain mystery idle time.

why it shipped

Field profiling (Facebook, Microsoft and others drove the original API) produces traces from devices you'll never reproduce locally. Without engine context, a 40ms hole in the samples could be GC, a forced layout storm, or paint — three different fixes. DevTools shows those categories locally; markers bring the same vocabulary to field traces, deliberately coarse (10ms-resolution samples, COI-gated) so GC timing doesn't become a fingerprinting or GC-observability side channel.
