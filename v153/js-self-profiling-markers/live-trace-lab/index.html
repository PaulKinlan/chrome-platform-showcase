Live trace lab

The whole point of markers is attributing a real trace’s dead time. This lab attempts exactly that: construct a real Profiler, run a deliberately mixed workload — hot JavaScript, forced style/layout, an allocation storm to invite GC — then stop() and analyse whatever the browser actually returned: sample counts, stack coverage, and the per-marker histogram. Every gate that blocks the run is named, never papered over.

Profile a mixed workload

Runs for about a second. The workload is real: fib(24) loops (script), 300 style-write + offsetHeight-read cycles on a live element (style/layout), and a million short-lived allocations (GC pressure).

what a marker histogram buys you

Without markers, a field trace from this exact workload shows stacks for the fib phase and unexplained gaps for much of the rest — you cannot tell a layout stall from a GC pause from idle. With markers (Chrome 153 origin trial + cross-origin isolation), the same gaps come back labelled style, layout, gc… which is the difference between “something was slow” and “we thrash layout in the commit phase”.

the code

const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10_000 });
profiler.addEventListener("samplebufferfull", () => console.warn("buffer full"));

runHotJs();          // stacks with marker: "script"
thrashLayout();      // stackless samples with marker: "style" / "layout"
allocateGarbage();   // interrupting samples with marker: "gc"

const trace = await profiler.stop();
const histogram = {};
for (const s of trace.samples) {
  const key = s.marker ?? (s.stackId === undefined ? "(no marker — idle)" : "(no marker + stack)");
  histogram[key] = (histogram[key] ?? 0) + 1;
}
