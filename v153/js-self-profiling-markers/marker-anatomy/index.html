Marker anatomy

A profiler trace is a trie: frames are deduplicated function descriptions, stacks are linked lists of frame ids, and each sample is a timestamp plus an optional stackId — and now, optionally, a marker. Walk a worked example below: filter by marker, select any sample, and watch its stackId chain resolve, including the samples where no stack exists and only the marker explains what the browser was doing.

Honest labelling: the trace below is a recorded worked example assembled from the shapes in the WICG markers explainer — it was not produced by your browser on this page (this route cannot run the profiler yet; the live trace lab attempts the real thing and says exactly why when it cannot). Every field name and enum value matches the explainer and spec PR #89.

The marker enum, and the two rules people miss

markermeaning (explainer definition)
scriptScript-processing-model activity — your JavaScript and its plumbing.
gcGarbage collection. GC interrupts stack execution, so a sample can carry both a stack and marker: "gc" — the frames were paused, not running. Timing is post-hoc at 10 ms resolution by design, so the marker is not a GC side-channel.
style / layout / paintThe three rendering stages of “update the rendering”, per the resize-observer processing-model description.
otherBrowser work that fits none of the above.
(missing)Rule 1: a sample with no marker member means the idle state is assumed — absence is meaningful, so analysis code must use "marker" in sample, not truthiness alone.
(gating)Rule 2: the IDL is [CrossOriginIsolated] ProfilerMarker? marker — without COOP+COEP isolation the member never appears, even on Chrome 153 with the origin trial active.

the shape

dictionary ProfilerSample {
  required DOMHighResTimeStamp timestamp;
  unsigned long long stackId;
  [CrossOriginIsolated] ProfilerMarker? marker;   // ← new in the 153 origin trial
};
enum ProfilerMarker { "script", "gc", "style", "layout", "paint", "other" };
