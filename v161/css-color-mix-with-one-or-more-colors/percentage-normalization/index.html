Percentage normalisation corners

Each colour in a variadic color-mix() takes an optional percentage. This page drives three of them with sliders and checks Chrome against the spec’s normalisation rules, including the cases where a colour disappears or a transparent result still has a hue.

Ships in Chrome 161. Before that, enable chrome://flags/#enable-experimental-web-platform-features (there is no dedicated flags entry), or launch Chrome/Canary with --enable-blink-features=CSSColorMixVariadic or --enable-experimental-web-platform-features. How it works

The question: does Chrome apply CSS Values 5’s normalisation exactly, including the corners where intuition fails? The page computes the expected sRGB result in JavaScript from the spec steps and compares it with getComputedStyle(). Four corners worth knowing:

  • Sum under 100%: the shortfall becomes transparency. Three colours at 30% give alpha 0.9.
  • Sum over 100%: everything scales down proportionally, so 50/50/50 is an equal mix.
  • Omitted colours get only what is left: with 60% and 60% specified, the specified sum clamps to 100% and the omitted colour gets 0%. It vanishes from the mix.
  • Every percentage 0%: the result is fully transparent, and because each pairwise step falls back to progress 0.5, later colours weigh more than earlier ones even in a rectangular space.

Findings

Tested 2026-11-26 on Chrome for Testing 160.0.8184.0 with --enable-experimental-web-platform-features: all six corners match the spec algorithm. The two results that surprise people: color-mix(in srgb, red 60%, lime 60%, blue) computes to color(srgb 0.5 0.5 0) because the omitted blue is given 0%, and color-mix(in srgb, red 0%, blue 0%, lime 0%) computes to color(srgb 0.25 0.5 0.25 / 0), so lime carries half the weight even though every colour asked for 0%. The colour channels of a fully transparent result still matter if you later strip the alpha with relative colour syntax. Percentages outside 0–100% (for example red 120% or red -10%) are rejected by the parser, which is unchanged from the two-colour form. Chrome 158: the three-colour values are rejected; not verified in Chrome 161.
