How it works

  1. Chrome 161 accepts color-mix(<color-interpolation-method>?, [<color> && <percentage [0,100]>?]#): any number of colours, each with an optional percentage.
  2. Omitted percentages share whatever is left of 100% equally, so color-mix(in oklab, a, b, c) is a one-third mix of each.
  3. The nested form needs hand-worked weights: the inner pair is two-thirds of the total, so the outer call gives the third colour 33.3333%.
  4. The page sets both strings as style.background, reads getComputedStyle().color for each, and compares.

Common errors and fixes

  • The whole declaration is dropped in Chrome 160 and older without the flag: the parser rejects a third colour, so use @supports (color: color-mix(in srgb, red, lime, blue)) and keep the nested value as the fallback.
  • Percentages above 100% or below 0% are a parse error for that colour, not a clamp.
  • Mixing with white or grey in oklch keeps the other colour's hue; use oklab for tints, as the default does.

Findings

Tested 2026-11-26. Chrome for Testing 160.0.8184.0 (Canary build) with --enable-blink-features=CSSColorMixVariadic or --enable-experimental-web-platform-features: every check above passes; an equal three-colour sRGB mix of red, lime and blue computes to color(srgb 0.333333 0.333333 0.333333), the same as the nested form. Chrome 158.0.8127.36 stable, with or without either flag: any value with a third colour is rejected by the parser, and CSS.supports() returns false. Two-colour mixes and the omitted in <space> (defaulting to oklab) already work in 158. Chrome 161 itself: not verified (no build available in this environment).
