How it works

  1. At parse time the browser checks only the argument grammar, random-item(<declaration-value>, [<declaration-value>?]#): a non-empty first argument, then one or more comma-separated items that may be empty. Unbalanced braces and stray !, ;, ), ] or } make it invalid.
  2. The key is only parsed as a <random-key> at computed-value time. So random-item(serif, sans-serif) and random-item(fixed -0.5, serif, sans-serif) both parse, then make the property invalid at computed-value time (serif is not a key, and -0.5 is out of [0, 1]).
  3. When an item is picked, it is substituted like a var() value. An empty item, or an item whose own var() fails, leaves the property invalid at computed-value time: color then inherits, which is rgb(0, 0, 0) here.
  4. Items that are not picked are never resolved, so random-item(fixed 0.999, var(--missing), rgb(1, 2, 3)) is fine.
  5. In a shorthand, the picked item is expanded: margin: random-item(fixed 0, 1px 2px, 3px 4px) gives margin-top: 1px and margin-right: 2px.

Findings

Tested 2026-11-28 in Chrome for Testing 158.0.8127.36 (Linux, headless), with and without --enable-experimental-web-platform-features: every valid-grammar row fails (the declaration is dropped), every invalid-grammar row is vacuous, and every compute row fails. The one exception is the var() trap: a value with var() anywhere inside random-item() is kept at parse time by Chrome 158, because any declaration containing var() is, and then resolves to the property's inherited or initial value. A registered custom property (--length, syntax <length>) also keeps the declaration at parse time, because registered properties only validate after substitution, and then computes to its initial value 0px. An unregistered custom property accepts any random-item() and stores it as a token string, because custom properties accept any tokens. Native behaviour in Chrome: not verified, no Chrome build has the function yet.
