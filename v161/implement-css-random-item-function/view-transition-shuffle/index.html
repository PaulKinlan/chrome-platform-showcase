Redraw in a View Transition

A card wall whose layout and styling come from random picks, redrawn by changing the random key inside a View Transition. It tests whether a new draw, including a change of grid span, animates like any other style change.

Not in any Chrome build yet (checked 2026-11-28). The implementation, CL 8816057, is still in review. It adds the runtime flag CSSRandomItemFunction with status experimental, so once it lands in Canary you can turn it on with chrome://flags/#enable-experimental-web-platform-features or by launching with --enable-blink-features=CSSRandomItemFunction. ChromeStatus lists Safari Technology Preview 251 as shipping it and Firefox as prototyping it behind layout.css.random-item.enabled. Chrome 158 already ships random(), which this page uses for the labelled fallback. Probing this browser…

Live demo: redraw the wall inside a View Transition

The cards are this feature's own concept pages. Each card's column span, tilt and top-stripe colour come from a random pick keyed by --draw-N element-scoped. Redraw changes N inside startViewTransition(), so every card glides from its old pick to its new one. The DOM order never changes, so keyboard and screen-reader order stay put.

    How it works

    1. Question: random picks are fixed per key, so can a View Transition animate between two draws, and does the layout change (a card's span) animate as well as the paint (tilt, colour)?
    2. Native path: each card gets inline grid-column: random-item(--draw-N element-scoped, span 1, span 2, span 3) and the same for rotate and border-block-start-color, with separate key names so the three picks are independent.
    3. Fallback path, used when @supports (color: random-item(--x, red, blue)) fails: registered <integer> properties take random(--draw-N element-scoped, 0, 2, 1), and if(style()) maps each index to the same items.
    4. Each card has view-transition-name: match-element, so the browser pairs old and new snapshots by element identity without generated names. The redraw prefers wall.startViewTransition() (scoped to the list, so the rest of the page stays interactive), then document.startViewTransition(), then a plain update.
    5. With prefers-reduced-motion: reduce the tilt is removed and the transition animations are turned off; the redraw still happens.

    Findings

    Tested 2026-11-28 in Chrome for Testing 158.0.8127.36 (Linux, headless), fallback path: a redraw changes the picks for most cards, and the View Transition runs and finishes. The readout records whether the scoped or the document transition was used. Span changes reflow the grid, and match-element animates each card to its new box. Below 30rem the page forces every card to one column, so on phones only the tilt and stripe colour change. Native random-item() path in Chrome: not verified, no Chrome build has the function yet.
