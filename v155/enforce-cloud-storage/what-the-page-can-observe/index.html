What the page can observe

A page hands a download to the browser and its knowledge ends at the click. Whether the file went to disk, to corp Google Drive under a DLP rule, or nowhere at all — the page cannot tell the difference, and this demo earns that claim: it triggers real downloads with every plausible listener attached, and journals exactly which ones speak and which stay silent.

Download via data: link
    Trigger a download. Rows on white are real events; rows on grey were written by a timer because nothing happened — and that nothing is the finding.

    The generated file goes through Blob → URL.createObjectURL() → a[download] → click(). Listeners for error, progress, load, loadend and abort are attached to the anchor before the click. On every browser this page has been run in, none of them ever fires — a download is a navigation-shaped handoff, not an observable transfer.

    What the user sees instead — manual observation only

    On a managed profile where a File-download DLP rule fires with the Enforce cloud storage action, the outcome surfaces in browser UI this page cannot read: the download shelf reports "Failed - Local download blocked" (IDS_PROMPT_DOWNLOAD_FORCED_SAVE_TO_CLOUD) and chrome://downloads explains "Your organization's policies aren't met" (IDS_FORCED_SAVE_TO_CLOUD_DESCRIPTION), while the file is uploaded to the corp drive. Both strings are quoted from Chromium's generated_resources.grd, not detected — there is nothing here to detect with.

    That is the design. A page that could read the DLP outcome could tell a managed profile from an unmanaged one — a fingerprinting surface — and a page trying to exfiltrate data could probe its way around the rule. The silence you journalled above is the enforcement boundary working.
