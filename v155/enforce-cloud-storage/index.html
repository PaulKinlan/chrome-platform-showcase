A download that never touches the disk

From Chrome 155, an admin can give a File-download DLP rule a new action: Enforce cloud storage. When the rule triggers, the file is not saved to the user's local storage at all — it is uploaded to the organisation's corp Google Drive or corp OneDrive instead. There is no web-facing API. The page that served the file is never told, and that asymmetry is what these demos are about.

concepts

  1. What the page can observe

    Real downloads, triggered from real controls, with a journal of everything the page learns at each step. The last thing it learns is the click. No completion event, no destination, no verdict — proven by listening on every channel and showing they stay silent.

  2. The rule an admin writes

    Compose the DLP rule from its real parts — trigger, scope, tags, action, destination — and read the resulting user journey narrated step by step, down to the exact Chromium enum values and download-shelf strings involved. An illustration of admin-console behaviour, clearly not the thing itself.

  3. Saving a file yourself

    The same bytes saved two ways: handed to the browser's download pipeline — where this DLP action lives — and written through showSaveFilePicker(), where the page does get a completion signal. A live comparison of the two paths, with honest fallbacks where the picker is unavailable.

why it shipped

Data-loss-prevention rules on downloads used to have blunt endings: allow the file, warn about it, or block it. Blocking protects the data but stops the work — the user often had a legitimate reason to want that file, just not on an unmanaged local disk that leaves the organisation's control the moment a laptop does.

Enforce cloud storage is the middle path. The download still happens, but its destination is decided by policy rather than by the page or the user: the file lands in the user's corp Google Drive or corp OneDrive, where retention, audit and sharing controls already apply. Locally, the download surface reports that the local save was blocked; the file itself is where the organisation can see it.

there is no API

// None of this exists, and none of it is proposed:
navigator.downloads               // undefined — chrome.downloads is extension-only
navigator.enterprise              // undefined
anchor.ondownloadcomplete         // no such event has ever existed

// What actually exists is browser-internal (Chromium source):
//   FinalContentAnalysisResult::FORCE_SAVE_TO_CLOUD
//   DOWNLOAD_DANGER_TYPE_FORCE_SAVE_TO_GDRIVE  (= 24)
//   DOWNLOAD_DANGER_TYPE_FORCE_SAVE_TO_ONEDRIVE (= 25)
//   EVENT_RESULT_FORCED_SAVE_TO_CLOUD           (reporting, = 8)

That is by design. A page has never been told what happens to a download after the handoff — no completion event, no path, no verdict — and this feature simply routes inside that existing blind spot. A page that could read the DLP outcome could tell managed profiles from unmanaged ones, which would be both a fingerprinting surface and an evasion aid.

seeing it for real

Nothing on this site can trigger the policy: it is an enterprise rollout (Chrome 155 on desktop platforms), enforced browser-side for profiles managed by an organisation whose admin has created a File-download Chrome DLP rule with the Enforce cloud storage action. On a managed profile with such a rule, the observable surface is the downloads UI — the shelf reports "Failed - Local download blocked" and chrome://downloads explains "Your organization's policies aren't met" (both strings from Chromium's generated_resources.grd) — while the file appears in the corp drive. That is manual observation on managed hardware, and these pages label it as such rather than pretending to detect it.

Most of what is public about this feature is documented for admins, not for web developers; the public surface is the downloads UI. Where these pages state internals, they cite the Chromium source they were read from.

portfolio note

Three angles are built: the canonical observable-edge demo, the admin-side configuration anatomy, and the edge/migration comparison against page-initiated saving. A "practical product use case" concept is deliberately not built: with no web-facing API there is nothing a product could integrate — the honest product guidance (serve downloads normally; never assume a local path) is folded into the first and third concepts instead of being padded into a fourth page.
