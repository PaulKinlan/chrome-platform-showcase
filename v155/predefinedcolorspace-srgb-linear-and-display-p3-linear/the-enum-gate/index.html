The enum gate

New enum values are the quietest kind of platform change, and the easiest to feature-detect wrong. This page throws deliberately bad and deliberately new values at the gate and shows every rejection verbatim — then demonstrates the older failure mode where nothing is thrown at all, which is the one that actually catches people.

WebIDL enums are case-sensitive allowlists: any string not in the browser's copy of PredefinedColorSpace is rejected with a TypeError during dictionary conversion, before canvas code ever runs. That is why SRGB fails on every browser and srgb-linear fails only on browsers whose enum predates Chrome 155.

The failure mode that doesn't throw

The trap: a browser that predates the colorSpace member entirely — not just these two values — ignores it, because unknown dictionary members are silently dropped in WebIDL, while unknown enum values for known members throw. On such a browser getContext("2d", {colorSpace: "srgb-linear"}) returns a perfectly ordinary sRGB context and no exception. Code that treats "didn't throw" as "supported" ships wrong colors there.

Not probed yet. This uses a getter that flips a flag if — and only if — the dictionary conversion actually reads colorSpace.

The honest probe therefore has two stages, in order: attempt creation and catch the possible TypeError, then read the result back — getContextAttributes().colorSpace or ImageData.colorSpace — and compare against what was requested. Only requested === read back is support. Every other combination, including "no exception", is not.

Two rejections are not always the same rejection

Run srgb-linear and display-p3-linear above on a pre-155 Chromium and compare the two messages, because they can differ in a telling way. On the Chromium 141 this page was built with, srgb-linear was rejected with a bare "not a valid enum value" while display-p3-linear was rejected with an extra "Failed to read the 'colorSpace' property from 'CanvasContextCreationAttributesModule'" prefix — the first value was already in that build's enum behind the ColorSpacePredefinedLinearSpaces runtime gate, the second had not been added at all. Same TypeError, different distance from shipping. Your browser's own messages are in the table above.

the code this runs

// Stage 1: attempt, catching the enum gate.
let ctx = null, gateError = null;
try {
  ctx = document.createElement("canvas")
    .getContext("2d", { colorSpace: candidate });
} catch (error) {
  gateError = error;               // TypeError: not in this browser's enum
}

// Stage 2: never trust a quiet gate — read back.
const got = ctx?.getContextAttributes().colorSpace;
const supported = got === candidate; // the ONLY test that means support
