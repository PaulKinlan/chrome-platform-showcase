A canvas that stores light, not gamma

Every 2D canvas keeps its pixels in a gamma-encoded space, which is right for storage and wrong for arithmetic: add two encoded grays and you get a number, not twice the light. Chrome 155 adds "srgb-linear" and "display-p3-linear" to PredefinedColorSpace, so a canvas backing store can hold values that are proportional to luminance — the space where compositing, resampling, and physically-based rendering actually work.

concepts

  1. The enum, swept

    All four PredefinedColorSpace values offered to getContext, OffscreenCanvas, and new ImageData(), each on a fresh surface, each verdict read back from getContextAttributes(). An unknown enum value throws a TypeError — which is what makes this feature honestly detectable, and this page detects it honestly.

  2. The light-math it fixes

    Overlap two lights with globalCompositeOperation: "lighter", then shrink a checkerboard. A gamma canvas gets both wrong in measurable ways; the same operations on a linear canvas match the physics. The math a linear canvas does for you runs in JavaScript alongside, so every browser can see the difference — and the native half only claims to run where it really does.

  3. Same color, different numbers

    One fillStyle, read back through every color space the browser will give you. getImageData has converted between srgb and display-p3 for years — the linear spaces join the same pipeline, and the pixel numbers show exactly what "as defined by CSS" means.

why it shipped

sRGB's transfer function exists because eyes notice small differences between dark shades more than between bright ones, so 8 bits go further if the encoding spends more of them on the dark end. That is a storage decision. The moment you do arithmetic on those values — average neighbouring pixels while scaling down, add overlapping light sources, interpolate during anti-aliasing — the encoding turns the math wrong: averaging a black-and-white checkerboard gives 50% of the code values but about 21% of the light.

Games, image pipelines, and anything else that models physical light already work internally in linear spaces, and WebGL and WebGPU have offered linear-ish paths for years. The 2D canvas had no way to say "keep my pixels linear". These two enum values give it one, defined by reference to the same srgb-linear and display-p3-linear spaces CSS Color 4 defines, so a color that round-trips through CSS, canvas, and getImageData means the same thing everywhere. WebKit suggested the addition and already implements it; ChromeStatus notes a rec2100/rec2020 linear space was requested and deliberately not included here.

the API shape

// The enum, as of Chrome 155:
enum PredefinedColorSpace { "srgb", "srgb-linear", "display-p3", "display-p3-linear" };

// A linear backing store for a 2D context…
const ctx = canvas.getContext("2d", { colorSpace: "srgb-linear" });
ctx.getContextAttributes().colorSpace;   // "srgb-linear"

// …for pixel data…
const px = new ImageData(64, 64, { colorSpace: "display-p3-linear" });

// …and for readback, converting on the way out:
ctx.getImageData(0, 0, 8, 8, { colorSpace: "srgb-linear" });

// Linear values quantise badly in 8 bits, so they pair with float16
// (already shipping): colorType: "float16" / pixelFormat: "rgba-float16".

enabling it now

Chrome 155 ships both values enabled for all users (the rollout is guarded by the ColorSpacePredefinedLinearSpaces runtime feature, status experimental before the 155 launch). To try it earlier in Canary or Dev:

  1. Launch with --enable-blink-features=ColorSpacePredefinedLinearSpaces, or
  2. enable chrome://flags/#enable-experimental-web-platform-features (there is no dedicated chrome://flags entry for this feature), or launch with --enable-experimental-web-platform-features.

Measured while building these pages, on Chromium 141: without flags, all four surfaces reject both linear values with TypeError: The provided value 'srgb-linear' is not a valid enum value of type PredefinedColorSpace. With experimental web platform features enabled, srgb-linear is accepted and echoed back from getContextAttributes() — 141 predates this feature, and its srgb-linear enum value sits behind the older CanvasHDR-era guard — while display-p3-linear is not in that binary at all and still throws. The demos report whatever your browser actually does, surface by surface.
