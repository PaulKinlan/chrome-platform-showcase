PredefinedColorSpace srgb-linear and display-p3-linear

A canvas has always stored pixels the way screens encode them, not the way light adds up. Chrome 155 lets a 2D canvas keep its backing store in a linear color space — srgb-linear or display-p3-linear — where a pixel value of 0.5 really is half the light of 1.0, and every blend, average and addition suddenly behaves like physics.

concepts

  1. The four values, asked directly

    All four enum values tried against all four API surfaces that accept one — getContext, OffscreenCanvas, new ImageData and getImageData — with the browser's actual answer read back per cell. Creating a context is not the probe; what getContextAttributes() reports afterwards is.

  2. Blending as light, not as code values

    The same two compositing operations run in an sRGB store and a linear store, side by side, with pixel readbacks. Half-transparent green over red comes out visibly brighter in linear — because that is what mixing light does — and additive lighter stops clipping to white.

  3. The transfer function, by hand

    Pick a color and watch it move through the sRGB transfer curve the spec defines: encoded value, linear value, and what an 8-bit linear store rounds it to. The math runs in page JavaScript as a labelled computed reference, and is checked against the browser's real readback wherever the linear spaces exist.

  4. The enum gate

    What actually happens when a browser meets a colorSpace value it does not know: a TypeError at WebIDL enum conversion, with the real messages on display — and the older, sneakier failure mode where the whole member is silently ignored, which is exactly why "it didn't throw" must never be read as "it's supported".

why it shipped

The sRGB encoding a canvas uses by default is perceptual: it spends its 8 bits where human vision is sensitive, which is the right trade for storing pictures and the wrong one for doing arithmetic. Average two sRGB pixel values and you get a color darker than the light you would actually see; add two and you clip. Anything that touches physical light — game rendering, anti-aliasing, downscaling, blurring, interpolation — wants pixel values proportional to luminance first, which is why every serious rendering pipeline works in linear and converts at the edges.

WebGL and WebGPU pipelines have had this working style for years; the 2D canvas could only fake it in JavaScript. Adding srgb-linear and display-p3-linear to PredefinedColorSpace — the same spaces CSS Color 4 already defines — lets a 2D backing store hold linear values natively, in sRGB or Display P3 primaries. WebKit suggested the addition and had already implemented it; Chrome 155 catches up.

the API shape

// A 2D context whose backing store is linear sRGB.
const ctx = canvas.getContext("2d", { colorSpace: "srgb-linear" });

// The honest probe is the readback, not the absence of an exception.
ctx.getContextAttributes().colorSpace   // "srgb-linear" if supported

// ImageData in a linear space — construction, and readback from a context.
const px  = new ImageData(1, 1, { colorSpace: "display-p3-linear" });
const out = ctx.getImageData(0, 0, 1, 1, { colorSpace: "srgb-linear" });
out.colorSpace                          // "srgb-linear"

running it before 155

The feature ships enabled for all users in Chrome 155; there is no origin trial. On earlier builds it sits behind the runtime feature ColorSpacePredefinedLinearSpaces (status experimental in Chromium's runtime_enabled_features.json5), so to try it today: enable chrome://flags/#enable-experimental-web-platform-features and relaunch, or launch with --enable-blink-features=ColorSpacePredefinedLinearSpaces.

Measured on the Chromium 141 these pages were built with: the experimental-features flag enables srgb-linear on all four surfaces — every readback below was reproduced for real behind it — but display-p3-linear was added to the enum later and no flag revives it on a 141 build. The pages report whatever your browser actually returns.
