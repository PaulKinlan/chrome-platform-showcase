v155 · canvas color spaces

Same color, different numbers

A canvas color space is invisible until you read pixels back. Then it is the whole answer: the same fillStyle becomes different bytes in every backing store, because getImageData hands you values in a color space, converted by the CSS Color 4 rules the spec points at. Most of this page works in the browser you're using right now — the linear rows join in Chrome 155.

Ships in Chrome 155. The srgb and display-p3 rows below have worked since Chrome 94 and run here today. The srgb-linear / display-p3-linear rows run where the enum values exist — Chrome 155, or Canary/Dev with --enable-blink-features=ColorSpacePredefinedLinearSpaces or experimental web platform features — and are reported as the TypeError they are everywhere else.

Pick a color

One color, four backing stores

Each row creates a canvas with that colorSpace, fills one rect with the color above, and reads the pixel twice: once in the canvas's own space (what is actually stored) and once converted to srgb (a common yardstick — out-of-gamut colors clip against it). Storage in the linear spaces is the raw backing value quantised to the 8 bits getImageData defaults to, which is precisely why linear canvases pair with float16.

The converter is in getImageData itself

One plain srgb canvas, filled once. Then the same pixel is requested under every colorSpace the settings dictionary will take, plus pixelFormat: "rgba-float16" for the full-precision view. The canvas never changes — only the question does. This is how you inspect what any canvas is really holding, and it works on the two shipped spaces in every current Chrome.
