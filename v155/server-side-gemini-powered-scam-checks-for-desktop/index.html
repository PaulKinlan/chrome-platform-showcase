Server Side Gemini Powered Scam Checks for Desktop

Chrome 155 moves desktop scam detection for Enhanced Safe Browsing users from the on-device Gemini Nano model to a server-side Gemini model, matching Android. When a page shows high-confidence scam indicators — keyboard lock, full-screen takeovers, pointer lock, suspicious clipboard commands — Chrome may send the page’s text to Safe Browsing, where it is processed ephemerally (never logged, retained or used for training), and Chrome may then show its own warning interstitial.

What a web page cannot do: there is no JavaScript API for this feature. A page cannot tell whether the visitor has Enhanced Safe Browsing on, whether a check ran, what the model decided, or force a warning. Everything on these pages works with the real web-observable surface around the check — the trigger APIs your page calls, the text your page renders, the commands it copies, and the review process if your site is flagged. Nothing here imitates Chrome’s warning.

concepts

  1. Trigger API playground

    Call, for real, the web APIs Chrome’s detector listens for — full-screen, navigator.keyboard.lock(), pointer lock, navigator.vibrate(), clipboard writes and the notification prompt — plus a de-fanged “lockdown” sequence showing how scam pages chain them and how the escape hatch still works.

  2. Page-signal self-audit

    Paste your own HTML/JS or fetch a same-origin page and get a line-by-line report of every call site that maps to a Chromium ClientSideDetectionType trigger, with advice for keeping legitimate uses unambiguous.

  3. What gets sent

    Render a page in a sandboxed frame and extract the visible text the way the scan sees it: hidden text dropped, query string stripped from the URL, the source-verified 5-byte minimum, the optional title prefix and the 5-scans-a-day desktop quota.

  4. Clipboard command check

    The desktop clipboard trigger mirrored token-for-token from Chromium: loaders, runners, decoders and endpoints. See why curl … | bash install snippets can match while npm install does not — then copy for real.

  5. False-positive review

    Flagged by mistake? Check a site’s Safe Browsing status, request a review in Search Console, report an incorrect warning — and generate the SafeBrowsingProtectionLevel enterprise policy that controls who gets these checks.

how a check flows (from Chromium source)

  1. Enhanced Safe Browsing gate. Every trigger handler in ClientSideDetectionHost returns immediately unless IsEnhancedProtectionEnabled().
  2. A trigger fires. ClientSideDetectionType: keyboard lock, pointer lock, full-screen, vibration, clipboard copy, notification prompt, a real-time URL lookup that forces a request, the local phishing model, and others. Keyboard lock, vibration and clipboard classify only once per URL.
  3. Pre-classification decides whether the URL may be classified at all (allowlists, private addresses, error pages).
  4. Safe Browsing asks for an intelligent scan (LlamaForcedTriggerInfo.intelligent_scan). High-confidence allowlisted sites are recorded as ALLOWLISTED and no text is sent.
  5. Model choice. On desktop in 155, SERVER_SIDE_MODEL replaces ON_DEVICE_MODEL, capped at 5 scans a day by default (SERVER_SIDE_MODEL_EXCEED_QUOTA after that).
  6. Text threshold. If the page’s inner text is 5 bytes or fewer, nothing is sent (EMPTY_TEXT / TEXT_TOO_SHORT).
  7. Verdict. The server returns an IntelligentScanVerdict. If it says scam, Chrome shows its own interstitial. Your page never sees any of this.

what developers should know

  • There is no new API to adopt or flag to test against. A legitimate game, kiosk or presentation app that uses keyboard lock or full-screen is not penalised for that alone; it only makes the page eligible for a closer look.
  • Compared with the on-device model this replaces, the server model removes the failure mode csd.proto records as ON_DEVICE_MODEL_UNAVAILABLE (“device incapability or not enough space on disk”); the new failure modes are SERVER_SIDE_MODEL_UNAVAILABLE, SERVER_SIDE_MODEL_OUTPUT_MISSING and the daily quota.
  • Enterprises control enrolment with the existing SafeBrowsingProtectionLevel policy (0 off, 1 standard, 2 enhanced). Only level 2 runs these checks.
  • If a warning hits your site in error, the review process is the usual Safe Browsing one; see False-positive review.

the observable surface

// None of these calls reveal whether a check ran. They are the
// web APIs Chrome's ClientSideDetectionHost listens for.
await el.requestFullscreen();              // FULLSCREEN_API
await navigator.keyboard.lock(["Escape"]); // KEYBOARD_LOCK_REQUESTED
await el.requestPointerLock();             // POINTER_LOCK_REQUESTED
navigator.vibrate(200);                    // VIBRATION_API
await navigator.clipboard.writeText(cmd);  // CLIPBOARD_COPY_API
await Notification.requestPermission();    // NOTIFICATION_PERMISSION_PROMPT
