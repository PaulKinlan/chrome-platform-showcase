Server Side Gemini Powered Scam Checks for Desktop

Chrome on desktop used to look for tech-support and similar scams with an on-device Gemini Nano model. From this release it sends the text of a suspicious page to a server-side Gemini model instead, the same way Chrome on Android already does. This only happens for users enrolled in Enhanced Safe Browsing, and only after the page shows high-confidence scam indicators. The text is processed ephemerally: not logged, not retained, not used for training. Enterprises control enrollment with the SafeBrowsingProtectionLevel policy.

What these pages can and cannot do. This is a browser protection, not a JavaScript API. A web page cannot start a scam check, read its result, or detect that one happened, and no page here does or shows a scam verdict. The concepts use what is real and observable instead: the web APIs that Chromium's own source lists as detection triggers, how a legitimate site uses them responsibly, the real enterprise policy, and the documented pipeline. Every manual step that only Chrome's own UI can show is labelled "manual observation". The client-side switch for the desktop server model is the Chromium base feature ClientSideDetectionServerModelForScamDetectionDesktop (--enable-features=ClientSideDetectionServerModelForScamDetectionDesktop). It is a field-trial feature controlled together with Google's servers, so turning it on locally does not guarantee a scan.

concepts

  1. Trigger-signal self-audit inspection

    Chromium's client-side detection records why it pinged Safe Browsing (ClientSideDetectionType in csd.proto): keyboard lock, pointer lock, fullscreen, vibration, clipboard copy, a notification prompt, a credit-card form, and more. This page calls each of those real APIs on demand. It shows exactly what your page would be doing, with genuine return values, and how to release each one. No verdict is shown, because none is observable.

  2. Legitimate fullscreen & keyboard-lock patterns practical

    Remote desktops, games and presentation tools need the same powerful APIs that tech-support scams abuse. This is a working fullscreen and keyboard-lock "shortcut trainer" with a live scorecard. It checks that the session started from a user gesture, locks a specific key list rather than every key, keeps exit instructions visible, unlocks on exit, and does not re-enter fullscreen by itself. It also tries the anti-patterns for real so you can see the browser refuse them.

  3. Enrollment & enterprise policy configuration

    A SafeBrowsingProtectionLevel generator for Windows (.reg), macOS (plist key) and Linux (managed or recommended JSON), driven by the real policy definition (0 NoProtection, 1 StandardProtection, 2 EnhancedProtection; mandatory or recommended). It is paired with a "who gets the server-side check" decision readout and the chrome:// pages to verify it.

  4. Pipeline: on-device vs server-side edge · migration

    A step-through of the old (Gemini Nano, on device) and new (server-side Gemini) pipelines, built from Chromium's IntelligentScanInfo fields. Its branch explorer walks the documented reasons no model output is produced (EMPTY_TEXT, TEXT_TOO_SHORT, ALLOWLISTED, SERVER_SIDE_MODEL_EXCEED_QUOTA, and others) and the 5-scans-per-day desktop default. It measures this page's own innerText, and tells site owners what to do after a false-positive warning.

use-case portfolio

  • Basic / canonical and inspection tooling: trigger-signal-self-audit. There is no developer-callable surface, so the "basic" use is understanding which of your own API calls are scam-trigger signals.
  • Practical product use: legitimate-fullscreen-patterns.
  • Configuration: enrollment-and-policy.
  • Edge / failure / migration: pipeline-on-device-vs-server, covering the no-output branches, quota, the on-device to server migration, and false-positive recovery.
  • Advanced composition: not applicable. The feature exposes no web-facing API (ChromeStatus: no spec, no explainer, no samples; Chromium implements it entirely in components/safe_browsing). There is nothing to compose with other platform APIs, and simulating a verdict would be fake output. The self-audit already exercises the real trigger APIs together.
