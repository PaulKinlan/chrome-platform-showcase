Trigger-signal self-audit

Chrome does not send every page to a model. Its client-side detection waits for a reason, and Chromium's csd.proto lists those reasons as ClientSideDetectionType. Several are ordinary web APIs. Each card calls one for real and shows the genuine result, and the page tracks which of these signals it is currently exhibiting.

Manual observation only for the scan itself. A page cannot detect a scam check or its verdict, and this page never claims one. Even with a trigger present, a server-side scan also needs Enhanced Safe Browsing, Google's server-side trigger rules (LlamaTriggerRuleInfo), the page not being on a high-confidence allowlist, enough page text, and daily quota (desktop default: 5 intelligent scans per day). Heads-up: if you use Enhanced Safe Browsing, calling these APIs here can make Chrome evaluate this page's (benign) text. To look for client-side detection activity yourself, open chrome://safe-browsing in a new tab before you start. Tab names vary by version.

what a site owner should take from this

  • One of these calls on its own is ordinary. Video players use fullscreen, games use pointer lock, checkouts render card forms. They are reasons to look, not verdicts. Safe Browsing decides from what the model extracts from the page text (brand and intent fields) plus its other intelligence.
  • The combination that tech-support scams use is keyboard lock plus fullscreen plus text that imitates an operating-system security alert and asks the user to phone someone. If your product needs locks, see legitimate patterns.
  • Other trigger types in the same enum (TRIGGER_MODELS, IMAGE_EMBEDDING_MATCH, UNFAMILIAR_LOGIN_PAGE, USER_REPORT, POLICY_ENGINE, FORCE_REQUEST) come from Chrome's own models, user reports or server rules. Page script cannot exercise them, so they are not shown.
