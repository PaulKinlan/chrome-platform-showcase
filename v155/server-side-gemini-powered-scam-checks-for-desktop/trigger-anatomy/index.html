Trigger anatomy lab

Chrome doesn't send every page to Gemini. A scan only starts once a page shows scam-characteristic behaviour. Chromium lists those behaviours in the ClientSideDetectionType enum (KEYBOARD_LOCK_REQUESTED, FULLSCREEN_API, POINTER_LOCK_REQUESTED, …). Build a tech-support-scam specimen below and see which documented trigger types it would raise and exactly what page text a scan would read.

Educational model, not Chrome's classifier. This page never calls the specimen's APIs, never contacts Safe Browsing and cannot trigger or see Chrome's real scam check. The specimen is inert: it has no links or controls. The mapping uses Chromium's csd.proto enum names. The content-cue scan is a set of simple, visible regular expressions written for this page, and it outputs no score or verdict because Chrome's real decision (local models, allowlists, the server-side Gemini model, Safe Browsing verdicts) can't be reproduced here.

how the mapping is grounded

The trigger names come from enum ClientSideDetectionType in Chromium's components/safe_browsing/core/common/proto/csd.proto. When one fires for an Enhanced Safe Browsing profile, the client-side-detection host can ask for an "intelligent scan". In Chrome 155 on desktop, the feature kClientSideDetectionServerModelForScamDetectionDesktop sends that scan to a server-side Gemini model, which returns brand, intent and a scam_score (IntelligentScanInfo). The 2025 Google post on the on-device predecessor named the Keyboard Lock API as a characteristic trigger.

// csd.proto (excerpt)
enum ClientSideDetectionType {
  FORCE_REQUEST = 1;            // server-pushed rules ("Llama" trigger rules)
  TRIGGER_MODELS = 2;           // local DOM / visual model fired
  NOTIFICATION_PERMISSION_PROMPT = 3;
  KEYBOARD_LOCK_REQUESTED = 4;
  POINTER_LOCK_REQUESTED = 5;
  VIBRATION_API = 6;
  FULLSCREEN_API = 7;
  CLIPBOARD_COPY_API = 8;
  CREDIT_CARD_FORM = 9;
  …
}
message IntelligentScanInfo { brand; intent; no_info_reason; model_type; scam_score; }
